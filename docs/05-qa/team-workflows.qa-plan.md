# 기획·디자인·개발 팀별 QA 계획

기준: docs/PRD.md 핵심 5단계와 docs/ARCHITECTURE.md 불변식. 실제 팀 자료 대신 합성 데이터를 사용한다. 제품 코드를 결과에 맞춰 튜닝하지 않고 최초 실패도 보존한다.

| 팀 | 업무 시나리오 | 정상·경계 조건 |
|---|---|---|
| 기획 | 출시 범위, 인터뷰, 예산, KPI, PRD 반영 | 미결 승인 vs 확정 후 실행, 문서 제목, 출시 제외, 근거 없는 매출 질문 |
| 디자인 | 시안 승인, 브랜드 예외, 접근성, Figma 전달 | 승인 요청 vs 파일 전달, 레이어 이름, 터치 크기, 승인자 혼동 |
| 개발 | 배포/롤백, 라이브러리, 우선순위, DB 일정 | 미결 롤백 vs 승인된 실행, 테스트 이름, 오류율 기준, 로그 취합 |

- L1: 기존 전체 회귀 + 팀별 데이터 160개 파생 검사. 마스킹/동의/인용 변조 포함.
- L2/모델: 실제 production classifyItem 48개(팀당 네 레이블 각 4개), answerQuestion 18개(팀당 6개). 실제 Groq 호출, DB/검색/임베딩/작업/Slack/telemetry는 메모리 대체. 외부 업무 쓰기/발송 없음.
- DB: 기존 격리 PGlite SQL 전체 및 RLS 2,016조합 재실행. 수집 원자성/중복/동의/위조/늦은 완료 포함. 팀 이름 자체로 권한이 달라지는지 주장하지 않는다.
- 브라우저: 기존 게스트 Playwright 1440/390px 완주 및 부서 접근 차단/쓰기 0 검사를 재실행한다. 현재 디자인팀 데모가 없다면 이를 누락으로 보고하고, 다른 팀을 디자인팀으로 재명명하여 통과로 포장하지 않는다.
- L3~5 Chrome MCP 전용 스킬 흐름은 미사용. Playwright 실행 증거를 별도 기록한다.
- 모델 정답은 에이전트 작성 잠정 정답이며 독립 검수되지 않았다. 문자열 검사로 의미적 근거 전체를 보장하지 않는다. RAG 검색 정확도나 실제 Slack/회의 봇 이벤트 전달을 테스트했다고 주장하지 않는다.
- 사전 스캐너: WSL에서 Windows CRLF로 실행 실패. 검증 도구 제약으로 기록하며 제품 CRITICAL=0으로 치환하지 않는다.
