분류 decision 재현율은 반복 포함 24/24지만, false promotion 3건이 존재한다. “결정을 놓치지 않았다”만으로 품질이 좋다고 판단할 수 없다.

거절 실패의 설계상 의심 지점: AnswerDraft는 refused=true여도 citations 최소 1개를 요구한다(lib/contracts.ts). 프롬프트는 근거 부족 시 거절을 요구하고, answerQuestion은 llm_refusal만 정상 거절로 변환한다. 실제 공급자 400/422는 SchemaInvalidError로 매핑되어 이 경로를 빠져나간다. 스키마와 거절 의도의 충돌이 의심되지만 원시 공급자 오류 내용은 보안 정책상 수집하지 않았으므로 단일 근본 원인으로 확정하지 않는다. schema_invalid 전체를 refused로 덮는 방식도 기술 오류를 숨기므로 피해야 한다.

## 단위·파이프라인·SQL

- 최종 `npm test`: 30파일 **639/639 통과**. 기존 452개에 팀별 파생 검사 187개 추가(데이터 무결성 1, 마스킹 48, 동의 96, 답변 인용 15, 카드 24, 회의 3). 테스트 개수를 639개 고유 업무로 해석하지 않는다.
- 카드: 12개 미결 안건 × 공개/리드 전용. 원문 인용 보존, 부서 ID 유지, 공개 담당자/비공개 lead 배정, 두 번 실행해도 카드 및 발송 enqueue 1건. DB/모델은 모의 처리이며 실제 발송 없음.
- 회의: 팀별 미결/액션 원문 인용, 타부서 ID 거부, 중복 요약 병합. 실제 회의 봇 접속·전사 정확도 평가는 아님.

- 프로덕션 build, lint, 최종 테스트 타입 검사(tsc --noEmit), diff check 실행 성공. 앱 코드는 이번 평가에서 변경하지 않았다.

## 브라우저 결과와 기존 테스트의 사각지대

- 기존 게스트 Playwright **4/4 통과**: 1440/390px, 현재 노출된 부서 카드·원장·답변, 잘못된 서명/실부서 접근 차단, 열람 전후 6개 테이블 카운트 불변.
- 세 팀을 이름으로 지정한 추가 검사: 개발 통과, 기획·디자인은 데모 진입 링크 0개로 실패.
- 기획 직접 URL 완주 검사는 통과(5.0초). 최종 팀별 브라우저 suite는 직접 URL/개발 2 pass, 기획 진입/디자인 진입 2 fail. 최초 직접 URL 검사는 팀명이 h1에 있다는 테스트 작성자의 잘못된 가정으로 실패했고, 실제 팀명이 있는 header를 검사하도록 수정한 뒤 재실행했다. 제품 오류와 테스트 작성 오류를 구분한다.
- 공개 demo_departments RPC 직접 조회에는 영업·개발·기획 3개가 존재한다. 그러나 빌드된 `.next/server/app/demo.html` 및 브라우저 첫 화면에는 영업·개발만 있다. `/demo`가 build 출력에서 정적 페이지(○)로 나타난다. 기획 데이터 자체 부재가 아니라 정적 출력/데이터 갱신의 불일치가 관찰됐다. 정확한 최초 누락 시점은 미확인.
- 디자인은 공개 RPC에도 없고 시드 정의에도 없다. 디자인팀 전체 UI 완주와 실제 Slack/회의 연계 테스트는 할 수 없으므로 합격 처리하지 않는다.
- 기존 게스트 테스트는 현재 노출된 링크만 순회하고 최소 2팀만 요구해 두 누락을 검출하지 못했다. 새 팀별 acceptance 테스트를 스킵하거나 기대값을 낮추지 않고 유지한다.
- 개발 Q&A 스크린샷을 직접 확인했다. 준비된 답변과 인용이 렌더되지만 일부 무관한 질문에 관련 없는 인용이 붙은 거절 문구가 있다. 인용 존재 여부가 의미적 뒷받침 전체를 검증하는 것은 아니다.

## 다음 수정/검증 순서

1. 거절 가능한 출력 스키마와 인용 필수 성공 답변을 구분하고, 무관한 근거에서 정상 종료하는 회귀를 보강한다.
2. 확정·완료와 미결 상태를 구분하고 업무 외 선택 질문 오탐을 낮춘다. 이번 문장을 외워 통과시키지 말고 별도 보류 데이터로 검증한다.
3. 데모 부서 목록 갱신 정책을 검증하고 디자인팀 시나리오/시드를 추가한 후 세 팀 acceptance를 완주한다.
4. 승인된 격리 환경에서 세 팀별 실제 검색 → 카드 → 결정 → Q&A를 검증한다. 현재 실행은 실모델 부분과 격리 SQL 부분이 분리되어 있다.
5. 실제 회의 봇/Slack 이벤트, 부하·lease 복구, 장시간 배포 유지 검증은 별도다. 이전 Vercel 작성자 권한 문제를 이번 테스트 성공으로 해결했다고 표시하지 않는다.

## 도구 제약/안전

QA 스킬을 따라 계획·실패·실행 경계를 분리했다. 사전 스캐너는 WSL에서 플러그인의 CRLF 파일로 실행 실패해 PASS로 집계하지 않았다. Chrome MCP 전용 L3~5 워크플로는 미사용이며 실제 Playwright 브라우저 실행을 별도 증거로 사용했다. 실팀 발송, 업무 DB 변경, 배포, 시드 재생성은 하지 않았다. 새 데이터는 합성이고 저장/콘솔 출력에 실사용자 질문을 포함하지 않았다.
