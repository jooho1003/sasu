# 부서별 회고 커넥터 설계 — 부서마다 다른 흔적을 같은 활동 항목으로 모은다

- 작성일: 2026-09-19 · 상태: **§0 제안값 10개 사용자 확정 · phase 30 구현 착수 / 운영 반영 미실행.** [개발 회고 자동화 설계](개발_회고_자동화_설계.md)(ADR-063, phase 27)를 전제로 하며 그 위에 얹는다. 9/20 제출 범위가 아니다.
- 범위 원천: [PRD §3-6 RET-11~16·§8](../PRD.md), 구조: [ARCHITECTURE §6-4 불변식 27~29](../ARCHITECTURE.md), 선택 이유: [ADR-064](../ADR.md)
- 조사 근거(1차 출처만, 2026-09-19): [디자인·기획 문서](retro-connectors-research-2026-09-19/design-planning.md) · [영업·CS](retro-connectors-research-2026-09-19/sales-cs.md) · [개발·마케팅·인사](retro-connectors-research-2026-09-19/dev-marketing-hr.md) · [법령·정책](retro-connectors-research-2026-09-19/legal-policy.md)
- 사용자 요구(9/19): 각 부서가 당일 회고를 쓸 수 있는 방향을 **모두** 조사해 설계한다. 디자인은 수정된 피그마·달린 댓글, 기획은 수정된 문서를 이전과 비교, 영업은 어떤 전화를 받고 걸었는지 같은 식으로.
- 현재 기능: 회고 기반(ADR-063)은 개발자 본인 활동(git·Claude/Codex·메모리·문서·Chrome)과 사수 내부 활동(결정·질문·카드·검토 자료)만 다룬다. 부서별 외부 서비스 연결·부서별 회고 형식·수동/음성 한 줄 기록은 모두 신규 설계다. 이 문서는 상위 문서를 바꾸지 않는다.

## 0. 사용자 결정이 필요한 항목

| # | 항목 | 제안 | 대안 | 왜 사용자 판단인가 |
|---|---|---|---|---|
| 1 | 첫 파일럿 부서 | **개발 + 기획** — 새 외부 연결 0개로 시작할 수 있다(git 수집기 + 사수 내부 슬랙·노션·회의 파생). 그다음 디자인(Figma), 영업(CRM/VoIP 보유 여부에 따라) | 영업부터 | 영업은 전화 기록을 API로 얻을 수 있는지가 회사의 전화 시스템(VoIP/CRM 사용 여부)에 달려 있어 확인이 먼저다 |
| 2 | 외부 서비스 연결 주체 | **개인 OAuth**(각자 자기 계정을 연결, 토큰은 본인 행에만). 조직 단위 설치는 이미 있는 Slack·Notion만 재사용 | 조직 관리자가 한 번 설치 | 회고는 "내가 한 일"이다. 조직 토큰으로는 "누가"를 서버가 골라내야 하고 남의 활동을 읽는 권한을 갖게 된다 — 감시 논란의 출발점 |
| 3 | 전화 기록 | 개인 휴대폰 통화 기록은 **만들지 않는다**(Android는 Google Play 정책상 기본 전화 앱·승인된 예외 앱만 `READ_CALL_LOG` 사용 가능, iOS는 API 없음). 회사가 VoIP(RingCentral·Aircall 등)를 쓰면 커넥터로 방향·시각·길이만 가져오되, **통화 메타데이터는 통신비밀보호법 §2 11호 "통신사실확인자료" 정의에 문언상 들어가므로 VoIP 커넥터는 법률 자문 게이트 뒤에 둔다**(§8.1). 자문 전에는 CRM에 사람이 기록한 통화(`crm_call`)와 **음성 한 줄 기록**("오늘 A사 2통, 견적 1건")만 | 통화 기록 읽기용 안드로이드 앱 배포 / 자문 없이 VoIP 연결 | 정책 승인 대상 앱은 별개 제품이고, 통신사실확인자료의 "제공" 해당 여부는 조문만으로 확정되지 않는다 |
| 4 | 고객 개인정보 | 회고 활동에 **고객의 이름·전화번호·이메일을 저장하지 않는다.** 상대는 회사명 또는 CRM 레코드 ID의 해시 라벨(`상대 3`)로만. 통화는 방향·시각·길이만 | 뒷자리 마스킹 후 저장 | 회고는 본인 기록이지만 `dept`로 공개될 수 있고 마케팅으로 내보내질 수 있다. 식별정보가 회고에 남지 않으면 개인정보보호법 §15 "수집 목적 범위" 쟁점 자체가 축소된다(법령 조사 §2). 마스킹은 §2 1호의2 가명처리에 닿지만 §28조의2의 허용 목적(통계·연구·공익 기록)에 회고가 드는지는 별도 판단이라 근거로 삼지 않는다 |
| 5 | 메일·Drive | Gmail·Outlook 직접 연결은 **1단계에서 뺀다.** Gmail `gmail.metadata`·`gmail.readonly`는 restricted scope라 서버 저장 시 연 1회 CASA 보안평가 + OAuth 앱 검증이 필요하다. **Drive의 `drive.metadata.readonly`도 restricted**이므로 Google 문서 편집 이력은 `drive.activity.readonly`의 등급을 확인한 뒤(restricted면 제외) 붙인다. 메일 활동은 CRM(HubSpot `emails`)을 통해서만 | 처음부터 Gmail·Drive | 심사 통과 전까지 테스트 사용자 100명 제한. 정책 원문상 서버에 저장·전송하지 않는 구조만 평가 요건을 피한다 |
| 9 | 부서 공개 동의 분리 | 외부 연결 시 받는 **수집 동의**와, 회고를 처음 `dept`/`leads_only`로 여는 순간 받는 **공개 동의**를 분리해 각각 기록한다(`retro_user_settings.share_consented_at`) | 연결 동의 하나로 | 표준 개인정보 보호지침 §6⑥의 무동의 예외는 임금·교육·증명서·복지에 한정되고, 인사·노무 가이드라인은 근로자 개인정보 **공개**에 별도 동의를 요구한다(법령 조사 §3) |
| 10 | 연결 해제 시 데이터 | 해제하면 토큰과 **그 제공자에서 온 활동을 즉시 삭제**한다. 확정 회고의 해당 인용은 사라지고 그 항목은 렌더되지 않는다(인용 없으면 렌더 없음). 이미 내려받은 Markdown은 사용자 것 | 활동은 남김 | Notion·Atlassian 개발자 약관이 연동 해제·삭제 요청 시 삭제 의무를 명문화한다(법령 조사 §5) |
| 6 | 마케팅 집계 지표 | GA4·광고 성과처럼 "작성자가 없는 집계"는 활동이 아니라 **지표 스냅샷**으로 넣되, 회고 문장은 "확인했다/비교했다"까지만 쓰게 한다 | 집계를 활동으로 취급 | 집계 수치는 개인의 행동이 아니다. 개인 회고에 지표 등락을 성과처럼 쓰면 평가 도구가 된다 |
| 7 | 웹훅 | 1단계는 **pull만**(하루 1~2회). 웹훅은 쓰지 않는다 | Figma·Notion 웹훅 | 당일 회고에 실시간성이 필요 없고, Figma 웹훅은 요금제 조건이 문서에 없으며 Miro 웹훅은 실험 기능이 제거됐다 |
| 8 | 부서별 회고 형식 | 4개 섹션 키(`did`·`learned`·`decided`·`next`)는 유지하고 **라벨과 힌트만 부서 프리셋**으로 바꾼다 | 부서별 스키마 | strict json_schema·인용 검증·화면을 하나로 유지한다 |

## 1. 부서별 흔적 지도 — 어디에 남고, 무엇을 가져올 수 있나

조사 결과(2026-09-19, 공식 문서 기준)를 회고 관점으로 정리한다. **가능**은 시간 필터와 작성자 필드가 확인된 것, **조건부**는 요금제·권한·심사가 걸리는 것, **불가**는 API가 없거나 정책이 막는 것이다.

### 1.1 디자인

| 흔적 | 소스 | 가져올 것 | 판정 | 근거 |
|---|---|---|---|---|
| 수정한 파일·저장한 버전 | Figma `GET /v1/files/:key/versions` (`file_versions:read`) | 버전 라벨·설명·작성자·시각 | 가능 — 이름 붙여 저장한 버전만 잡힌다 | [design-planning §1](retro-connectors-research-2026-09-19/design-planning.md) |
| 달린 댓글·해결한 댓글 | Figma `GET /v1/files/:key/comments` (`file_comments:read`) | `message`·`user`·`created_at`·`resolved_at` | 가능 | 같은 문서 |
| 파일이 바뀌었다는 사실 | Figma Webhooks V2 `FILE_UPDATE`·`FILE_VERSION_UPDATE`·`FILE_COMMENT` | 이벤트 | 조건부 — 요금제 조건이 문서에 없음, 1단계 미사용(§0-7) | 같은 문서 |

| 채용 진행 | Greenhouse `applications?last_activity_after=`(**`updated_after` 없음**)·`candidates/{id}/activity_feed` · Lever `opportunities?updated_at_start=` · Workable `candidates?updated_after=` (`r_candidates`) | 가능 — 지원자 이름은 저장하지 않고 공고명·단계만 | dev-marketing-hr §9 |
| 면접 | Google Calendar(제목 패턴 "면접") | 가능 — 참석자 저장 안 함 | 같은 문서 §10 |
| 직원 활동 감사 로그 | Google Admin SDK Reports API | **쓰지 않는다** — 관리자 감사 로그는 개인 회고 재료가 아니다 | 같은 문서 §10 |
| 원티드·플렉스 | 원티드 OpenAPI는 채용공고 위주로 보이고 지원자 API 미확인, 플렉스 공개 API 문서 없음 | 재조사 | 같은 문서 §11 |

### 1.8 모든 부서 공통 — 새 연결 없이 사수 안에서 나오는 것

| 흔적 | 근거 | 활동 종류 |
|---|---|---|
| 내가 오늘 슬랙에 쓴 메시지 | `items.author_ext_id = members.slack_user_id`, `spoken_at::date` — 이미 동의·마스킹·저장됨 | `slack_message` |
| 내가 참여한 회의(전사 확정) | `reviewed_materials.participants @> {me}` + `confirmed_at::date` | `meeting_attended` |
| 오늘 바뀐 부서 노션 문서 | `sources.kind='notion_page'`·`last_synced_at::date` + 청크 변화 | `notion_page_changed` (부서 문맥) |
| 내가 답을 받은 질문·내린 결정·닫은 카드·확정한 자료 | ADR-063 Tier 0 | 기존 `sasu_*` |

## 2. 핵심 결정 — 커넥터는 네 형태뿐, 산출물은 `RetroActivity` 하나

| 형태 | 무엇 | 주체·인증 | 예 |
|---|---|---|---|
| **A 서버 pull** | 하루 1~2회 잡이 개인 토큰으로 외부 API를 읽어 활동으로 변환 | 개인 OAuth(`retro_connections`), 스코프 최소·읽기 전용 | Figma·GitHub·Jira·Confluence·Google(Drive Activity·Calendar)·HubSpot·Pipedrive·RingCentral·채널톡·Intercom·ATS·Meta·GA4 |
| **B 사수 내부 파생** | 이미 저장된 부서 자료에서 본인 행위만 SQL로 추출 | 없음(RLS·`auth.uid()`) | §1.8 전부 |
| **C 로컬 수집기** | 사용자 PC의 파일 | 없음(ADR-063) | git·Claude/Codex·메모리·문서·Chrome |
| **D 수동·음성 한 줄** | API가 없는 흔적을 사용자가 직접 남김 | 세션 | "A사 통화 2건, 견적 1건 발송", 오프라인 미팅, 카카오 상담 |

- 네 형태 모두 `retro_activities`로 들어가고, 그 뒤(초안·검토·확정·열람·내보내기)는 ADR-063 파이프라인 그대로다. **부서별로 다른 것은 "어떤 커넥터를 켜는가"와 "프리셋 라벨"뿐이다.**
- A는 **본인 토큰으로 본인 계정의 것만** 읽는다. 조직 토큰으로 팀 전체를 읽고 서버가 "내 것"을 고르는 방식은 만들지 않는다(§0-2). 관리자 감사 API(Figma Activity Logs·Google Admin Reports·Zendesk 관리자 export)는 어떤 부서에도 쓰지 않는다.
- D는 사수의 기존 음성 입력(`llm.transcribeAudio`, 원본 비저장)을 재사용한다. 전사 텍스트를 마스킹해 `voice_note` 활동 1건으로 저장하며 원본 음성은 남기지 않는다.
- 웹훅·실시간 동기화는 만들지 않는다(§0-7). Notion은 사수가 이미 5분 폴링을 한다.

## 5. 데이터·잡·라우트

### 5.1 `retro_connections` — 개인 연결 (마이그레이션 `0049_retro_connections.sql`)

```sql
create table public.retro_connections (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users on delete cascade,
  dept_id uuid not null references public.departments,
  provider text not null check (provider in ('figma','notion','google','github','atlassian','hubspot','pipedrive','ringcentral','channel','intercom','greenhouse','lever','workable','meta','youtube')),
  auth_kind text not null check (auth_kind in ('oauth','token')),
  encrypted_secret text not null,               -- refresh/access 토큰 또는 API 키 암호문 (lib/notion-installation.ts 방식)
  scopes text[] not null default '{}',
  account_label text,                            -- "@handle"·워크스페이스명. 이메일·이름은 넣지 않는다
  config jsonb not null default '{}',            -- 대상 파일 키·저장소 목록·프로젝트 키 등 사용자가 고른 범위
  status text not null default 'active' check (status in ('active','error','revoked')),
  last_pulled_at timestamptz, last_error text,   -- 에러 코드만
  consented_at timestamptz not null default now(),
  revoked_at timestamptz,
  created_at timestamptz not null default now(),
  unique (user_id, dept_id, provider)
);
-- RLS: select/delete는 user_id = auth.uid()만. insert/update는 RPC(OAuth callback은 수집 어댑터로 분류: service role이 검증된 토큰을 본인 행에 저장, ADR-052 패턴).
-- encrypted_secret은 어떤 select 정책·RPC 반환에도 포함되지 않는다(컬럼 권한 revoke).
```

- OAuth 시작·콜백 라우트 `app/api/retro/connect/[provider]/{start,callback}` — Slack OAuth(`app/api/slack/oauth/*`)의 origin 검증·HttpOnly cookie·단회 state를 그대로 쓰되 **주체가 조직 관리자가 아니라 세션 사용자 본인**이다. state에는 `user_id`·`dept_id`·`provider` 해시를 묶는다.
- API 키 방식(`token`)은 사용자가 설정 화면에 붙여넣고 서버가 즉시 검증 호출 후 암호화 저장, 응답에 평문을 되돌리지 않는다. Greenhouse·Workable·채널톡·Pipedrive처럼 OAuth가 없거나 파트너 전용인 서비스용.
- 범위 `config`는 사용자가 고른다: Figma는 파일 키 목록(팀 전체 열거 금지), GitHub는 저장소 목록, Google Drive는 폴더 `ancestorName`, Jira는 프로젝트 키. **열거 범위를 넓히는 것은 사용자 조작뿐**이다.
- 해제(`revoked_at`)는 즉시 토큰을 삭제(`encrypted_secret := ''`, status revoked)하고 **그 제공자 접두사의 활동을 같은 트랜잭션에서 삭제**한다(§0-10). 확정 revision의 인용은 활동이 없어져 렌더에서 빠진다.
- `retro_user_settings(user_id, dept_id, share_consented_at, share_consent_version, created_at)` — 공개 동의 기록(§0-9). `set_retro_visibility`가 `dept`/`leads_only`로 바꿀 때 이 행이 없으면 `share_consent_required`를 반환하고, 화면이 동의 문구("이 회고를 부서원이 볼 수 있게 됩니다 · 외부 서비스에서 가져온 활동 제목이 포함됩니다")를 띄운 뒤 `consent_retro_share(p_dept, p_version)`로 기록한다. 철회는 설정에서, 철회 시 기존 `dept` 회고는 `self`로 되돌린다.

### 5.2 잡 `retro_pull`

- payload `{connectionId, date}`. 결정적 id `md5('retro-pull:'||connection||':'||date)`. 하루 23:00(KST) `schedule_retro_pulls()`가 활성 연결마다 큐잉(대량 레인 `bulk`), 사용자가 "지금 가져오기"를 누르면 실시간 레인으로 1건. 분당 사용자당 1회.
- 핸들러 `lib/pipeline/retro-pull.ts`: 토큰 복호화 → `lib/retro/connectors/<provider>.ts`의 `pull({config, date, tz, fetch}) → RetroActivity[]`(순수 변환은 `lib/retro/connectors/<provider>/map.ts`에 TDD, HTTP는 어댑터) → `mask()` → 서비스 RPC `upsert_retro_activities_as(p_user, p_dept, p_date, p_activities)`(`auth.role()='service_role'` 가드, `retro_days` 없으면 `collecting`으로 생성) → 그 날의 `retro_draft` 재큐잉은 하지 않고 **사용자가 초안 생성을 누를 때** 합쳐진다(Tier 0·번들과 같은 규칙).
- 커넥터 공통 규칙: 읽기 전용 스코프만 · 페이지네이션 상한(활동 200건/커넥터/일) · 429는 `Retry-After` 준수 후 1회 재시도 · 응답 본문은 로그 금지 · 상대 개인정보 필드(전화번호·이메일·지원자명·참석자 이메일)는 **파싱 자체를 하지 않는다**(테스트로 증명) · `counterparty` 라벨은 회사명 또는 `상대 N`(레코드 ID sha256 앞 6자를 하루 안에서 순번으로 치환).
- 실패는 `retro_connections.status='error'`, `last_error=<코드>`. 3회 연속 실패면 설정 화면에 "다시 연결" 배지.

### 5.3 B 확장 — `create_retro_day`에 추가되는 본인 파생

| 활동 | SQL 조건(본인·부서·날짜) | `source_visibility` |
|---|---|---|
| `slack_message` | `items i join sources s` where `s.kind='slack_channel' and i.author_ext_id = (select slack_user_id from members where user_id=auth.uid() and dept_id=p_dept) and i.spoken_at::date = p_date and i.deleted_at is null` | `s.visibility` |
| `meeting_attended` | `reviewed_materials where auth.uid() = any(participants) and confirmed_at::date = p_date and status='ready'` | `visibility` |
| `notion_page_changed` | `sources where kind='notion_page' and dept_id=p_dept and last_synced_at::date = p_date` + 청크 증감(`items created_at::date = p_date` 수 / 같은 날 `deleted_at` 수) `(확인 필요: finish_notion_sync가 이전 청크를 soft delete로 남기는지 — 아니면 "갱신됨"만)` | `visibility`, `meta.dept_context=true` |

### 5.4 D — 수동·음성 한 줄

- `POST /api/d/[dept]/retros/[id]/notes` body `{text}`(≤500) 또는 `multipart audio`(≤10MB, `validateVoiceUpload`) → 음성이면 `llm.transcribeAudio` → `mask()` → RPC `add_retro_note(p_day, p_kind, p_text)` → `manual_note`/`voice_note` 활동. 하루 20건 상한. 원본 음성은 저장하지 않는다(ADR-032 짧은 음성 규칙).
- 슬랙에서도 가능: DM으로 `/회고 A사 통화 2건` → 같은 RPC(`search_as` 패턴의 `*_as` 서비스 RPC, 슬랙 사용자 매핑은 `members.slack_user_id`). 2단계.

## 6. 화면

- 설정 `/d/[dept]/settings` "회고" 절: **부서 프리셋**(lead만) · **내 연결** 카드(제공자 아이콘·계정 라벨·범위 요약·마지막 수집·상태·[지금 가져오기]·[해제]) · [연결 추가] → 제공자 목록에서 프리셋 추천이 위로. 연결 화면은 어떤 데이터를 읽고 무엇을 저장하지 않는지(개인정보 필드 미수집)를 한 줄로 고지한다.
- 회고 만들기 패널(ADR-063 §6)에 "연결된 소스에서 오늘 가져오기"와 "한 줄 추가(텍스트·마이크)"가 붙는다.
- 상세 활동 패널은 접두사 그룹으로 늘어나고, `dept_context` 활동은 "오늘 부서에서 바뀐 것" 별도 그룹(회색)으로 표시하며 인용 칩이 달리지 않는다.
- 타임라인은 바뀌지 않는다. 필터 "주제"에 프리셋 라벨이 추가된다.

## 7. 부서별 초안 프롬프트 규칙

- `system`에 프리셋 라벨·힌트(§4)와 공통 규칙(ADR-063 §5)을 넣는다. 추가 공통 규칙: ① 상대는 회사명·`상대 N`으로만 부른다 ② `metric_snapshot`은 "확인했다·비교했다" 서술만 ③ `dept_context` 활동은 인용하지 않는다 ④ 통화·상담은 건수·방향·결과까지, 내용 추측 금지 ⑤ 지원자·고객 개인은 등장하지 않는다.
- 검증 `verifyRetroDraft`에 두 규칙을 추가한다: `dept_context` 활동을 인용한 항목은 버린다 · `text`에 마스킹 토큰(`[전화번호]` 등)이 포함된 항목은 버린다(마스킹된 값을 문장에 옮겨 적는 것을 막는다).

### 8.2 사수 불변식과의 대조
