# 백엔드·플랫폼 개발: 설계의 조건과 운영의 현재 상태

입력은 API 계약·ADR·동의된 장애 회고·변경 결정이다. 로그/소스/비밀키를 무작정 올리지 않는다. 사수는 장애 모니터링·배포 시스템이 아니며 최신 시스템 상태를 자동으로 관측하지 않는다.

| 페르소나·상황 | 실제 이용 방식 | 장점 가설 | 단점·실패 조건 | S/M 차이·검증 질문 |
|---|---|---|---|---|
| **BE-L1 주니어**. 권한 검사·재시도 규칙을 배우는 단계 | ‘왜 서버에서 이 값을 정하나’ ASK → ADR 인용 → 실제 코드/테스트와 확인 | 이유까지 배우며 위험한 복사 구현을 줄일 가능성 | 과거 설계와 현재 코드가 다르면 답변이 맞아 보여도 부정확. 비밀값 마스킹이 완전하다고 오해(G06·G09) | S는 문서 작성자에게 직접 확인. M은 소유 팀 탐색이 길어짐. **인용이 코드를 보증하지 않는다는 점을 이해하는가?** |
| **BE-L2 API 담당자**. 멱등/스키마 변경 제안 | 논의에서 카드 생성 → 영향 근거 확인 → 승인 후 변경 결과를 별도 기록 | 설계 선택과 재시도 처리 이유가 남음 | `decided`가 마이그레이션 적용으로 오해됨. 데이터/서비스 범위 묶음 약함(G15·G16·G19) | S는 제안·구현·운영 한 사람. M은 DBA·보안·서비스 팀 합의 필요. **누가 실행하며 실제 반영됐는지 찾을 수 있는가?** |
| **BE-L3 선임·아키텍트**. 여러 제안의 위험 검토 | 검토 기준 문서와 원장을 읽고 근거 있는 의견 작성; 역할 평가를 쓰면 근거 없는 항목 확인 | 기술적 반대의 맥락이 단순 반대로 잊히지 않음 | 자동 점수에 정성적 트레이드오프 축약, 자료 기여 권한 묶임(G04·G10·G17) | S는 최종결정도 겸함. M은 자문자와 서비스 오너 다름. **반대 의견과 최종 결정이 함께 보존되는가?** |
| **BE-L4 개발 팀장**. 장애 대응 중 임시 정책 승인 | 과거 유사 결정 확인 후 사람 판단 → 사유/유효 조건 기록 → 후속 점검은 별도 관리 | 급한 판단의 이유를 사후 인계 가능 | 읽는 근거의 오래됨, 담당자 휴가, 알림 지연. 긴급 runbook을 대체할 수 없음(G06·G23·G24) | S는 온콜·팀장 겸임. M은 사고 책임자와 서비스별 오너 구분. **AI 지연 때 기존 대응으로 바로 돌아가는가?** |
| **BE-L5 CTO·기술 본부장**. 공통 기술 투자·위험 수용 | 각 부서가 공유 가능한 범위의 결정 요약과 근거를 제공하도록 요청 | 비슷한 예외가 반복되는 구조적 원인 탐색 | 모든 lead 권한을 받아 전사 원문을 읽는 편법, 개인 리드타임 평가 위험(G07·G20) | S는 상세 맥락 필요. M은 민감 장애 원문 없이 선택·책임·영향만 필요. **요약의 누락/출처/유효 시점을 알 수 있는가?** |

[J05 장애 대응](../journeys.md)에서 ‘과거에는 이렇게 했다’와 ‘지금도 해야 한다’를 구별한다. 설계 기록 활용은 가능하나 실제 배포·취약점 조치의 정당성은 별도 검증 대상이다.
