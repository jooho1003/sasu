# 기획·프로덕트: ‘왜 이 범위를 선택했는가’

입력 후보는 확정된 제품 원칙·요구사항·릴리스 회의의 동의된 기록이다. 산출물은 출시 범위 결정, 보류 이유, 확인할 질문이다. 고객 인터뷰는 외부 참여자 절차와 자료 목적을 충족한 요약만 취급한다. Jira·Linear 이슈 생성/수정이나 출시 실행은 현재 기능으로 가정하지 않는다.

| 페르소나·상황 | 실제 이용 방식 | 장점 가설 | 단점·실패 조건 | S/M 차이·검증 질문 |
|---|---|---|---|---|
| **PM-L1 신입 기획자**. 입사 첫 주, 이전에 빠진 기능의 이유를 매일 질문 | 웹 ASK → 인용과 원장 확인 → 부족하면 기존 담당자에게 별도 질문. 바로 적용하기 전 대상 기능·날짜 확인 | 사소한 질문을 눈치 보며 반복하지 않고 의사결정 배경을 학습 | 오래된 예외를 현재 규칙으로 받아들임. 거절에서 인계가 끊김(G02·G06·G21) | S는 대표 구두 맥락이 적재되지 않음. M은 약어·부서 정책 차이가 큼. **다음 행동과 확인할 사람을 자기 말로 설명하는가?** |
| **PM-L2 기능 담당 PM**. 요구 변경을 주간 단위 조율 | Slack 논의가 카드가 되면 관련 근거 확인, 결정자에게 알림. 자기 범위 결정은 근거와 함께 직접 기록 | 범위를 바꾼 이유와 상대 의견이 사라지지 않음 | 프로젝트/기능 단위 묶음 부족, 직접 기록이 정식 승인처럼 보일 수 있음(G15·G19) | S는 한 문서에서 실행까지 담당. M은 FE/BE/영업의 수락이 따로 필요. **기록만 남겼는데 출시 승인으로 읽히지 않는가?** |
| **PM-L3 선임·파트 리드**. 여러 PM 제안을 검토 | lead라면 역할 기준으로 문서 비교, 원장과 상충 근거 확인. member면 읽기·질문과 카드 담당 처리 중심 | 반복 검토 기준을 표준화하고 누락 근거를 드러냄 | 기준 작성/실행에 lead가 필요, 문서 점수가 사용자 가치 검증을 대체할 위험(G04·G10) | S는 본인이 기획 초안도 작성. M은 품질 검토자와 예산 결정자가 다름. **낮은 점수의 이유를 근거로 반박·보완할 수 있는가?** |
| **PM-L4 제품 팀장**. 경쟁하는 출시 안건을 매일 선택 | 알림 받은 카드에서 원칙·과거 결정 확인 → 결과/사유 기록 → 원장에서 정정·알림 설정 | ‘결정 대기’를 놓치지 않고 이유를 팀에 남김 | 웹 결과 편집 결함, 첫 lead 배정, 자기 미결 큐 부재로 모든 안건이 몰림(G01·G03·G05) | S는 속도·설정 최소화가 중요. M은 영역별 책임과 대행이 필요. **바쁜 날에도 본인이 결정할 안건만 찾는가?** |
| **PM-L5 CPO·대표**. 분기 방향·부서 간 상충 조정 | 소속 부서 원장 또는 각 부서가 별도 공유한 자료를 읽고 필요한 결정을 자기 범위에서 기록 | 결론만 보고받는 대신 선택 이유와 뒤집힌 가정을 확인 | org admin으로 전사 기록을 볼 수 없음. 제품·영업·개발 합의 화면 없음(G07·G14) | S는 L2~L4 겸임. M은 요약의 출처·공유 범위·부서 수락이 중요. **원문 전체 없이도 어떤 선택을 요청받았는지 알 수 있는가?** |

대표 여정은 [J01 출시 범위](../journeys.md)다. 먼저 ‘이번 주 출시/보류’ 한 종류를 파일럿으로 삼고, 결정 재질문 수와 기록·수정 시간을 함께 측정한다. 기능 개수가 많아진 것을 생산성 향상으로 세지 않는다.
