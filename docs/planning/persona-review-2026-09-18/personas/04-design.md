# 디자인·UX: 피드백을 결정 이유로 남기기

입력은 텍스트 디자인 원칙·상태 설명·동의된 리뷰 기록이다. 원본 시각 자산·프로토타입의 상호작용은 텍스트 추출만으로 평가할 수 없다. 디자인 취향과 사용자 검증 결과를 같은 근거 수준으로 다루지 않는다.

| 페르소나·상황 | 실제 이용 방식 | 장점 가설 | 단점·실패 조건 | S/M 차이·검증 질문 |
|---|---|---|---|---|
| **DS-L1 주니어 디자이너**. 브랜드·컴포넌트 규칙 학습 | ASK로 근거 확인 → 원본 가이드 열기 → 실제 화면에서 적용 | ‘그때 왜 이 문구로 했나’를 선임 부재 시 탐색 | 화면 예시·이미지·톤의 뉘앙스가 추출문에 없으면 답변 제한(G09·G21) | S는 가이드가 짧고 대표 취향 의존. M은 브랜드/제품 가이드가 분리. **규칙과 사례의 예외를 구별하는가?** |
| **DS-L2 서비스 디자이너**. 리뷰 후 수정 범위 정리 | 리뷰 전사를 lead가 검토 확정 → 카드/원장에서 선택과 보류 이유 확인 | 상충 피드백을 한 선택과 근거로 정리 | 자신의 추출문 수정/확정을 직접 못함, 디자인 파일 버전과 연결 수동(G04·G15·G22) | S는 자신이 리서치도 수행. M은 UX writer·리서처·FE와 인계. **어떤 버전의 어떤 화면에 적용하는지 찾는가?** |
| **DS-L3 선임·디자인 시스템 담당**. 반복 리뷰 | 문서 기준별 누락 점검과 원장 비교, 실제 사용성 평가는 별도 수행 | ‘왜 안 되는지’가 개인 취향 대신 공개 기준을 따름 | 점수로 심미성·사용성 평가를 대신할 위험, 반박 경로 부족(G10·G17) | S는 협업 합의 우선. M은 시스템 일관성과 서비스별 예외 균형. **좋은 예외를 낮은 점수로 배제하지 않는가?** |
| **DS-L4 디자인 팀장**. 출시 전 위험/범위 결정 | 미결 접근성·문구·실패 상태 카드 확인, 결과와 사유 기록 | 다음 리뷰에서 같은 결정이 뒤집히는 이유를 추적 | 웹 결과 수정 불가, 디자인 승인과 구현 검증이 섞임(G01·G16·G25) | S는 실제 UI 확인도 직접. M은 디자인 승인 후 FE·QA 완료 별개. **승인한 범위만 명시적으로 기록되는가?** |
| **DS-L5 디자인 총괄·브랜드 책임자**. 여러 제품의 일관성 | 부서가 공개 승인한 결정 묶음으로 예외와 투자 필요 확인 | 브랜드 원칙과 현장 제약의 반복 패턴 탐색 | 타 부서 자료 접근 안 됨, 원문 링크가 권한 없는 Figma/Notion으로 이어질 수 있음(G07·G12) | S는 대표 역할과 결합. M은 본사 원칙을 모든 부서 비공개 근거와 섞지 않아야 함. **공용 규칙과 민감 피드백이 분리되는가?** |

[J04 자료 검토](../journeys.md)에서 이미지 중심 PDF의 추출 한계를 ‘근거 없음’으로 드러내는지 확인한다. 텍스트가 적다고 디자인 품질이 낮다는 결론을 내리지 않는다.
