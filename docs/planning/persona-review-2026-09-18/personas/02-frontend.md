# 프론트엔드: 요구·화면 상태·구현 이유의 연결

입력은 텍스트로 명시한 UI 상태·접근성 기준·기술 선택 근거다. Figma 화면이나 PR 링크가 있다는 이유만으로 화면 인식·코드 실행·테스트 통과를 가정하지 않는다. [채용 데모](../../../../fixtures/hiring/missions.ts)의 합성 미션도 실제 개발자의 성과 측정이 아니다.

| 페르소나·상황 | 실제 이용 방식 | 장점 가설 | 단점·실패 조건 | S/M 차이·검증 질문 |
|---|---|---|---|---|
| **FE-L1 주니어 개발자**. 폼 오류·로딩 상태 구현 전에 기준을 매일 확인 | ASK로 상태 정의 질문 → 원문 인용 확인 → 저장된 결정과 실제 티켓을 대조 | 선임에게 같은 배경을 다시 묻는 비용 감소 | 추출문에 없는 화면 상태·코드 버전은 답할 수 없음. 그럴듯한 코드 조언을 실행 검증으로 오해(G09·G21) | S는 문서 미비·구두 요구. M은 디자인시스템과 서비스별 예외 충돌. **없는 상태를 추측하지 않고 확인 요청하는가?** |
| **FE-L2 화면 담당 개발자**. 요구 변경으로 일정 영향 | Slack에서 ‘A 상태를 제외해도 되는가’ 논의 → 카드 → 결정 후 자기 구현 사유 직접 기록 | 범위 축소와 기술적 타협의 이유를 추적 | 카드 결정이 실제 배포 완료로 읽힘. PR/릴리스와 원장이 수동 연결(G15·G16) | S는 구현·QA 겸임. M은 리뷰·QA·릴리스 팀이 분리. **결정과 배포 시점을 구별하는가?** |
| **FE-L3 선임·UI 플랫폼 담당**. 공통 컴포넌트 기준 검토 | 기준 문서를 근거로 ASK·문서 역할 평가. 불일치는 구체 인용으로 검토 | 접근성·실패 상태 누락을 체크리스트로 반복 검토 | 문서 점수로 실제 키보드·스크린리더 품질 판단 불가. lead 승격은 과도(G04·G09·G10·G25) | S는 검토/최종 결정 겸임. M은 전문가 의견과 일정 결정자가 다름. **검토 의견이 최종 승인으로 표시되지 않는가?** |
| **FE-L4 프론트 팀장**. 호환성·속도·인력 선택 | 카드의 대안·과거 결정 확인 → 책임 범위 내 선택 → 담당자에게 후속 구현을 별도 전달 | 반복된 브라우저 지원 논쟁을 근거와 함께 정리 | 담당 추정 오류, 대행 부재, 과거 기간 한정 예외 재사용(G03·G06·G24) | S는 대표에게 예외를 올림. M은 웹/앱/디자인 부서 의존. **‘이 브라우저만 예외’ 범위가 유지되는가?** |
| **FE-L5 엔지니어링 임원**. 공통 플랫폼 투자·출시 위험 | 권한 있는 결정 묶음을 받아 기술 부채·공통 장애 원인을 확인 | 특정 개인 평가 대신 반복되는 의사결정 제약을 볼 가능성 | 현재 전사 포트폴리오/실시간 품질 지표 없음. 질문/결정 속도로 사람을 평가할 위험(G07·G20) | S는 직접 코딩하며 L2 겸함. M은 집계라도 작은 집단 식별 위험. **투자 판단에 필요한 정보와 개인 감시를 분리하는가?** |

파일럿은 실제 상태 전이 하나(입력→오류→재시도→완료)의 결정 이유를 찾는 과제로 한정한다. 사수 응답을 따랐다는 사실과 실제 UI 접근성 검증 결과를 별도 기록한다.
