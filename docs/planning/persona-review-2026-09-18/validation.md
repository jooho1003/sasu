## 다음 실제 사용자 검증: 두 규모를 같은 과제로 비교

다음은 수행 전 연구안이다. 초기에 S/M 각각 최소 한 조직에서 서로 다른 책임을 맡은 구성원을 모집한다. 한 조직 결과를 전체 규모의 결과로 일반화하지 않는다. 사용자 섭외·연락은 이 작업에서 실행하지 않았다.

| 모집군 | S에서 확인 | M에서 확인 | 우선 역할 |
|---|---|---|---|
| 질문/실행자 | 입사 초기·겸직·자료 없는 질문 | 전문 업무/용어·타부서 의존 | L1~2, PM/CS/FE/SA |
| 검토 전문가 | 실무와 검토 겸임 | 인사관리 없는 전문 검토자 | L3, DS/BE/FN |
| 결정 책임자 | 대표/팀장 한 명에게 모임 | 복수lead·범위별 책임·대행 | L4, PM/SA/OP |
| 조직 관리자 | 콘텐츠 책임과 설치 겸임 | IT와 부서 책임이 분리 | X01/X05 |
| 경계 사용자 | 미동의·휴가·다른 부서 겸직 | 부서 이동·교대·민감 업무 | X02~X04/X08 |

첫 모집에서 모든 50역할을 같은 비중으로 인터뷰하지 않는다. 서로 다른 행동/권한/위험을 보여주는 대표를 먼저 보고 실제 사용 패턴에 따라 페르소나를 합치거나 나눈다. 사람 수보다 역할·업무·실패 조건의 다양성을 기록한다.

### 인터뷰: 의견 대신 최근 사건

1. 가장 최근에 ‘누가 결정했는지/왜 그렇게 했는지’ 다시 찾은 일을 보여 달라고 요청한다. 실제 민감 원문을 받을 필요는 없다. 합성·삭제본으로도 과정은 설명할 수 있다.
2. 누가 요청·검토·결정·실행했고, 각 사람이 무엇을 볼 수 있었는지 그려본다. 직함으로 추정하지 않는다.
3. 결정 내용을 바꿨거나 조건부 승인한 사례, 동료와 해석이 달랐던 사례를 확인한다.
4. 근거가 없거나 자료 접근권한이 없을 때 실제로 어떻게 해결했는지 확인한다.
5. 사수에 입력/수집되면 곤란한 자료, 질문을 주저하게 만드는 상황, 동의 철회 때 기대하는 결과를 확인한다.
6. 현재 검색·재설명·회의·기록·정정에 드는 시간을 범위로 물어보고 관찰값과 구별한다.
7. 누가 설치/소스 갱신/멤버 이동/비용/장애를 맡는지, 그 사람이 운영을 지속할 여력이 있는지 확인한다.
8. 어느 상황에서는 사수를 쓰지 않는 것이 나은지 묻고, 그 반례를 설계에 남긴다.

### 공통 과제 세트

| 과제 | 합성 자료 구성 | 관찰할 행동 | 성공 조건 |
|---|---|---|---|
| U01 현재 정책 찾기 | 현재 정책·폐기 정책·과거 고객 예외를 함께 준비 | 시점/대상 구별·근거 확인 | 올바른 대상/시점 조건으로 답하고 필요한 불확실성 설명 |
| U02 추천 일부 변경 | 12% 추천, 사용자는5%만 결정 | 결과/사유 편집·확정 내용 확인 | 사용자가 의도한 조건이 실제 원장에 동일하게 남음 |
| U03 근거 없음 | 답할 수 있는 자료를 의도적으로 두지 않음 | 반복 질문/포기/사람 인계 | 모름을 이해하고 존재하지 않는 근거를 만들지 않음, 인계 가능 |
| U04 검토자 기여 | member 작성자·전문가·lead를 분리 | 업로드/반려/보완·확정 | 권한을 넓히지 않고 정확한 확정본만 근거로 사용 |
| U05 대행 경합 | lead휴가·대행 만료·동시 결정 | 다음 담당 확인·오래된 탭 제출 | 허용된 한 사람의 결정1건, 권한 상실 후 읽기/DM 차단 |
| U06 부서 전환 | 두 멤버십·다른 답변/비공개 정보 | 부서 선택·입력/결과 분리 | 이전 부서 내용이 새 부서에 섞이지 않음 |
| U07 결정 정정 | 이미 실행한 결정과 새 정정 | 과거/현재/후속 실행 구별 | append-only 이력과 재작업 필요를 이해 |
| U08 실패 복구 | job 지연·소스 변경·전달 실패 | 새 요청 남발 여부·상태 재조회 | 영구 로딩·중복 생성 없이 명확한 다음 행동 |

기존 도구만 사용하는 조건과 사수 조건을 같은 난도의 서로 다른 합성 업무로 비교한다. 순서를 교차해 같은 답을 외워 빨라지는 효과를 줄인다. 두 조직 규모의 업무 난도와 참여자 경험이 달라 단순 평균 속도만으로 우열을 내리지 않는다. 당사자의 질문/실수는 직원 성과 평가 자료로 전달하지 않는다.

## 측정 정의

| 지표 | 정의·수집 최소 단위 | 해석 주의 |
|---|---|---|
| 업무 성공 | 올바른 조건/대상/권한으로 과제 완주 여부 | 버튼 클릭·답변 생성만으로 성공 처리 금지 |
| 결정 충실도 | 기록된 결과가 사람의 최종 선택과 일치하는 사례 수 / 완료 사례 수 | 사유가 맞아도 outcome이 다르면 실패 |
| 근거 타당성 | 인용의 실재성 + 결론 함의 + 시점/대상 적합성의 각각 평가 | 문자열 검증률 하나로 합치지 않음 |
| 인계 성공 | 근거 부족에서 책임 있는 사람이 요청을 받아 해결 또는 적법하게 반환 | 거절률이 낮다고 성공 아님 |
| 처리 시간 | 작업 시작~정확한 완료의 경과시간과 실제 사람 투입시간 각각 | job 대기와 다른 일을 할 수 있는 시간을 구별 |
| 운영 부담 | 동의·소스·검토·오탐·정정·재시도에 든 시간/관찰기간 | lead/admin 숨은 비용을 제외하지 않음 |
| 알림 품질 | 받은 알림 중 확인/결정이 실제 필요했던 비율, 중복/잘못된 담당 수 | 열람/클릭률을 업무 가치로 대체하지 않음 |
| 권한 이해 | ‘누가 무엇을 볼 수 있나’ 설명이 실제 권한과 일치하는지 | lead/admin/직급 혼동 별도 기록 |
| 신뢰 보정 | 맞는 답 확인과 모르는 답 인계의 행동을 관찰 | 만족 점수만으로 과신/불신을 판단하지 않음 |
| 재사용 | 관찰 기간에 같은 종류 업무를 다시 자발적으로 수행 | 매일 사용을 모든 직무의 성공 기준으로 강요하지 않음 |

순시간 편익 = 기존 검색/재설명/확인 시간 감소 − 새 설정/검토/수정/운영 시간. 현재 숫자는 없다. 시간×가정 임금으로 만든 비용은 `[추정]`이라고 구분해야 하며 실제 지불 의사를 대신하지 못한다.

## 구현 검증의 권한 조합

각 D 설계를 구현할 때 아래 조합을 합성 DB에서 실행한다. UI 숨김 검사만으로 통과 처리하지 않는다.

- 같은 부서 member: 담당/비담당, 동의/미동의, 공개/lead전용 근거.
- 같은 부서 lead 두 명: 동일 카드 경합, 각기 다른 결정 책임, 한 명의 권한 회수.
- org admin만 있는 사람: 운영 메타데이터 허용, 질문/카드/전사 본문 불가.
- 다른 부서/다른 조직 사용자: 직접 URL/RPC/검색/보존된 답변/후속 알림으로 유출0.
- 복수 소속자: dept 전환 도중 job 완료, 한 소속만 제거.
- 대행자: 유효 전/중/후, 철회, 비공개 읽기 없는 대행.
- 자료 작성자/검토자/확정자: 미확정 revision, 동시 수정, 원본 만료·다운로드 제한.
- 게스트: API 직접 호출까지 쓰기/LLM/외부전달0.

| D07 부서 간 출판물 | 실제 협업 빈도 낮거나 공개 계약을 합의 못함 | 부서 격리 유지, 기존 승인 문서를 사람이 전달 |

사용자 검증 전의 좋은 설계는 기능 수가 많다는 뜻이 아니다. 가설을 작게 시험하고, 얻는 가치보다 유지 비용이 큰 기능은 줄이는 것이 이 검토의 실행 원칙이다.
