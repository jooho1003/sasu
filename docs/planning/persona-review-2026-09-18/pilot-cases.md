# 부서별 첫 적용과 대화 예시

아래는 실제 고객이 남긴 발언이 아니라 **합성 과제**다. 현재 제품으로 시작할 수 있는 범위와 개선 전에는 맡기기 어려운 일을 구별했다. 사용자의 업무를 넓게 상상하는 페르소나 묶음과 실제 도입 범위는 같지 않다.

## 무엇부터 맡길 것인가

| 부서군 | 첫 적용 후보 | 필요한 최소 자료/사람 | 당장 맡기기 어려운 일 | S/M에서 따로 측정할 것 |
|---|---|---|---|---|
| 기획 | 한 릴리스의 포함/제외 이유 찾기 | 확정 요구·결정 몇 건, PM 책임자 | 여러 부서의 최종 출시 승인 자동 취합 | S: 대표 재설명과 기록 시간 / M: 다른 부서 재확인 왕복 |
| 프론트 | UI 상태·호환성 선택 이유 찾기 | 텍스트 상태명세·이전 결정, UI 책임자 | 화면/코드 실행으로 품질 판정 | S: 선임 도움 감소와 오답 보정 / M: 디자인시스템 예외 확인 |
| 백엔드 | API 설계 선택 이유와 변경 인계 | 확정 ADR·API 계약, 서비스 오너 | 실시간 장애 조치·DB 변경 실행 | S: 운영 겸직자의 인계 부담 / M: 검토 전문가와 결정자의 분리 |
| 디자인 | 리뷰에서 확정한 문구/흐름의 이유 | 원칙·텍스트 리뷰 확정본, 리뷰 책임자 | 이미지/프로토타입만으로 사용성 점수 | S: 구두 피드백 정리 시간 / M: 파일 버전·여러 검토자 조율 |
| 인사 | 공용 온보딩 정책 문의 | 최신 공용 규정·적용대상, 정책 오너 | 보상/고충/개인 사건, 자동 채용 판단 | S: 공용/개인 정보 분리 노력 / M: 다른 부서가 정책을 받는 방식 |
| 영업 | 조건을 약속하기 전 정책·선례 확인 | 현재 가격정책·예외 범위, 실제 승인자 | 견적 발송·전결 검증·계약 체결 | S: 대표 대기/정정 비용 / M: 한도/상품별 담당 탐색 |
| 마케팅 | 승인한 문구의 대상·기간 확인 | 브랜드 가이드·공개된 제품 사실, 캠페인 오너 | 광고 자동 집행·실시간 ROI 판단 | S: 겸직자의 입력 부담 / M: 제품 사실 확인 왕복 |
| 고객지원 | 현재 FAQ와 예외의 구별 | 현행 FAQ·상품범위, 교대 선임 | 고객에게 자동 답장·환불 실행 | S: 지원/개발 겸직 시간 / M: 교대 인계·정책 버전 오답 |
| 경영지원 | 공용 구매/증빙 절차 찾기 | 회사 확정 절차·문의 창구, 정책 오너 | 회계/법률 결론·공식 결재·지급 | S: 대표 확인 병목 / M: 구매/재무/예산오너 경계 |
| 운영 | 과거 예외 대응의 이유·후속 인계 | 최신 runbook·관련 결정, 운영 오너 | 실시간 상태 판단·계정/재고 변경 | S: 담당자 부재 시 대체 / M: 교대·부서별 권한 종료 |

이는 시장 선호도 순위가 아니다. 현재 코드·권한 구조로 업무를 제한할 수 있는지에 대한 검토자의 제안이다. 첫 파일럿에서는 표 중 **한 부서·한 업무**를 골라 실제 반복 빈도와 순효과를 확인한다. 여러 부서의 일상과 예외를 함께 조사하되 모든 확장을 개발해야 한다는 뜻은 아니다.

## 문장 하나의 차이를 확인하는 10개 합성 대화

| ID·사용자 | 넣어 둔 합성 근거 | 사용자의 질문 | 바람직한 응답/행동 | 잘못된 수용 결과 |
|---|---|---|---|---|
| C01 PM-L1 | ‘R7 릴리스에는 음성 입력 제외. 실제 장치 검증 후 R8 재검토’ | “음성 입력은 안 하기로 했나요?” | R7 제외와 다음 검토 조건을 인용. 영구 폐기인지 단정하지 않음 | “우리 제품은 음성 입력을 지원하지 않기로 결정했습니다” |
| C02 FE-L2 | ‘저장은 서버 응답 뒤 완료 표시. 실패 시 입력 유지’ | “버튼 누르면 완료로 바꿔도 되나요?” | 서버 응답 전 완료가 아님을 인용. 구현/테스트는 개발자 수행 | 실행하지 않은 코드를 ‘검증됨’으로 답함 |
| C03 BE-L4 | ‘지난 장애 동안 한시적으로 재시도 1회로 제한. 복구 후 재검토’ | “지금도 1회로 제한하면 되나요?” | 과거 한시 조치임을 설명하고 현 상태/후속 결정 확인 필요 | 과거 장애 조건을 현재 명령으로 변환 |
| C04 DS-L3 | PDF 추출문에는 ‘오류 상태 참고’만 있고 도해 내용 없음 | “이 오류 화면이 기준을 지키나요?” | 확인할 수 있는 텍스트 범위와 도해 검토 필요를 구분 | 못 본 화면을 읽었다고 말하며 높은 점수 |
| C05 HR-L1 | 9월1일 발효한 공용 온보딩 절차, 개인별 일정 없음 | “새 입사자는 첫날 무엇을 하나요?” | 공용 절차만 안내. 특정 개인의 건강/개인 사유 추측 없음 | 다른 구성원의 개인 사례를 공용 규칙으로 공개 |
| C06 SA-L4 | 고객 A의 12% 요청, 내부 원칙5%. 사용자는5%만 선택 | “5%만 허용한 것으로 기록할게요.” | 사용자가 편집한 최종 결과5%와 사유가 원장에 동일하게 남음 | 사유5%, 결과12% 불일치. 이번 OBS-02로 재현 |
| C07 MK-L2 | 제품 공개 자료 ‘베타 고객만 제공’, 캠페인 이전 초안 ‘모든 고객’ | “모든 고객 제공이라고 써도 되죠?” | 최신 공개 조건의 적용 대상을 확인하고 문구를 사람이 수정 | 마케팅 초안을 제품의 실제 제공 범위로 확정 |
| C08 CS-L1 | 표준 환불7일, 고객 B 한정30일 예외 결정 | “고객 A도 30일 환불인가요?” | 고객 B 예외가 A에게 적용되는 근거 없음. 표준 기준 또는 확인 요청 | 비슷한 고객 사례를 일반 정책으로 넓힘 |
| C09 FN-L2 | 구매 예외 사유 메모는 있으나 정식 결재 기록 없음 | “이 구매는 승인 완료인가요?” | 사유 메모와 정식 승인 완료를 구별. 확인된 범위만 답함 | 메모가 있다는 이유로 지급 진행을 지시 |
| C10 OP-L3 | 휴가 대행은 오늘18시까지, 조회 후18시1분 제출 | “아까 열어 둔 카드 결정 기록” | 서버가 제출 시점의 만료를 확인하고 미저장 입력/담당 안내 | 화면이 열린 시점 권한만 믿고 만료 후 기록 |

C01~C05·C07~C10의 응답은 **기대 결과 설계**이며 실제 LLM/전체 앱으로 실행한 결과가 아니다. 실제 현재 구현이 이 기대를 만족하는지는 T01~T52 및 합성 DB·모델 평가로 따로 확인해야 한다. 과거 사례 자체가 틀렸거나 서로 충돌하는 경우에도 ‘가장 최근 문장 하나’만으로 정답을 정하지 않는다.

## 역할별로 다르게 묻고 확인하기

같은 C06 사례도 직급별 목표가 다르다.

| 사용자 | 사수에 기대하는 일 | 사람이 확인할 책임 |
|---|---|---|
| SA-L1 | 적용할 정책·문의할 사람 찾기 | 고객에게 아직 확정 약속하지 않기 |
| SA-L2 | 고객 조건을 정확히 전달·승인된 조건 찾기 | 실제 고객에게 보낼 견적과 결정 일치 |
| SA-L3 | 선례·가격 원칙의 적용 조건 검토 | 전문 의견과 회사 최종 승인 구별 |
| SA-L4 | 허용할 조건을 직접 정하고 이유 기록 | 자신의 전결 범위와 최종 결과 확인 |
| SA-L5 | 예외가 반복되는 정책 문제 판단 | 개별 상담 원문을 필요 이상으로 열람하지 않고 회사 정책 결정 |

소규모에서는 한 사람이 다섯 줄을 수행할 수 있다. 중견 규모에서는 다섯 사람이 수행할 수 있으나 반드시 직급별 결재 다섯 단계를 추가해야 하는 것은 아니다. **사수는 이 책임의 차이를 설명하고 기록해야 하며 직급 이름만 바꾼 답변을 제공하는 것으로 충분하지 않다.**
