# 실제 업무를 따라가는 14개 검토 여정

모든 이름·조건은 합성이다. 아래의 현재 흐름은 코드/명세 대조이며 **J02의 결정 입력과 J03의 거절 UI만 이번 브라우저에서 직접 재현**했다. ‘개선 후’는 아직 구현되지 않은 제안이다. 각 여정의 성공은 사용자가 원하는 일을 정확한 권한으로 마치는 것으로 정의한다.

## J01 출시 범위: 기획 → 개발·디자인 → 제품 책임자

- **주인공/목적:** PM-L2가 금요일 출시에서 음성 입력을 제외할지 묻는다. FE-L3·DS-L3는 실패 상태가 덜 검증됐다는 근거를 제공, PM-L4가 범위를 정한다.
- **현재 흐름:** 동의된 Slack 논의 수집 → 분류/카드 → lead/담당자가 근거 확인 → 결정 → 원장 → 신입이 ‘왜 제외했나’ ASK. 각각 같은 부서 권한 내에서 가능하다.
- **얻는 점:** 출시 이후 논쟁이 ‘누가 그렇게 말했나’ 대신 기록된 이유를 중심으로 이어질 수 있다.
- **막힘:** 다른 부서의 비공개 증거를 읽을 수 없고, 같은 출시의 카드 묶음·부서별 수락·실제 배포 완료는 별도다. 같은 부서로 다 합치는 편법은 정보 접근을 바꾼다.
- **S/M:** S는 한 팀 안 판단과 기록의 빠른 연결. M은 검토 의견·최종 범위 결정·FE/DS 수락을 구별해야 한다.
- **개선 후 성공:** 사람의 확정 범위와 사유가 보이고(D01), 릴리스 대상이 연결(D08), 다른 부서는 승인된 최소 전달물만 수락(D07). 검증 질문: ‘이번 금요일 제외’가 ‘영구 폐기’로 읽히지 않는가? G01·G07·G15·G16.

## J02 할인 예외: 영업 실무자 → 팀장 → 재무

- **주인공/목적:** SA-L2는 고객 A의 12% 할인 요청을 전달한다. SA-L4는 정책상 5%까지만 허용하려 한다. 12/5라는 숫자는 합성이다.
- **현재 실행 관찰:** 실제 CardActions에 ‘5%만 승인, 12%는 승인하지 않음’ 입력 → 결정 클릭 → 캡처한 `outcome`은 ‘12% 할인 승인’, `rationale`만 5%. 저장 API는 합성 응답으로 처리해 실제 원장은 변경하지 않았다. Slack 모달에는 결과 입력란이 있다.
- **얻는 점:** 정상적으로 기록된다면 고객에게 약속한 조건의 이유와 승인자를 추적할 수 있다.
- **막힘:** 사유에 조건을 썼다는 것만으로 최종 결과가 바뀌지 않는다. 사후 정정 기능은 있지만 잘못된 최초 기록을 예방하지 못한다.
- **S/M:** S는 대표가 같은 판단을 직접 한다. M은 회사 전결표/재무 검토를 별도 완료해야 한다. 현 사수 권한을 회사 규정 준수로 해석하면 안 된다.
- **개선 후 성공:** 결과5%·사유·대상·정식 승인 필요 여부를 확인 후 기록. 다른 사람이 먼저 기록했다면 새 입력으로 덮어쓰지 않고 실제 저장 내용을 보여준다. D01·D03, G01·G03·G19.

## J03 입사 첫 주: 근거 없는 질문을 사람에게 넘기기

- **주인공/목적:** PM/HR/CS-L1이 ‘이 고객/이 비용/이 기능은 누가 결정하나요?’라고 질문한다.
- **현재 실행 관찰:** 합성 refused 응답에서 근거 부족 안내와 ‘카드로 승격’ 설명은 있지만 결과 행동은 ‘이어서 질문하기’뿐이다. 현 cards API에는 원본 item이 필요하다.
- **얻는 점:** 모른다고 답하는 것은 근거 없는 확신보다 신뢰할 수 있는 경계다.
- **막힘:** 반복 질문으로 답을 얻으려 하거나 동료를 다시 찾는다. 권한 밖 자료가 있다는 암시를 보여주는 방식은 해법이 아니다.
- **S/M:** S는 대표/한 lead 확인. M은 담당 업무가 다른 여러 lead가 있어 확인 주체 선택부터 필요하다.
- **개선 후 성공:** 질문자 검토를 거친 확인 요청 → 받을 사람이 수락/다른 적법한 담당 안내 → 확인 가능한 근거 또는 사람 답변 → 필요시 정식 결정으로 전환. 근거 없는 AI 추천 카드/DM을 만들지 않는다. D02·D03, G02·G21·G23.

## J04 리뷰 자료: 실무자 초안 → 전문가 검토 → lead 확정

- **주인공/목적:** DS-L2의 PDF 화면 설명 또는 PM-L2 요구 문서를 확정 근거로 만들고 싶다.
- **현재 흐름:** lead가 업로드 → 추출/전사 job → 오류와 원문 확인 → 편집/확정 → 요약/질문/역할 평가. 단순 업로드 즉시 모든 텍스트가 확정 사실이 되지 않는 점은 장점이다.
- **막힘:** 실무자가 자료를 보내고 lead가 대신 올려 고쳐야 한다. 화면 중심 PDF의 빠진 그림을 문서 점수로 평가할 위험도 있다.
- **S/M:** S는 한 사람의 검토 시간이 병목. M은 전문가에게 lead를 줘 해결하면 비공개 접근과 결정권한까지 넓어질 수 있다.
- **개선 후 성공:** 승인된 contributor가 제한된 초안에 기여 → 지정 검토자 → 확정 담당자의 공개 범위 확인. 확정 전에는 검색/평가 근거로 사용하지 않는다. OCR/비전 지원 없으면 한계를 명시한다. D04·D06, G04·G09·G22.

## J05 장애 중 과거 결정 참조: 백엔드 → 운영 책임자

- **주인공/목적:** BE-L2가 과거에 재시도 제한을 완화한 이유를 찾고 BE-L4가 이번 장애에서 적용할지 판단한다.
- **현재 흐름:** 권한 있는 원장/ASK로 당시 결정 확인 → 현재 상태는 모니터링/runbook에서 별도 확인 → 사람이 새 결정 기록.
- **막힘:** 과거 장애의 한시 조치가 현행 정책처럼 제시될 수 있다. 사수 응답 지연 때문에 장애 대응을 멈춰서는 안 된다.
- **S/M:** S는 온콜이 팀장 겸임. M은 사고 지휘자·서비스 오너·보안 담당이 다르다.
- **개선 후 성공:** 과거의 대상/유효 기간/대체 결정과 현재 확인 시점을 구별. 긴급 운영은 기존 절차로 진행하고 사후 근거를 연결한다. 자동 복구 명령은 없다. D03·D06·D08, G06·G16·G23.

## J06 표준 환불 정책: 고객지원 신입 → 선임

- **주인공/목적:** CS-L1이 특정 고객의 환불 조건을 확인하되 아직 고객에게 답하지 않는다.
- **현재 흐름:** 부서 공개 FAQ/정책 ASK → 인용 확인 → 사람 응대. 타 고객의 과거 예외도 검색 근거로 들어올 수 있어 조건 판단이 필요하다.
- **막힘:** 현 정책 시행일·고객 유형·상품 범위와 예외의 차이가 잘 보이지 않는다. 모르면 별도 선임 DM으로 돌아간다.
- **S/M:** S는 대표에게 바로 예외 요청. M은 교대 책임자와 환불 한도별 담당이 다르다.
- **개선 후 성공:** 정책과 고객 예외를 구별, 부족하면 확인 요청, 실제 환불/답장은 기존 도구에서 수행. 고객 개인정보를 최소화한다. D02·D03·D06, G02·G06·G08.

## J07 마케팅 승인: 콘텐츠 → 제품 사실 확인 → 집행

- **주인공/목적:** MK-L2가 ‘이번 달 모든 고객 제공’ 문구를 쓰려 하나 제품 출시는 일부 고객만 대상이다.
- **현재 흐름:** 마케팅 부서 기록만으로 답변/카드. 제품 부서 비공개 문서를 마음대로 가져올 수 없다.
- **막힘:** 마케팅이 모르는 제품 변경 사실을 모델이 보충할 수 없다. 문구 결정과 광고 실제 집행은 다르다.
- **S/M:** S는 제품/마케팅 겸직자가 잘못된 부서에서 질문하기 쉽다. M은 제품 사실의 공개 책임과 브랜드 검토가 나뉜다.
- **개선 후 성공:** 제품팀이 공유 가능한 사실만 전달·버전 관리 → 마케팅이 해당 조건으로 문구 확정 → 실제 집행 확인 별도. D06~D08, G07·G14·G16.

## J08 구매/계약: 경영지원 → 예산 책임자 → 공식 시스템

- **주인공/목적:** FN-L2가 예외 구매 사유를 남기고 FN-L4/예산오너가 검토한다.
- **현재 흐름:** 카드 또는 직접 기록으로 선택과 사유를 남길 수 있다. 회사의 전자결재·지급·법률 검토를 완료하는 기능은 아니다.
- **막힘:** 직접 기록자와 승인자가 같은 것으로 보이거나 AI 배정된 실무자가 회사 승인자로 해석될 수 있다.
- **S/M:** S는 대표 전결이 단순할 수 있지만 확인해야 한다. M은 금액/유형/부서별 여러 책임자와 시스템이 있다.
- **개선 후 성공:** 결정 기록의 지위, 공식 결재 참조, 후속 지급 상태가 분리된다. 범용 전자결재를 새로 만들지 않는다. D01·D03·D08, G03·G19.

## J09 휴가·교대: 담당자 대행과 되돌림

- **주인공/목적:** OP/CS-L4 휴가 중 OP/CS-L3가 일부 공개 안건만 담당한다.
- **현재:** 알림/보류 기능은 있지만 범위·기간·수락을 가진 대행 계약은 확인 범위에서 찾지 못했다. 임시 lead 승격으로 해결하면 열람 권한도 바뀐다.
- **S/M:** S는 한 대행자와 짧은 목록. M은 교대 시작/종료·영역별 대행·처리 중 경합이 반복된다.
- **성공/실패 테스트:** 대행자가 볼 수 없는 원문은 알림에 포함하지 않고, 기간 만료 직전 열린 페이지의 제출도 서버에서 거부. 원래 담당 복귀 후 완료/미결 구분, 양쪽 동시 결정은 한 건. D03·D05, G03·G24.

## J10 전문가 겸직·부서 이동

- **주인공/목적:** BE-L3가 플랫폼과 제품 두 부서에 소속돼 다른 범위의 질문을 한다.
- **현재:** 웹 기본 부서는 첫 멤버십, 일반 사이드바에는 전환 링크가 없다. Slack DM에는 부서명 선택 계약이 있다.
- **S/M:** S는 대표 겸직으로도 발생. M은 이동·매트릭스 협업에서 자주 발생할 가설.
- **성공/실패 테스트:** 소속만 목록에 표시, 전환 시 이전 질문/인용/비동기 응답을 새 부서에 표시하지 않음. 소속 제거 뒤 직접 URL·저장 답변 재조회 차단. 입력을 옮길 때는 명시적 확인 없이 전송하지 않는다. D07, G14·G24.

## J11 민감 HR 사건과 공용 규정

- **주인공/목적:** HR-L3는 공용 휴가 정책을 안내하면서 특정 구성원의 민감 사유를 비공개로 지키려 한다.
- **현재:** dept/leads_only 두 범위는 공용 정책에 유용하지만 ‘사건 담당자 두 명만’ 범위를 표현하지 못한다.
- **S/M:** S에서도 대표/겸직자에게 모든 사유를 알릴 필요는 없다. M은 인사 부서 안 직무별 접근 차이가 더 많다.
- **성공/실패 테스트:** 공용 규정은 필요한 부서에 승인된 전달물로 공유, 개인 사건 자료는 현재 지원 범위 밖으로 안내. 인사팀 모든 lead에 공개하거나 질문 원문을 관리자 진단에 노출하지 않는다. G07·G20·G26. 이 여정의 개인 사건 수용은 향후 별도 설계이며 현재 도입 성공으로 세지 않는다.

## J12 동의 철회·노션 범위 변경·원본 삭제

- **주인공/목적:** X03이 수집 동의를 철회하고 OP admin은 수집 범위를 변경한다.
- **현재:** 미동의 발언 skip·원문 생명주기/보존·재검증 계약이 있고 노션 확대 수집은 다른 세션에서 진행 중이다.
- **S/M:** S는 한 명 미동의로 자료 구성이 달라질 수 있다. M은 신규 입사·이동으로 수집 준비 상태가 반복 변화한다.
- **성공/실패 테스트:** 요청→job→DM 직전 권한/동의 변화, 노션 page/root 제거, 원문/원본 삭제를 각각 테스트. 질문자에게 권한 밖 문서 수·제목·발언 여부를 암시하지 않는다. 원장 인용의 보존과 검색 가능 여부를 같은 의미로 설명하지 않는다. D06·D10, G12·G13·G26.

## J13 문서 평가와 지원자 체험

- **주인공/목적:** HR-L2와 FE/DS-L3가 사수의 합성 채용 미션을 검토한다.
- **현재:** 다섯 부서 mission 합성 체험과 문서 역할 평가가 있으며, 개별 지원자 링크/제출/파기는 phase26 설계다.
- **S/M:** S는 실제 채용에 빠르게 쓰고 싶을 수 있음. M은 면접관별 기준·지원자 목적/동의·접근/보존이 중요.
- **성공/실패 테스트:** 합성 데이터/참고 점수 표시, 근거 부족을 저역량 판정으로 변환하지 않음, 기준 버전과 사람 검토 분리. 실제 지원자 flow를 이 검토의 제안으로 개시하지 않는다. D09, G10·G18.

## J14 첫 설치와 2주 후 유지

- **주인공/목적:** S의 대표 겸 lead 또는 M의 IT admin+부서 lead가 실제 반복 업무 한 종류를 시작한다.
- **현재:** 동의·소스·원칙 문서·자료/알림 설정 기능이 있지만 기능을 연결했다고 유용한 근거가 생기는 것은 아니다.
- **막힘:** 데모는 자료가 풍부하고 실제 새 부서는 비어 있다. 분류 오탐·업로드·동의 안내·노션 범위 관리 시간이 편익을 상쇄할 수 있다.
- **S/M:** S는 한 사람이 관리하는 총시간, M은 부서/관리자 간 요청 왕복과 접근 계약이 핵심.
- **성공/실패 테스트:** 실제 질문 5개와 결정 3개를 모집해 baseline과 비교하는 연구 제안. 모르는 질문도 포함. 검색시간 절약에서 검토/설정/정정 비용을 뺀다. 두 주는 제안한 관찰 기간이며 수행 결과가 아니다. D10, G05·G21·G23·G27·G28.
