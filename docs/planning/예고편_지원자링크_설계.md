# 채용 예고편 — 지원자별 개별 링크·제출·채점 설계

> 상태: **설계 승인·문서 개정 완료 (2026-09-18, PRD 1.14 · ADR-062 · 불변식 20·21). 구현·운영 반영을 뜻하지 않는다.** 사용자 결정(9/18): ① 지원자마다 다른 URL을 발급해 전달 ② 제출·채점 포함 ③ 지원자 식별은 이메일 저장 ④ 7일 만료·기간 내 여러 번 열람.
> 이 문서는 상위 문서를 바꾸지 않는다. 승인되면 PRD §3-2·§8-1 → ARCHITECTURE 불변식 → ADR-062 순으로 먼저 고친 뒤 phase step을 만든다(§9).

## 0. 지금 구조와 바뀌는 점

| | 지금 (ADR-045) | 이 설계 |
|---|---|---|
| 링크 | 예고편당 1개 `/t/<slug>`, 가진 사람 누구나 | 그대로 유지 + 지원자별 `/t/i/<token>` 추가 |
| 지원자 구분 | 없음 | `trailer_invites` 1행 = 지원자 1명 |
| 제출 | 없음(브라우저 메모리만, 서버 전송 0) | 개별 링크에서만 1회 제출 → `trailer_attempts(kind='candidate')` |
| 채점 | 합성 지원자 3명만 | 같은 `score_trailer_attempt` job·같은 근거 검증을 실제 제출에 적용 |
| 개인정보 | 수집 0 | 이메일·자유 서술 이유·선택 이벤트 수집 → **동의·보관·파기·철회 필요** |

공개 슬러그 링크(`/t/<slug>`)의 "전송·저장하지 않는다"는 약속은 **바꾸지 않는다.** 제출은 개별 링크 경로에만 있다.

## 1. 풀어야 하는 상위 문서 조항

| 조항 | 현재 | 개정 방향 |
|---|---|---|
| PRD §8-1 유보 표 (`docs/PRD.md:911`) | 실제 지원자 사전과제(초대·동의·제출·채점·보관 파기)는 법률 자문 전 유보 | 기능은 만든다. **조직별 개시는 여전히 유보** — `orgs.trailer_assessment_enabled`는 기본 off, 운영 스크립트만 변경(법률 확인·처리방침 게시 확인 후) |
| PRD §3-2 "바뀌지 않는 것" (`:248`) | 실제 지원자 초대·채점 비활성 | "기본 비활성, 조직 단위 개시는 운영 절차" 로 수정 + phase 26 행 추가 |
| ADR-045 4항 | 실제 지원자 초대·동의·보관 파기는 만들지 않는다 | ADR-062가 이 항만 대체. 합불·추천·순위 금지, 표현 금지선은 그대로 |
| ARCHITECTURE 불변식 21 | 채점은 `trailer_assessment_enabled`=true에서만, 값은 운영 스크립트만 | **그대로 유지**(이 설계의 법적 안전장치). 문장만 "초대 발급·제출·채점 모두 이 값에 묶인다"로 확장 |
| ARCHITECTURE 불변식 20 | 공개 조회는 `{scenarios, apply_url}`만, 조직 미노출 | 개별 링크 경로에 한해 **수집 주체 표시용 조직 표시 이름** 1개를 추가로 반환(동의의 유효 요건). 슬러그 경로는 불변 |
| ADR-040·ARCHITECTURE §6-1 | 체험에 API·쿠키·스토리지·행동 로그 추가 금지 | 슬러그 경로·`/trailers`·데모는 불변. 개별 링크 경로만 제출 API 1개를 갖는다. 쿠키·localStorage는 여전히 쓰지 않는다 |

**개시 3중 게이트** — 셋 다 참일 때만 발급·열람·제출이 된다.
1. 환경 플래그 `SASU_TRAILER_INVITES_ENABLED`(코드 경로 자체, 기본 false → 라우트 404)
2. `orgs.trailer_assessment_enabled`(조직 단위, 운영 스크립트만)
3. 예고편이 발행 3조건을 만족(`status='published'`, 두 해시 일치, `trailer_publish_enabled`)

`(확인 필요: 법률 자문)` — 개인정보보호법 §15(동의)·§37-2(자동화된 결정), 채용절차법 §4-3·§11(채용서류 반환·파기), AI 기본법 고영향 영역 해당 여부. 자문 전에는 2번 게이트를 어떤 실제 조직에도 켜지 않는다.

## 2. 데이터 모델 (마이그레이션 1개 + 롤백 SQL)

번호는 작성 시점의 다음 번호를 쓴다(다른 세션이 0039를 쓸 수 있다).

```
trailer_invites
  id uuid pk
  trailer_id uuid → trailers(id) on delete cascade
  dept_id, org_id           -- 트리거가 trailers에서 채운다(요청 본문 불신)
  email_normalized text      -- lower(btrim), 길이 ≤ 254. 파기 시 null
  email_hash text            -- sha256(email_normalized). 열람 시 대조용, 파기 후에도 중복 발급 판정에 사용하지 않는다(파기 시 같이 null)
  token_hash text unique     -- sha256(token). 평문 토큰은 저장하지 않는다
  expires_at timestamptz     -- 발급 + 7일
  revoked_at, first_opened_at, consented_at, consent_version text
  open_failures int default 0   -- 이메일 불일치 횟수, 10회면 잠금
  attempt_id uuid unique → trailer_attempts(id)   -- 1 초대 = 1 제출
  purge_after timestamptz    -- §6
  created_by uuid → auth.users, created_at
  unique (trailer_id, email_hash) where revoked_at is null  -- 같은 예고편에 같은 지원자 활성 링크 1개
```

- `trailer_attempts`에는 **이메일을 넣지 않는다.** `invite_id uuid unique` 컬럼만 추가하고, `label`은 비식별 값(`지원자 01`…, 발급 순번)으로 채운다. 이메일은 초대 테이블에만 있고 파기도 거기서 한다.
- 토큰: 기존 `member_invites` 패턴 그대로 — DB 안에서 `gen_random_uuid()` 2개 → 64자 hex, 해시만 저장, 평문은 발급 RPC 반환값으로 **한 번만**.
- RLS: `revoke all … from public, anon, authenticated` → `grant select to authenticated`. 정책은 읽기 1개 `can_see(auth.uid(), dept_id, 'leads_only')`. **anon 정책·데모 읽기 정책은 만들지 않는다.** 쓰기 정책 0개(전부 RPC).
- **데모 조직 금지**: 발급 RPC는 `orgs.is_demo`면 거부한다. 이유: 데모 시드가 데모 조직의 `trailer_assessment_enabled`를 켜고, `trailer_attempts_demo_read`가 데모 부서의 attempt를 anon에 공개한다 — 막지 않으면 실제 지원자 제출이 로그인 없이 읽힌다. `guard_trailer_attempt` 트리거에도 "데모 부서에 `kind='candidate'` 금지"를 추가해 이중으로 막는다.
- 조직당 활성 초대 한도(예: 예고편당 200, 1회 발급 20). 감사 기록은 `admin_events`가 아니라 초대 행 자체(`created_by`·시각)로 충분하다.

## 3. RPC (전부 SECURITY DEFINER, 실행 권한 회수 후 최소 grant)

| 함수 | 실행 | 하는 일 |
|---|---|---|
| `create_trailer_invites(p_trailer, p_emails text[])` | authenticated | 부서장(`leads_only`)·3중 게이트·비데모 검사 → 행 생성 → `(invite_id, email, token, expires_at)[]` 반환. 이미 활성 링크가 있는 이메일은 건너뛰고 사유 반환 |
| `revoke_trailer_invite(p_invite)` | authenticated | `revoked_at` 기록, `token_hash='void:'||id` |
| `trailer_invite_open(p_token, p_email)` | **anon** | 토큰 해시·만료·철회·잠금·게이트 확인 → 이메일 해시 대조(불일치면 `open_failures+1`, 동일한 모호 오류) → `first_opened_at` 기록 → `{scenarios, apply_url, org_display_name, state, consent_required, consent_version}` |
| `trailer_invite_consent(p_token, p_email, p_version)` | **anon** | 동의 시각·버전 기록. 동의 전에는 제출 거부 |
| `submit_trailer_invite_attempt(p_token, p_email, p_submissions jsonb)` | **anon** | 위 검사 전부 + 동의 확인 + `attempt_id is null` → `trailer_attempts(kind='candidate')` insert + `invites.attempt_id` 연결 + **같은 트랜잭션에서 `jobs`에 `score_trailer_attempt` insert**(멱등키 `attemptId:updated_at`) |
| `withdraw_trailer_invite_attempt(p_token, p_email)` | **anon** | 지원자 본인 철회: attempt 행 삭제, 초대의 이메일·해시 null, 상태 `withdrawn` |

핵심 규칙
- **요청 경로에서 service role 클라이언트를 쓰지 않는다.** 공개 라우트는 anon 클라이언트로 위 RPC만 부른다. "세션"에 해당하는 검증(토큰+이메일)은 TS가 아니라 SQL 안에 있다. job insert도 RPC 안에서 한다.
- 오류는 구분하지 않는다: 없는 토큰·만료·철회·이메일 불일치·게이트 off 모두 같은 `invite_unavailable`. (부서장 화면에서는 상태를 구분해 보여 준다.)
- 제출 본문 구조 검증은 라우트에서 Zod(`TrailerAttemptSubmission`) + `validateAttemptSubmissions()`(열람 RPC가 돌려준 scenarios 기준), SQL에서는 배열 길이·바이트 상한(64KB)만. 워커가 채점 전에 다시 검증한다(기존 동작).
- 한도: 초대당 제출 1회(unique), 이메일 불일치 10회 잠금, 예고편당 하루 제출 상한(0027의 카운터 패턴 복제).

## 4. 화면

**부서장 — 예고편 검토·발행 화면(S18)에 "지원자 링크" 구역 추가**
- 이메일 여러 줄 붙여넣기(≤20) → [링크 만들기] → 결과 표에 이메일·링크·[복사]. **링크는 이때 한 번만 보인다**(해시만 저장). 닫은 뒤에는 [철회 후 새로 만들기]만 가능.
- 전달은 부서장이 직접 한다(메일·메신저). 사수는 메일을 보내지 않는다 — 발송 인프라·스팸 책임·수신 동의 문제를 만들지 않기 위해서다.
- 목록: 이메일 · 상태(미열람 / 열람 / 동의 / 제출 / 채점 완료 / 만료 / 철회 / 본인 철회) · 만료일 · [철회]. 조직 관리자 화면에는 나오지 않는다(메타데이터 집계에도 이메일 미포함).
- 점수표: 기존 "합성 지원자" 탭과 분리된 **"지원자 제출" 탭**. 정렬은 **제출순 고정** — 점수순 토글을 두지 않는다(여러 실제 지원자를 점수로 줄 세우면 순위표가 된다, ADR-045). 고정 문구·금지어 필터·클라이언트 재검증은 그대로. `_data.ts`의 `.eq("kind","synthetic")`는 탭별 분기로 바꾼다.

**지원자 — `/t/i/<token>`** (`noindex`, `Referrer-Policy: no-referrer`, 공고 링크는 `rel="noreferrer"`)
1. 이메일 확인: "링크를 받은 이메일 주소를 입력하세요" — 링크가 새도 이메일을 모르면 열 수 없다.
2. 안내·동의: 수집 주체(조직 표시 이름), 수집 항목(이메일·선택·이유 서술), 목적(채용 과제 참고 자료), 보관 기간, **AI 점수는 참고 자료이며 합격 여부를 자동으로 결정하지 않는다는 고지**, 설명·이의 제기 창구(채용 담당자), 동의 거부 시 불이익 없음(공개 체험은 가능). 체크 후 시작.
3. 체험: 기존 `RecruitmentTrailer`에 제출 모드 prop. 이 모드에서만 "서버로 전송하지 않아요" 문구를 "제출하면 채용 담당자에게 전달됩니다"로 바꾼다.
4. 제출 1회 → 완료 화면. 7일 안에 다시 열면 완료 상태와 [내 제출 철회]만 보인다. 점수는 지원자에게 보여 주지 않는다.
- 상태를 쿠키·localStorage에 두지 않는다. 새로고침하면 이메일 확인부터 다시 한다(미제출 작성 내용은 사라진다고 미리 안내).

## 5. 채점

- job·프롬프트·근거 검증·`weightedScore()`는 phase 12 그대로. 입력에 이메일·초대 id를 넣지 않는다(이미 `mask()` 적용).
- 실패 시 `status_reason`은 문자열 코드만. 제출 이유 원문을 로그·에러에 싣지 않는다(불변식 9).
- 영원한 스피너 금지: 기존 10분 스윕이 `failed`로 정리. 부서장 화면은 "채점 실패 · 다시 채점" 버튼(같은 attempt 재큐잉, 기존 RPC의 `on conflict` 경로).

## 6. 보관·파기·철회

- `purge_after` = 제출 시각(미제출이면 만료 시각) + **90일** `(확인 필요: 법률 자문 — 채용절차법 §11의 반환·파기 기간과 맞출 것)`.
- 매일 도는 정리 job: `purge_after` 지난 초대의 attempt 삭제, 이메일·해시 null. 행 자체는 "발급 n건·제출 n건" 집계를 위해 남긴다.
- 부서장 즉시 삭제, 지원자 본인 철회(§3) 둘 다 같은 파기 함수를 쓴다.
- 예고편 철회·삭제 시: 초대 cascade. 조직의 `trailer_assessment_enabled`가 꺼지면 열람·제출은 즉시 막히고 기존 데이터는 파기 일정대로.
- `app/(site)/privacy/page.tsx`에 지원자 항목 추가(처리 목적·항목·보관·파기·자동화된 결정 고지). 문구는 `korean-privacy-terms` 기준으로 작성하되 `(확인 필요: 법률 자문)` 표시.

## 7. 데모

- 실제 발급은 데모 조직에서 SQL로 막힌다(§2).
- 대신 `/demo/d/[dept]/trailers`에 **브라우저 전용 흉내**: 합성 지원자 3명에 대한 발급 목록·상태·[복사] 버튼, 링크는 `/demo/d/[dept]/trailers?candidate=A`로 열려 "합성 지원자 A의 링크로 들어온 화면" 배너와 함께 같은 체험이 뜬다. DB 쓰기 0·LLM 0(ADR-059 경계 유지). 점수표는 기존 합성 스냅샷을 그대로 쓴다.

## 8. 남는 위험

| 위험 | 대응 |
|---|---|
| 토큰이 URL 경로에 있어 호스팅 접근 로그에 남는다 | 해시만 저장·7일 만료·이메일 대조·철회. 앱 로그에는 토큰·이메일을 쓰지 않는다 |
| 이메일을 아는 제3자가 링크를 가로채 대리 응시 | 계정이 없는 구조의 한계. 점수는 참고 자료이고 면접 질문 생성용임을 부서장 화면에 고지 |
| 점수가 사실상 선발 기준으로 쓰임 | 점수순 정렬 없음·합불/추천/순위 필드 없음·금지어 필터·고지 문구. 조직 개시는 운영 절차 |
| 동의 없이 제출 | SQL에서 `consented_at is null`이면 제출 거부 |
| 데모로의 누출 | 발급 RPC + attempt 트리거 이중 차단, RLS 하니스에 anon 읽기 0건 케이스 추가 |

## 9. 진행 순서 (승인 후)

문서 개정(메인 세션, 위임 안 함) → phase `26-trailer-candidate-links` step 파일 생성 → Codex 실행.

| step | 이름 | 범위 | 티어 |
