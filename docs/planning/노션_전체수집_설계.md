# 노션 전체 수집 설계 — 자동 수집과 직접 등록을 한 파이프라인으로

- 작성일: 2026-09-18 · 상태: **설계 완료 · 구현 착수 승인(9/18) / 개통 검증·운영 반영 미실행**
- 범위 원천: [PRD §3-5·§8](../PRD.md), 구조: [ARCHITECTURE](../ARCHITECTURE.md), 선택 이유: [ADR-060](../ADR.md)
- 사용자 요구(9/18): 도입 초기의 방대한 노션 자료를 사람이 하나씩 넣지 않고 수집·정리·답변에 쓰게 한다. **최대한 자동화하는 방식과 일일이 붙이는 방식을 둘 다 제공한다.**
- 현재 기능: 부서장이 페이지 URL을 하나씩 붙여넣는 연결, 전체 스냅샷 원자 반영, 5분 자동 갱신, [다시 가져오기]는 운영 중이다(ADR-052). 아래 조직 연결·자동 발견·청크·증분·대량 레인은 신규 설계다.

## 1. 현재 구조와 요구 사이의 거리

| 항목 | 현재 (코드 확인 2026-09-18) | 대량 수집에서 생기는 문제 |
|---|---|---|
| 인증 | 서버 전역 `NOTION_TOKEN` 1개 (`lib/notion.ts:40`) | 고객사별 워크스페이스 구분 불가. 토큰이 닿는 페이지면 어느 조직의 부서장이든 ID만 알면 가져올 수 있다 |
| 등록 | 부서장이 URL 1개씩 → `sources` 1행 | 수백 페이지면 수백 번 붙여넣기 |
| 발견 | 없음. `/v1/search`·DB 조회 호출 0건 | 데이터베이스(회의록·위키 표)의 행 본문을 읽지 못한다 |
| 읽기 | 블록 BFS, 타입 무관 재귀, 5,000블록 초과 시 전체 실패 (`lib/notion.ts:96-97`) | 하위 페이지가 부모 소스에 섞여 들어오고, 루트 하나에 전체를 걸면 실패 |
| 저장 단위 | 블록 1개 = item 1개 (`lib/pipeline/notion-import.ts:25`) | 한 줄짜리 블록마다 분류 LLM 1회 + 임베딩 1회. PRD §6-10의 "헤딩 단위 청크"는 미구현 |
| 갱신 | 5분마다 전체 재읽기, `last_edited_time` 미사용, 틱당 20소스 (`0030_source_lifecycle.sql:160`) | 페이지 수에 비례해 호출이 늘고 예약이 밀린다 |
| 제한 대응 | 429의 `Retry-After` 미사용, 3회 실패 시 종료 (`lib/jobs.ts:53`) | 대량 수집 중 제한에 걸리면 곧 포기 |
| 처리량 | 워커 단일 레인, 분당 10 job, 임베딩 단건 호출 | 실시간 슬랙 처리와 같은 줄에서 경쟁 |

재사용하는 것: `begin/finish/release_notion_sync`의 lease·원자 교체, `items_version` 트리거와 파생물 무효화, 버전 조건부 완료(`complete_item_embedding`), jobs 재시도·실패 소유자 매핑, `can_see()` 단일 가시성, Slack 설치의 AES-256-GCM 암호화 저장(`lib/slack/installation.ts`), `is_org_admin()`.

## 2. 핵심 결정 — 단위는 하나, 등록 경로가 둘

**노션 페이지 1개 = `sources(kind='notion_page')` 1행**으로 통일한다. 데이터베이스의 행도 노션에서는 페이지이므로 같은 단위다. 자동 수집과 직접 등록은 "누가 그 행을 만들었는가"만 다르고, 읽기·청크·마스킹·저장·임베딩·갱신·삭제는 같은 코드를 탄다.

| | 직접 등록 (일일이 붙이기) | 자동 수집 |
|---|---|---|
| 누가 | 부서장 | 조직 관리자가 범위 지정, 이후 시스템 |
| 어떻게 | URL 1개 또는 여러 줄 붙여넣기. 선택: `하위 페이지 포함` | 노션 최상위 항목 → 부서 매핑, 또는 `전체를 한 부서로` |
| `sources.root_id` | null (`하위 포함`이면 부서장 소유 root) | 조직 관리자 소유 root |
| 새 페이지 | 다시 붙여넣어야 함 (`하위 포함`이면 자동) | 자동 포함(끌 수 있음) |
| 적합한 곳 | 원칙 문서 몇 개, 보안상 범위를 좁게 통제하려는 조직 | 도입 첫날 전체 이관, 회의록 DB, 팀 위키 |

두 방식은 한 조직 안에서 동시에 쓴다. 같은 부서에 같은 페이지가 두 경로로 들어오면 **활성 소스는 부서당 페이지당 1개**(부분 유니크 인덱스)로 막고, 먼저 있던 행에 root만 연결한다.

대안 비교 — root 1개를 소스 1개로 두고 페이지 목록을 별도 테이블로 관리하는 안은 소스 수가 적지만, 페이지별 lease·원자 교체·가시성·오류 표시·인용 제목을 전부 새로 만들어야 하고 직접 등록과 구조가 갈라진다. 채택하지 않는다.

## 3. 연결 — 조직당 워크스페이스 1개

`notion_installations`(조직당 1행)를 Slack 설치와 같은 규칙으로 둔다: 조직 관리자만 생성, 암호문만 저장(AAD에 조직·워크스페이스 id), 브라우저는 쓰기 RPC 실행 불가, 데모 조직 거부, 해지 시 토큰 삭제·소스 비활성. 복호화 토큰은 요청·job 단위 AsyncLocalStorage에만 둔다. **전역 `NOTION_TOKEN` fallback은 제거**하고 기존 파일럿 조직은 `scripts/register-legacy-notion.ts`로 검증 후 이전한다.

연결 방식은 저장소 하나에 두 가지를 담는다(`auth_kind`).

| 방식 | 흐름 | 상태 |
|---|---|---|
| `internal_token` | 고객사 관리자가 자기 워크스페이스에서 내부 통합을 만들고 토큰을 붙여넣음 → 서버가 `GET /v1/users/me`로 워크스페이스·봇을 검증 → 암호화 저장. 노션에서 최상위 페이지에 `연결 추가`를 하면 하위 전체가 공유된다 | **1차 구현.** 외부 심사·리다이렉트 설정이 필요 없다 |
| `oauth` | [노션 연결] → 노션 승인 화면의 페이지 선택 → callback(세션·HttpOnly cookie·10분 단회 state) → code 교환 → access/refresh 토큰 암호화 저장 | 2차. 노션 문서상 OAuth 토큰은 만료되고 refresh로 회전하며, 공개 통합의 승인 URL은 심사 제출 뒤 발급된다(2026-09-18 문서 확인, 실제 개통 검증 필요). 회전은 조직 단위 advisory lock 아래 1회만 수행 |

사람이 하는 일은 어느 쪽이든 **조직당 1회**다: 토큰 1번(또는 승인 1번) + 최상위 페이지 공유 + 부서 매핑.

## 4. 수집 범위 — `notion_roots`

| 컬럼 | 의미 |
|---|---|
| `org_id`, `dept_id` | 대상 부서. 조직 일치는 SQL에서 검증 |
| `scope` | `workspace`(공유된 전체 → 한 부서) · `subtree`(페이지 또는 데이터베이스 이하) |
| `notion_id` | subtree의 루트 페이지/DB id. workspace는 null |
| `visibility` | 이 범위에서 발견된 페이지의 기본값 `dept`\|`leads_only` |
| `include_new` | 새 하위 페이지 자동 포함(기본 true) |
| `created_role` | `org_admin` \| `lead` |
| `state`, `discover_cursor`, `last_discovered_at`, 집계 카운트 | 진행·재개 |

규칙:

- **매핑되지 않은 페이지는 본문을 읽지 않는다.** 통합에 공유됐지만 어느 root에도 속하지 않으면 `미배정 N건`으로 수만 센다. 부서가 정해지기 전에는 아무것도 저장되지 않는다.
- 한 페이지가 여러 root에 걸리면 **가장 가까운 조상 root**가 이긴다. `workspace`는 최후 순위다.
- 같은 페이지를 두 부서가 각각 매핑하면 부서별로 따로 저장된다(items는 부서 단일 소속). 전사 공용 범위는 `can_see()` 변경이 필요하므로 이 설계에 넣지 않는다.
- 제외: 부서장이 페이지/하위 트리를 제외하면 `notion_exclusions`에 기록하고 해당 소스를 비활성·본문 소프트 삭제한다. 제외는 재발견 때도 유지된다. 제목 패턴 제외(예: `템플릿`)는 부서장이 직접 추가한 규칙만 적용하며 기본 규칙은 없다.
- **조직 관리자는 내용을 보지 못한다(ADR-044 유지).** 관리자 화면은 자기가 공유한 최상위 항목의 제목, 부서 매핑, 부서별 카운트만 보여준다. 하위 페이지 제목·본문·오류 상세는 해당 부서장의 부서 설정에서만 보인다.
- 원본 권한은 상속하지 않는다(PRD §6-9 유지). 매핑 화면에서 "노션에서 일부만 보던 문서도 이 부서 전원(또는 부서장)에게 검색된다"를 고지하고, 조직 관리자가 업무 자료 수집 권한이 있음을 확인한 시각·계정을 설치 행에 기록한다.

## 5. 발견과 증분

job 3종. 모두 `sourceId`/`rootId`와 버전만 payload에 넣는다.

1. **`notion_discover` (root 단위)** — 트리 하강으로 발견한다.
   - subtree: 루트 페이지를 읽으며 `child_page`·`child_database` 블록을 하위 페이지로 등록. DB는 행을 조회해 각 행을 페이지로 등록. workspace: `/v1/search`로 최상위를 구한 뒤 같은 하강.
   - 1회 실행은 40초 시간 상한. 남으면 `discover_cursor`(대기 큐 위치 + API 커서)를 저장하고 자신을 다시 예약한다. 중단돼도 이어서 진행한다.
   - 등록은 `register_notion_page(root, page_id, parent_id, remote_edited_at)` RPC 하나가 한다: 제외·상한·중복을 검사하고 소스를 만들고 `notion_import`를 예약한다.
2. **`notion_import` (페이지 단위, 기존)** — 변경점 셋.
   - **하위 페이지로 내려가지 않는다.** `child_page`/`child_database`를 만나면 본문에 섞지 않고 발견 목록으로만 돌려준다. 페이지 자신의 토글·컬럼 등은 계속 재귀한다.
   - 블록을 청크로 묶는다(§6).
   - 404·`archived`·`in_trash`면 소스를 비활성화하고 본문을 소프트 삭제한다(기존 결정의 인용 스냅샷은 유지).
3. **`notion_poll` (조직 단위, 5분)** — `/v1/search`를 `last_edited_time` 내림차순으로 읽다가 저장된 워터마크보다 오래된 결과에서 멈춘다. 등록된 페이지면 `remote_edited_at`이 달라진 것만 `notion_import` 예약, 모르는 페이지면 부모가 등록된 경우에 한해 부모의 root로 등록한다.
   - `last_edited_time`은 분 단위라 같은 분의 재수정을 놓칠 수 있다. 값이 같아도 마지막 수집이 그 분 안이었다면 한 번 더 읽는다.
   - 검색 색인은 지연·누락이 있을 수 있으므로 **하루 1회 `notion_discover` 재조정**이 기준이다. 재조정은 트리를 다시 내려가며 편집 시각만 비교하고, 사라진 페이지를 정리한다.
   - 기존 `schedule_source_syncs()`의 5분 전체 재읽기는 `root_id`가 없고 증분 워터마크도 없는 기존 소스에만 남긴다.

3차: 노션 webhook(`page.created`·`page.content_updated`·`page.deleted`, `X-Notion-Signature` HMAC 검증). 구독은 통합 설정 화면에서 검증 토큰을 수동 입력해야 하므로 고객사별 개통 절차가 생긴다. 폴링이 기준이고 webhook은 지연을 줄이는 보조로만 쓴다.

**API 버전 — `2025-09-03`으로 전환한다(9/18 사용자 결정).** 현재 `2022-06-28` 고정인데, 노션 문서상 이 버전의 DB 조회는 사용자가 DB에 데이터 소스를 추가하면 실패한다(2026-09-18 확인). 새 버전에서 데이터베이스는 data source들의 컨테이너다. `child_database` 블록 → `GET /v1/databases/{id}`의 `data_sources[]` → 각각 `POST /v1/data_sources/{id}/query`로 행을 읽고, 검색 필터는 `page`\|`data_source`를 쓴다. 기존 단일 페이지 읽기(`/pages`·`/blocks/{id}/children`)가 새 버전에서 같은 응답 형태인지 어댑터 테스트와 실제 호출로 확인하고, 조회 불가 DB는 `notion_database_unsupported`로 구분해 표시한다. 조용히 빈 결과로 처리하지 않는다.

## 6. 정리 — 청크와 분류 생략

- **헤딩 단위 청크.** 헤딩(`heading_1~3`)에서 끊고, 2,400자(자료 검토함 확정 청크와 같은 값)를 넘으면 블록 경계에서 더 나눈다. 단일 블록이 상한을 넘으면 문장 경계로 자른다. `external_ref` = 청크 첫 블록 id(단일 블록 분할은 `#n` 접미). 청크 안의 수정은 같은 item의 내용 변경으로 잡혀 기존 버전 트리거가 재임베딩을 예약한다. 인용 검증은 문자열 포함 검사라 청크에서도 그대로 동작한다.
- 청크는 헤딩 블록으로 시작하므로 저장 본문(`items.content`)은 원문 그대로 둔다. 임베딩 입력에만 마스킹된 페이지 제목을 앞에 붙여 검색 문맥을 보강한다. 저장 본문을 바꾸지 않으므로 인용 검증은 영향이 없다.
- DB 행은 속성(제목·선택·날짜·사람 이름 제외)을 `속성: 값` 줄로 첫 청크에 넣는다. 사람 속성은 넣지 않는다.
- 40자 미만 본문만 있는 페이지는 소스는 만들되 item을 만들지 않는다(`빈 페이지`로 집계).
- **대량 수집분은 분류 LLM을 거치지 않는다.** root에서 온 소스는 `ingest_mode='reference'`로 두고 `finish_notion_sync`가 `classify` 대신 임베딩을 바로 예약한다. 과거 문서에서 결정 카드가 쏟아지는 것을 막고 LLM 비용을 0으로 만든다. 직접 등록한 원칙 문서(`root_id` null)는 지금처럼 분류한다. 부서장은 root 단위로 `카드 후보로도 사용`을 켤 수 있다(기본 off).
- 1년 넘게 수정되지 않은 페이지는 `오래된 문서`로 표시만 하고 수집한다. 답변 인용에는 기존처럼 출처 제목이 붙고, 수정 시각을 함께 보여주는 것은 UI step에서 정한다.
- 기존 소스 호환: `sources.import_version` 1(블록 단위·하위 페이지 인라인, 현행)과 2(청크·하위 미포함)를 둔다. 기존 행은 1로 남고 부서장이 [새 방식으로 전환]을 눌러야 2가 된다. 전환은 item id가 바뀌어 열린 카드의 근거가 무효화되므로 자동으로 하지 않는다.

## 7. 처리량 — 실시간과 분리된 대량 레인

- **레인 분리.** `notion_discover`·`notion_import`·`notion_poll`·`embed_batch`는 `bulk` 레인. `pg_cron`이 매분 `/api/jobs/run?lane=bulk`를 추가로 호출하고, 이 호출은 240초 시간 상한 안에서 claim을 반복한다. 기존 호출은 bulk kind를 claim하지 않으므로 슬랙 답변·카드가 밀리지 않는다.
- **호출 제한.** 노션은 연결당 평균 3 req/s(Business·Enterprise 10 req/s, 2026-09-18 문서 확인)이고 429에 `Retry-After`(초)를 준다. `NotionError`에 `retryAfterSeconds`를 실어 기존 `retryAt()`이 따르게 한다. bulk 레인의 429는 시도 횟수를 소모하지 않고 미루되, job 생성 후 24시간이 지나면 실패로 닫는다. 조직당 동시 실행은 설치 행의 lease로 1개로 제한한다.
- **배치 임베딩.** `embed_batch`가 같은 부서의 `pending` item을 최대 64개(토큰 예산 내) 묶어 Voyage에 1회 호출하고, 결과는 item마다 기존 `complete_item_embedding(item, version, …)`로 반영한다. 버전이 바뀐 항목은 버려진다. 배치 상한·요금은 개통 전에 Voyage 문서로 확인한다.
- **페이지 상한.** 하위 페이지를 섞지 않으므로 5,000블록 상한은 유지하고 오류 코드를 `notion_page_too_large`로 분리한다.
- **조직 상한.** `org_settings.notion_page_limit`(기본 2,000). 임베딩은 1024차원 float4로 청크당 약 4KB이고 색인 비용이 더 붙는다. 현재 Supabase 요금제의 DB 용량에서 수만 청크는 들어가지 않으므로, 상한을 올리는 것은 용량 확인 뒤 운영자가 한다. 상한에 닿으면 발견은 계속 세되 등록을 멈추고 현황판에 표시한다.
- 규모 추정(가정: 1만 페이지, 페이지당 API 3회·청크 5개): 노션 읽기 약 3시간, 청크 5만 개, 임베딩 호출 약 800회, 벡터 약 200MB+색인. 수치는 가정이며 합성 워크스페이스 측정으로 대체한다.

## 9. 보안·불변식 점검

| 불변식 | 이 설계에서 |
|---|---|
| 가시성은 `can_see()` 하나 | 변경 없음. 소스 visibility만 채운다 |
| 요청 경로 service role 금지 | 관리자·부서장 화면은 세션 + SECURITY DEFINER RPC. 토큰 저장·발견·수집은 수집 어댑터/워커 |
| `dept_id`는 본문이 아니라 멤버십에서 | 직접 등록은 기존대로. root의 `dept_id`는 관리자 RPC가 `admin_org_id()`의 조직 소속 부서인지 SQL에서 검증 |
| 조직 관리자는 내용 열람 불가 | 최상위 제목·카운트만. 하위 제목·본문 없음 |
| 마스킹 후 저장, 로그에 본문 금지 | 청크·제목·속성 모두 `mask()` 후 저장. 로그는 id·개수·코드 |
| 비밀값 | 토큰은 암호문만 DB에. OAuth client secret은 서버 환경 변수 |
| 미동의 발언 미저장 | 노션 문서는 발언자 단위로 거를 수 없으므로 **부서 단위 동의 게이트**로 집행한다(9/18 사용자 결정: 동의를 모두 받고 전부 수집). root 생성·발견·수집은 대상 부서의 `members.consented_at` null이 0명일 때만 진행하고, 미동의 멤버가 생기면 그 부서 root를 `paused_consent`로 멈춘다(이미 수집한 본문은 유지, 새 읽기 중단). 조건은 SQL RPC 안에서 검사한다. 댓글·사람 속성·작성자 정보는 수집하지 않는다. 동의 철회 시 이미 수집된 문서의 처리(부서장 제외 조치 외의 자동 삭제 여부)는 미정이다 |
| 교차 테넌트 | 전역 토큰 제거. 페이지 접근은 그 조직 설치 토큰으로만 |
