# 사수의 AI 개발 절차

사수는 명세·코드 맥락·구현·검증을 연결하는 개발 절차를 사용한다. Claude가 PRD·아키텍처·완료 기준을 구체화하고, Codex가 단계별 명세를 구현하며, 하네스가 결과와 오류를 다음 작업에 전달한다. Graft의 코드 의존 관계 탐색과 Archify의 구조·실행 흐름 시각화를 이 절차에 추가했다.

이 문서는 개발 방법을 정의한다. 제품 범위·완료 조건은 [PRD](PRD.md), 런타임 구조와 불변식은 [ARCHITECTURE](ARCHITECTURE.md), 결정 이유는 [ADR](ADR.md)을 따른다.

## 1. 역할과 연결 지점

| 구성 | 역할 | 연결 지점·산출물 |
|---|---|---|
| Claude·SDD | 문제를 기능 명세·제약·완료 기준으로 구체화 | PRD·ARCHITECTURE·ADR → `phases/*/step*.md` |
| Graft | 관련 함수·호출·의존 관계 탐색, 변경 영향 범위 확인 | 구현 전 코드 위치·관계 목록, 수정 후 영향 범위 |
| Archify | 구성 요소·실행 순서·데이터 이동을 시각화해 설계 검토 | 구조화된 다이어그램 명세 → HTML/SVG, 발표용 이미지 |
| CLAUDE.md·AGENTS.md·스킬 | 프로젝트 규칙과 작업별 구현·리뷰 기준 제공 | 에이전트 작업 지침 |
| Codex·하네스 | 단계별 구현, 이전 결과 전달, 실패 피드백과 재시도 | `scripts/execute.py`, step 상태·요약·오류 |
| 훅·Vitest·Playwright | 편집 규칙, 빌드, 기능·사용 흐름 확인 | 테스트·빌드 출력, 실제 검증 기록 |

Graft와 Archify는 개발 도구다. 서비스에서 안건을 분류하고 답변을 만드는 모델은 Groq의 gpt-oss이며, 근거 검색에는 Voyage 임베딩을 사용한다.

## 2. 단계별 작업 절차

1. **명세:** 사용 장면, 기대 결과, 수정 범위, 제약, 실행 가능한 완료 기준을 step에 적는다.
2. **맥락:** Graft로 관련 코드와 호출·의존 관계를 확인하고 실제 파일을 읽어 수정 범위를 정한다. 그래프가 현재 작업 트리를 반영하는지도 확인한다.
3. **구조 검토:** 여러 구성 요소의 경계나 데이터 흐름을 바꾸는 작업은 Archify로 구조와 실행 흐름을 표현한다. 사람이 결정하는 지점, 비동기 작업, 실패·재시도를 명시한다.
4. **구현:** Codex에 명세·규칙·관련 코드·앞선 step 요약을 제공한다. 적용 스킬과 훅을 유지하고, 실패 내용은 다음 수정 시도의 입력으로 사용한다.
5. **검증:** 바뀐 기능과 영향을 받는 기능을 테스트한다. 훅의 lint·build·test와 필요한 Playwright 사용 흐름 확인을 수행한다. 다이어그램의 형식·레이아웃 검사와 서비스 기능 검증은 각각 기록한다.
6. **기록:** 변경 파일, 코드 관계, 구조도 경로, 검증 명령·결과, 남은 문제를 완료 요약에 남긴다. 다음 step은 이 결과를 이어받는다.

도구를 실행하지 못한 경우 실제 파일·검색으로 확인한 범위와 누락된 도구 결과를 기록한다. 도구가 필요한 완료 기준을 충족하지 못하면 해당 step을 완료로 처리하지 않는다. 설치·인증이나 외부 전송이 필요한 상황은 기존 작업 범위와 권한 규칙을 따른다.

## 3. 하네스가 받는 맥락과 산출물

`scripts/execute.py`는 AGENTS.md와 `docs/` 최상위 Markdown을 매 step의 가드레일로 읽는다. 이 문서도 기존 경로로 전달된다. 완료 step 요약과 직전 오류를 함께 제공하며, Graft·Archify 결과는 에이전트가 작업 명세의 지시에 따라 만들고 아래 위치를 요약에 연결한다.

- 코드 맥락: 변경 대상 파일·함수, 호출자·의존 대상, 영향받는 기능.
- 구조 산출물: 작업별 `docs/verification/<task>/`에 저장한 다이어그램 명세·HTML/SVG 경로.
- 검증 근거: 실제 실행한 명령, 성공·실패 결과, 기능·사용 흐름 확인 자료.
- 완료 요약: 구현한 기능, 바뀐 구조, 산출물 경로, 다음 step이 알아야 할 결정.

실행기의 직접 자동화 범위는 step 실행·맥락 전달·오류 재시도·상태 기록이다. Graft·Archify 사용은 이 문서와 step 명세가 에이전트에게 지시하는 개발 절차이며, 실행기에 두 도구의 직접 호출 코드를 추가한 것은 아니다.

## 4. 심사자에게 보여주는 두 흐름

- **개발 흐름:** PRD·완료 기준 → 코드 관계 탐색·구조 검토 → 명세 기반 구현 → 훅·테스트 → 오류 수정 → 기능 완성.
- **서비스 흐름:** 슬랙·회의록 → 안건 분류·결정 카드 → 담당자의 결정 → 결정 원장 → 근거 답변·채용 예고편.

발표용 구조도는 각 단계의 역할과 최종 결과를 중심으로 구성한다. 작은 수집·처리 안내나 각주는 넣지 않는다.

| 사용자가 하는 일 | AI의 역할 | 사용자에게 남는 결과 |
|---|---|---|
| 슬랙에서 논의하거나 회의록을 남김 | gpt-oss로 안건 분류·카드 생성 | 근거와 추천 방향이 담긴 결정 카드 |
| 담당자가 안건을 결정함 | 판단에 필요한 근거 제시 | 결정과 이유가 남는 원장 |
| “이 견적 승인해도 돼?”라고 질문함 | Voyage 검색과 gpt-oss 답변 생성 연결 | 팀 기준·과거 기록·원문 링크가 담긴 답변 |
| 입사 전 업무를 체험함 | 결정 기록을 가상 업무 사례로 구성 | 채용 예고편 |
