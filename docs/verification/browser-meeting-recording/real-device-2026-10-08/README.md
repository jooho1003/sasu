# Phase 23 실기기 녹음 실측 (2026-10-05·10-08)

사용자가 USB 마이크(fifine)를 PC 스피커(Realtek) 앞에 두고 맡긴 실측이다. 사람이 말하는 대신 TTS 합성 음성을 스피커·Chrome 탭·시스템 소리로 틀고, **제품 녹음기 화면을 실제 Chrome으로 조작**해 녹음·저장·서버 검증·전사까지 진행했다. 공유 창(“탭 오디오와 함께 공유”, “시스템 오디오와 함께 공유”)도 실제 Chrome 공유 창을 UI Automation으로 눌렀다. 마이크·스피커·공유 창을 흉내 낸 부분은 없다(`--use-fake-ui-for-media-stream`은 권한 확인 창만 자동 허용한다).

## V20 정확률

20.7분(1,243초) TTS 대본, 156문장, 부서 용어 30종(171회 등장). 세 모드를 각각 실제로 녹음해 저장한 원본(21~22구간, 전부 서버 검증 `verified`)을 같은 파일 해시로 두 번 전사했다: 저장 직후(용어집 0건) → 팀장 API로 용어 30개 등록 → 제품의 “원본 다시 읽기”.

| 모드 | 입력 경로 | CER 전→후 | 용어 CER 전→후 | 오류 구간 / 전체 구간(후) | 낮은 신뢰 표시(후) |
|---|---|---:|---:|---:|---:|
| 마이크 | 스피커 → 실제 마이크 | 9.41% → 8.70% | 38.98% → 36.49% | 85 / 207 | 0 |
| 탭 | Chrome 탭 재생 + 탭 오디오 공유 + 마이크 | 8.70% → 8.44% | 38.20% → 34.47% | 77 / 202 | 0 |
| 시스템 | 외부 프로세스 재생 + 시스템 오디오 공유 + 마이크 | 10.14% → 10.18% | 45.19% → 37.42% | 85 / 199 | 1 (오류 구간) |

- 채점: NFC, 공백 제외·구두점 포함 문자 편집거리(`lib/recording/accuracy.ts`와 같은 규칙). 용어 인식값은 전사-대본 문자 정렬에서 해당 용어 위치에 대응한 전사 문자열. 구간 오류 라벨은 **규칙 기반 자동 라벨**(구간 정렬 범위에서 구두점이 아닌 문자 편집 1개 이상)이며 수작업 라벨이 아니다.
- 용어집 프롬프트: 제품 규칙(224바이트, 최근 수정순)상 30개 중 **22개만** 들어갔다. 빠진 8개(Supabase·pgvector·Vercel·Groq·Notion·Slack·RLS·OKR)가 가장 많이 틀린 영어 제품명이다(예: Supabase→슈퍼베이스, pgvector→푸드벡터, Vercel→버셀).
- 용어집에 든 용어는 개선됐다. 같은 part 6 창을 직접 비교하면 프롬프트 없이 “품위서” 2회 → 프롬프트 있으면 “품의서” 정확.
- 신뢰도: 문장 구간은 `normal` 또는 미지정뿐이었고 `low`(avg_logprob < −1.0 또는 no_speech_prob > 0.6)는 6회 전사 중 1구간뿐이었다. 현재 임계값은 이 오류들을 표시하지 못한다.
- 경계: 6자 이상 연속 삽입·누락은 모두 60초 전사 경계에서 6초 이상 떨어져 있어, 경계 중복·손실로 볼 사례는 없었다(문장 끝 어절 누락 3~4건은 Whisper 누락).
- 수집 건강: 세 모드 모두 저장 지연 정지 0회, 샘플-벽시계 최대 차이 0.29 s / 0.95 s / 2.99 s, 클리핑 0. 21분 동안 Chrome 전체 private 메모리 +79 MB / +44 MB / +102 MB(최대 707 MB).

## 발견한 결함

1. **긴 녹음 전사가 경계값 하나로 통째로 실패한다(차단).** 61초 전사 창의 마지막 단어 끝을 Whisper가 61.04초로 돌려주자 `finish_review_recording_part`가 `transcription_boundary_invalid`(≤61)로 거절했다. 같은 창은 다시 시도해도 같은 값이 나와 결정적으로 재현된다. 20.8분 마이크 녹음이 part 6에서 멈췄다. 로컬 수정: `projectTranscriptionWindow`의 `lastOwnedWordEnd`를 61초로 보정(`lib/recording/transcription-window.ts` 1줄, 회귀 테스트 1건). 수정 후 같은 녹음이 52초 만에 21구간 모두 완료됐다.
2. **위 실패가 `timeout`으로 보인다.** 마무리 RPC 예외 → job 재시도 → 첫 시도의 lease가 남아 `claim_review_part`가 null → job은 `done`, 구간은 `processing`으로 남음 → 2분 스윕이 `timeout`으로 덮어쓴다. 실제 원인이 기록되지 않고 다음 구간도 예약되지 않는다.
3. **문서 요약 병합 호출이 출력 한도에 걸려 요약 전체가 실패한다.** `llm.structured`가 `max_completion_tokens`를 정하지 않아 gpt-oss-120b의 기본 한도(추론 토큰 포함)를 쓴다. 21문장 회의(M1)의 병합 출력이 잘려 Groq 400 `json_validate_failed`("max completion tokens reached") → `schema_invalid`가 됐다(진단 실행에서 병합 호출이 원인임을 확인). 1차 측정에서 M1은 문서 단위 재시도 3회 모두 실패했고(5건 7회 시도 중 3회 실패), 2차 측정에서는 M2·M3가 한 번씩 실패 후 재시도로 통과했다(7회 중 2회 실패). 2차의 실패가 병합 호출이었는지는 따로 확인하지 않았다. 실패하면 이미 검증된 청크 추출까지 버린다. 구간이 수백 개인 실제 녹음은 더 위험하다.
4. **병합 호출의 측정 가능한 이득이 없었다.** 위 5건에서 결정·액션 후보가 병합 전과 같았다(결함 3과 함께 보면 비용·실패 위험만 더한다).
5. **낮은 신뢰 표시가 오류를 거의 잡지 못한다.** V20 오류 구간 77~85개 중 0~1개만 표시됐다.
6. **다른 창에 가려진 녹음 창은 부하 순간 멈출 수 있다.** 측정 중 두 번, 다른 Chrome 창에 가려진 녹음 창만 “이 기기가 소리를 제때 저장하지 못해 녹음이 중단됐습니다”로 자동 정지했다(16:15 지점: 같은 PC에서 Next 빌드가 전 코어를 쓰던 순간 / 0:19 지점: 새 Chrome 창이 뜨며 가린 순간). 같은 시각 전면 창 녹음은 지연 0회였다. 두 경우 모두 확인 구간까지만 보존·표시(“원래 기록 0:19 중 일부만 남았습니다”)하고 저장·전사는 정상이었다 — 조용한 손실은 없지만, 회의 앱이 브라우저를 가리는 실제 상황에서 녹음이 끊길 수 있다.
7. **겹침 경계에서 단어가 사라지고, 빈 창 하나가 자료 전체를 실패시킨다.** V05 강제 종료 녹음의 마지막 창(180~183초)에서 Whisper는 “핫픽스로 바로잡았습니다.”를 단어 시각 [0, 0.62]·[0.62, 1.72]로 돌려줬다. 앞 창이 기록한 마지막 단어 끝은 60.64초(→ 컷오프 0.64초)라, “바로잡았습니다.”는 앞 창에서는 60초 이후 시작이라 버려지고 마지막 창에서는 컷오프보다 0.02초 이르다고 버려졌다 — 두 창 모두에서 빠졌다. 마지막 창의 소유 문장이 0개가 되자 `empty_extraction`으로 그 창이 실패했고, 앞 3창이 정상인데도 자료 전체가 `failed`가 됐다(같은 창을 다시 전사해도 같은 결과, `v05-kill/probe-part3.json`). 녹음이 짧은 말 꼬리나 무음으로 끝나는 일은 흔하므로, 창 사이 시각 오차 허용과 “소유 문장 0개 창은 성공(빈 결과)” 처리가 필요하다.
8. **소프트웨어 마이크 비활성화는 녹음기가 알아차리지 못한다.** V03 마이크 분리 행 참고. 물리 분리 동작은 아직 모른다.
9. (하네스) 탭 공유 직후 Chrome이 공유된 탭으로 화면을 옮겨, 녹음기 탭이 뒤에 있으면 “녹음 시작”의 공유 창이 뜨지 않는다. 사용자는 녹음기 탭에서 누르므로 제품 결함은 아니지만, 5초 테스트 뒤 화면이 바뀌는 UX는 `CaptureController.setFocusBehavior` 검토 대상이다.

## 재현

하네스는 `tools/`에 복사해 두었다(원본 위치 `.vercel/real-device-20261005/`, gitignore). 로컬 QA 비밀값 파일(`env.json`)은 `make-env.mjs`로 다시 만든다.

1. 로컬 QA: Docker의 `review-qa` Supabase를 켜고, **메인 체크아웃 밖** worktree에서 `npm ci` → `node scripts/review-qa.mjs setup` → `build` → `start`(:3011). 메인 체크아웃 안의 worktree는 Next가 상위 lockfile을 루트로 잡아 메인의 미커밋 파일을 섞거나 빌드가 멈췄다.
2. 음향 경로: `tools/probe-acoustic.ps1`(ffmpeg dshow, 스피커 재생 중 마이크 수음).
3. 녹음: 세션 0에서 `tools/run-s1.ps1 -TaskName … -LogPath … -Minutes 50 tools/v20.mjs microphone|tab|system chrome`(대화형 세션에서 실제 Chrome 실행). V04는 `v04.mjs chrome`, V03·V05·V06은 `batch-devices.ps1`(V03 분리는 관리자 권한 필요).
4. 용어집 전후: `v20-reextract.mjs glossary-set` → 각 자료 `reextract <reviewId> <out>` → 결과는 `review_parts.sections`(재추출 후보, UI의 “재추출 검토”)를 구간 순서대로 모은 값 → `glossary-clear`.
5. 채점: `py -3 v20_eval.py <run> <sections.json> <mode> before|after <trial.json>` → `v20_abs_paths.py` → `v20_assemble.py` → `npx tsx scripts/measure-recording-accuracy.ts <input.json>`(원본 해시 재검증 후 `accuracy.md` 생성).
6. 결정 후보: `npx tsx scripts/measure-decision-merge.ts meetings.json <local-env.json> <out.json>`.

녹음 측정 중에는 같은 PC에서 빌드·`tsx`·`npm` 같은 무거운 작업을 돌리지 않고, Chrome 프로필은 시스템 SSD(C:)에 둔다(D:는 HDD).
