# 사수(SASU) 실사용 UI/UX 감사

> 후속 구현과 재검증 결과: [`../ux-improvement-2026-09-17/README.md`](../ux-improvement-2026-09-17/README.md)

- 일자: 2026-09-17 (Asia/Seoul)
- 방식: 실제 브라우저 조작 + 시드 팀장/조직 관리자 읽기 세션 + Playwright 완주
- 화면 폭: 1440×900, 390×844, 320×800
- 범위: 랜딩, 게스트 4개 부서, 결정 카드, 원장, 묻기, 로그인, 로그인 부서 8개 화면, 조직 관리자 4개 화면, 채용 예고편, 개인정보 안내, 오류 상태
- 비범위: Slack 실제 DM 송신, 파일 업로드, 운영 데이터 쓰기, 조직/멤버 변경

## 1. 한 줄 결론

시각 완성도와 기본 반응형은 좋고, 특히 공개 채용 예고편은 바로 시연 가능한 수준이다. 그러나 **제품의 핵심 약속인 근거 신뢰성**을 훼손하는 데모 데이터 2건과 **QA 데이터가 사용자 화면에 섞인 문제**가 있어, 지금 상태로 심사자가 사용하면 디자인보다 신뢰 문제가 먼저 보인다.

제출 전 최우선은 다음 세 가지다.

1. 잘못 연결된 충돌 결정과 무관한 인용을 고친다.
2. 데모/파일럿 조직에서 QA·E2E·중복 데이터를 완전히 분리한다.
3. 모바일 내비게이션과 긴 목록을 정리해 사용자가 핵심 기능을 찾게 한다.

## 2. 실제 완주한 유저 플로우

| 플로우 | 실제 경로 | 결과 | 핵심 관찰 |
|---|---|---|---|
| 심사위원 첫 방문 | `/` → `/demo` → 영업 사수 | 완주 | 첫인상과 CTA는 명료하지만 4개 부서 중 추천 시작점이 없다. |
| 영업 결정 확인 | 대시보드 → 외주사 B 카드 → 충돌 결정 → 원장 | 완주, 신뢰 실패 | 충돌 링크가 외주사 견적과 무관한 고객 인터뷰 결정으로 이동한다. |
| 부서별 답 비교 | 영업 묻기 → 개발 묻기 → 동일한 가격 질문 | 완주, 신뢰 실패 | 개발 부서의 “가격 기록 없음” 답변에 장애 대응 원칙이 인용된다. |
| 게스트 4개 부서 | 영업·개발·기획·디자인의 카드 → 원장 → 묻기 | 데스크톱/모바일 완주 | 기능 오류와 DB 쓰기는 없었지만 의미상 근거 오류는 자동 테스트가 잡지 못한다. |
| 팀원 묻기 | 질문 입력·음성 입력·내 질문 기록·Slack 질문 | 읽기 화면 확인 | 기록이 길고 중복/실패 항목이 섞여 최근 질문을 찾기 어렵다. |
| 팀장 일상 | 대시보드·원장·문서·자료 검토·역할·보존·세팅 | 1440/390 모두 렌더 | 실제 시드 데이터에서는 목록 길이와 QA 오염이 가장 큰 문제다. |
| 조직 관리자 | 개요·멤버·수집 채널·기록 | 읽기 전용 완주 | 데스크톱은 명료하나 모바일 표가 잘리고 이메일이 글자 단위로 줄바꿈된다. |
| 채용 예고편 | 가상화 검토 → 공개 오피스 → 단서 → 결정 → 회고 | 데스크톱/모바일 완주 | 가장 완성도가 높은 흐름이다. 목록형 모드와 로컬 저장 안내도 좋다. |
| 로그인 | 매직링크 화면 → 빈 입력 검증 | 확인 | 시각적으로 좋지만 초대/멤버십 전제와 실패 후 도움 경로가 약하다. |
| 개인정보/오류 | `/privacy`, 비활성·권한 없는 경로 | 확인 | 내용은 충실하지만 모바일에서 긴 문장 벽이며, 로그아웃 상태의 관리자 URL도 404라 원인을 알기 어렵다. |

## 3. P0 — 제출 전 반드시 수정

### UX-P0-01. “과거 결정과 충돌”이 무관한 결정으로 연결된다

- 재현: 영업 사수 → `외주사 B 12% 인상 견적을 받아들일까요?` → `9월 15일 결정과 충돌`.
- 실제 결과: `고객 인터뷰를 다음 주로 확정`이라는 원장 항목으로 이동한다.
- 영향: 사수가 허위 충돌을 만든 것처럼 보인다. 제품의 가장 중요한 신뢰 장치가 반대로 작동한다.
- 개선:
  - 외주사 가격/재입찰과 직접 관련된 과거 결정을 별도로 시드한다.
  - 카드에는 “어떤 문장이 왜 충돌하는지”를 1문장으로 표시한다.
  - 원장 이동 후 대상 결정을 하이라이트하고 카드로 돌아가는 링크를 제공한다.
- 완료 기준:
  - 카드의 안건, 충돌 설명, 대상 원장 결정이 같은 주제를 가리킨다.
  - 연결된 원장에는 결정 이유와 원문 근거가 보인다.
- 증거: [결정 카드](../../../outputs/ux-audit/guest-sales-card-1440.png), [연결된 원장](../../../outputs/ux-audit/guest-sales-conflict-ledger-1440.png)

### UX-P0-02. “근거 없음” 답변에 무관한 인용을 붙인다

- 재현: 개발 사수 → 묻기 → `가격을 올릴 때 기준이 있나요?`.
- 실제 결과: 답은 “개발 부서의 기록에는 가격 원칙이 없습니다.”인데, 인용은 “장애 대응은 원인 분석보다 먼저 영향 범위와 롤백 가능 여부를 확인합니다.”이다.
- 추가 사례:
  - 개발 사수의 고객 인터뷰 질문에도 스테이징 로그 문장이 인용된다.
  - 영업 사수의 외주사 답변은 12% 요청 인용 하나로 10% 재입찰 원칙까지 함께 말한다.
- 영향: 문자열 인용 검증은 통과하지만 사용자가 보는 의미는 근거와 맞지 않는다. “인용 없는 문장은 렌더하지 않는다”는 핵심 약속을 사실상 위반한다.
- 개선:
  - 근거가 없으면 `refused` 전용 UI를 사용하고 무관한 인용을 붙이지 않는다.
  - 한 답변이 12% 요청과 10% 원칙을 모두 말하면 두 근거를 각각 표시한다.
  - 데모 질문을 `이 부서 추천 질문`과 `같은 질문 비교`로 분리한다.
  - 자동 검증에 문자열 포함뿐 아니라 답변 주장과 인용 주제의 의미 일치 검사를 추가한다.
- 완료 기준:
  - 모든 준비된 질문에 대해 각 주장 옆에서 그 주장을 직접 뒷받침하는 인용을 확인할 수 있다.
  - 근거 없음 답변은 무관한 인용 0개이며, 가장 가까운 부서 질문을 제안한다.
- 증거: [개발 부서의 무관한 인용](../../../outputs/ux-audit/guest-dev-no-evidence-1440.png), [영업 외주사 답변](../../../outputs/ux-audit/guest-sales-ask-1440.png)

### UX-P0-03. 실제 사용자 화면에 QA/E2E 데이터가 대량 노출된다

- 실제 결과:
  - 팀장 대시보드에 `[QA-...]`, `[합성 QA 테스트...]`, UUID가 포함된 기록이 수십 건 보인다.
  - 질문 기록에 중복 질문, 실패, 근거 부족, 합성 검증 문구가 그대로 보인다.
  - 원장이 수십 개의 반복 결정으로 길어지고, 조직 관리자에는 `E2E-*` 부서가 남아 있다.
- 영향: 심사자는 정상 제품 상태가 아니라 내부 테스트 잔해를 본다. 중요한 카드와 결정이 묻히고 데이터 신뢰도도 떨어진다.
- 개선:
  - 쇼케이스 조직과 자동 테스트 조직을 물리적으로 분리한다.
  - E2E는 매 실행마다 전용 조직을 만들고 종료 시 정리하거나, 완전히 격리된 프로젝트를 사용한다.
  - 제출 직전 `QA-`, `E2E-`, UUID 본문, 중복 결정, 실패 답변을 점검하는 읽기 전용 감사 스크립트를 둔다.
  - 사용자 기본 화면은 최근/미결/내 담당 항목 중심으로 제한한다.
- 완료 기준:
  - 게스트·파일럿·관리자 화면에 QA/E2E 식별자가 0개다.
  - 첫 화면에서 핵심 카드와 최근 정상 기록만 보인다.
- 증거: [팀장 대시보드](../../../outputs/ux-audit/auth-dashboard-1440.png), [질문 기록](../../../outputs/ux-audit/auth-ask-1440.png), [원장](../../../outputs/ux-audit/auth-ledger-1440.png), [조직 개요](../../../outputs/ux-audit/admin-overview-1440.png)

### UX-P0-04. 제출 기능 플래그가 빌드 시점과 런타임에서 다르게 보일 수 있다

- 현재 기본 실행에서는 `/demo/admin`, `/trailers`, 게스트의 관리자/예고편 진입 링크가 404 또는 미노출이다.
- 읽기 전용 플래그로 별도 서버를 켜면 관리자 본 화면과 부서 예고편은 렌더되지만, 이미 빌드된 정적 `/demo`에는 링크가 나타나지 않았다.
- 영향: 로컬에서는 기능이 있다고 판단해도 제출 배포에서는 심사 동선에서 발견되지 않을 수 있다.
- 개선:
  - 제출 빌드 환경에서 기능 플래그를 명시한 뒤 다시 빌드한다.
  - 배포 URL 기준으로 `/demo`의 두 링크와 대상 화면 200 응답을 체크한다.
  - 꺼진 기능은 404 대신 내부 운영자에게만 보이는 배포 체크에 명시한다.
- 완료 기준:
  - 제출 URL의 `/demo`에서 `조직 단위로 보기`와 `채용 예고편 만드는 과정`이 계획대로 노출된다.
  - 링크 대상이 모두 200이고 모바일에서도 접근된다.

## 4. P1 — 핵심 흐름 개선

### UX-P1-01. 게스트 30초 흐름이 사이드바 탐색에 의존한다

- 카드 상세 하단에는 다음 단계인 원장/묻기보다 로그인·다른 부서 CTA가 먼저 보인다.
- 개선: `1 결정 발견 → 2 근거 확인 → 3 과거 결정 → 4 같은 질문 비교` 진행 표시와 다음 버튼을 화면마다 고정한다.

### UX-P1-02. 랜딩의 “같은 질문, 다른 부서 답” 약속을 바로 체험하기 어렵다

- 현재는 사용자가 부서를 다시 선택하고, 긴 질문 목록에서 같은 질문을 다시 찾아야 한다.
- 개선: 답변 화면에 `개발 사수에게도 같은 질문` 버튼을 두고 질문을 유지한 채 부서만 전환한다. 가능하면 영업/개발 답을 나란히 비교한다.

### UX-P1-03. 부서 선택에 추천 시작점이 없다

- 4개 카드가 동일한 우선순위로 보여 처음 온 심사자가 망설인다.
- 개선: 영업 카드를 `추천 · 90초 핵심 데모`로 강조하고, 나머지는 `다른 사례`로 묶는다.

### UX-P1-04. 결정 카드의 핵심 메타데이터가 본문에 묻힌다

- 마감 `오늘 17시`, 담당 권한, 출처 수가 구조화된 정보가 아니라 문장 속에 있다.
- 개선: 제목 위에 `마감`, `결정자`, `가시성`, `근거 수`, `상태`를 스캔 가능한 칩/정의 목록으로 표시한다.

### UX-P1-05. 원장과 질문 기록이 전부 펼쳐져 끝없이 길어진다

- 데스크톱과 모바일 모두 검색, 기간, 상태, 담당자, 페이지 단위가 없다.
- 개선:
  - 기본 10건, `미결/결정/반려`, 담당자, 기간 필터를 제공한다.
  - 원장은 제목·상태·날짜만 보이는 압축 행을 기본으로 하고 상세를 펼친다.
  - 질문 기록은 최근 5건만 보이고 `전체 기록`에서 검색/상태 필터를 제공한다.

### UX-P1-06. 모바일 부서 메뉴에서 뒤쪽 기능을 발견하기 어렵다

- 390px에서는 `문서`, `역할`, `기록 보존`, `세팅`이 화면 밖이다.
- 세팅 화면에서도 현재 메뉴가 보이지 않고, 320px에서는 네이티브 가로 스크롤바가 노출된다.
- 개선: 핵심 4개 + `더보기` 구조 또는 모바일 전용 메뉴를 사용하고 현재 화면은 항상 보이게 한다.
- 증거: [390px 세팅](../../../outputs/ux-audit/auth-settings-390.png), [320px 게스트](../../../outputs/ux-audit/guest-sales-dashboard-320.png)

### UX-P1-07. 모바일 관리자 표가 주요 정보를 숨긴다

- 멤버 이메일이 글자 단위로 줄바꿈되고, 동의·Slack 상태가 오른쪽 화면 밖에 있다.
- 개선: 640px 이하에서는 표를 카드 목록으로 전환하고 `이름/부서/역할/동의/Slack`을 두 줄로 표시한다. 가로 스크롤을 유지한다면 안내를 표 위에 둔다.
- 증거: [모바일 관리자 멤버](../../../outputs/ux-audit/admin-members-390.png), [모바일 조직 개요](../../../outputs/ux-audit/admin-overview-390.png)

### UX-P1-08. `역할`이라는 메뉴명이 실제 기능을 설명하지 못한다

- 사용자는 사람/권한 관리를 예상하지만 실제로는 문서 기준표 평가와 서류 점수표다.
- 개선: `문서 평가 역할`, `평가 기준`, 또는 상위 메뉴 `자동화` 아래 `문서 평가`로 이름을 바꾼다.

### UX-P1-09. 기록 보존 화면이 운영 용어와 긴 문장 중심이다

- `미확인·다른 정책`, `누락 구간 확인 전`, `첨부 실물 미포함` 등이 한 블록에 이어진다.
- 날짜 입력도 한국어 UI에서 `yyyy-mm-dd`로 보인다.
- 개선: `1 Slack 정책 확인 → 2 채널 상태 확인 → 3 내보내기 → 4 백업 확인` 단계로 나누고, 상태를 정상/확인 필요/차단으로 표시한다. 날짜는 `2026. 9. 17.` 예시를 사용한다.
- 증거: [모바일 기록 보존](../../../outputs/ux-audit/auth-retention-390.png)

### UX-P1-10. 세팅에서 “무엇이 연결을 막는지”가 한눈에 안 보인다

- 상단은 2/3명 동의라고 보여주지만, 어떤 사람의 Slack 매핑/동의가 차단 원인인지 아래까지 읽어야 한다.
- 개선: 상단에 `설정 완료 3/4` 체크리스트와 `차단: 이주호 동의, 2명 Slack 연결`을 표시한다. 미매핑 사용자만 모아 일괄 저장한다.

### UX-P1-11. 문서 요약에서 섹션 간 내용이 중복된다

- `핵심 내용`과 `결정·정책`에 같은 결론 문장이 반복된다.
- 개선: 분류별 중복 제거 후 비어 있는 섹션은 숨기고, 각 문장 옆에 근거 번호를 붙인다.
- 증거: [문서 어시스턴트](../../../outputs/ux-audit/auth-documents-1440.png)

### UX-P1-12. 자료 검토 업로드의 완료 조건이 버튼 근처에 요약되지 않는다

- 파일, 제목, 참여자, 전체 동의 확인이 모두 필요하지만 비활성 버튼만 보고 다음 행동을 빠르게 알기 어렵다.
- 개선: 버튼 위에 `파일 선택 / 참여자 선택 / 동의 확인` 3단계 체크 상태와 미완료 이유를 표시한다.
- 증거: [음성·자료 검토](../../../outputs/ux-audit/auth-reviews-390.png)

### UX-P1-13. 채용 예고편 “만드는 과정”의 가상화본이 한 덩어리다

- 12개 승인 항목이 같은 회색 박스 계층으로 이어지고, 접근성 트리에서는 긴 텍스트 한 덩어리로 읽힌다.
- 개선: `상황`, `제약`, `질문`, `선택지`, `팀의 결정`으로 그룹화하고 승인 상태/원문 대응을 행 단위로 제공한다. 왼쪽의 큰 빈 공간도 활용한다.
- 증거: [채용 예고편 검토](../../../outputs/ux-audit/demo-trailer-1440.png)

### UX-P1-14. 로그아웃된 관리자 북마크가 로그인 대신 404를 보여준다

- 비로그인 `/admin`은 “주소가 바뀌었거나 권한이 없다”는 404다.
- 개선: 비로그인은 `next=/admin` 로그인으로 보내고, 로그인했지만 조직 관리자가 아니면 권한 안내 화면을 보여준다. 실제로 존재하지 않는 경로만 404로 둔다.

## 5. P2 — 완성도와 접근성 개선

1. 모바일 랜딩 메뉴가 열린 뒤에도 접근 가능한 이름이 `메뉴 열기`로 남는다. `메뉴 닫기`로 바꾼다.
2. 준비된 범용 답은 실제 실시간 답처럼 보일 수 있다. `범용 AI 답변 예시 · 사전 작성`으로 명확히 표시한다.
3. 개인정보 안내는 모바일에서 긴 문장 벽이다. 상단 요약, 목차, 핵심 권리, 문의 CTA를 먼저 둔다.
4. 문서 모바일 화면은 목록과 상세가 한 페이지에 이어져 매우 길다. 문서 선택 후 목록을 접거나 `문서 목록으로` 버튼을 둔다.
5. 모바일 질문 카드 가로 목록은 다음 항목 일부만 보여 스와이프 가능성을 추측해야 한다. `1/6`, 스크롤 스냅, 이전/다음 버튼을 제공한다.
6. 원문 근거의 `원문 확인`에 소스 종류·시각·작성자를 함께 표시한다.
7. 작은 회색 메타데이터가 긴 화면에서 약하게 보인다. 핵심 상태와 보조 설명의 대비·크기 차이를 더 크게 한다.
8. 채용 예고편 완료 화면에서 제품 전환 CTA가 작다. 공고 URL이 있으면 `공고 보기/지원하기`, 없으면 `사수 데모 보기`를 주 CTA로 둔다.
9. 로그인 화면에 `초대받은 이메일로 로그인하세요`, 메일 미수신 해결, 멤버십이 없을 때의 도움 경로를 추가한다.
10. 부서 선택/관리자 표의 가로 스크롤 안내는 표 아래가 아니라 표 위에 둔다.

## 6. 유지해야 할 좋은 점

- 랜딩의 메시지, 데모 CTA, 합성 데이터 고지가 명확하다.
- 데스크톱/390px 게스트 대시보드와 카드의 시각 위계가 안정적이다.
- 공개 채용 예고편은 입장 → 탐색 → 단서 → 결정 → 회고가 자연스럽다.
- 채용 예고편의 목록형 모드, 키보드/방향키 안내, 로컬 전용 저장 고지가 좋다.
- 로그인 화면은 간결하고 매직링크 기대를 잘 설명한다.
- 문서 어시스턴트는 문서 선택, 요약, 원문 근거, ASK/역할 연결이 한 흐름에 있다.
- 관리자 화면은 “관리자는 부서 내용을 볼 수 없음”을 상단에서 명확히 고지한다.
- 게스트 4개 부서는 읽기 동안 POST/DB/LLM 증가 없이 완주했다.

## 7. 권장 재설계 유저 플로우

### 게스트 핵심 데모

`랜딩` → `추천: 영업 사수 90초 체험` → `결정 카드(마감·담당·근거)` → `정확히 연결된 과거 결정` → `같은 질문을 영업/개발에 비교` → `우리 팀에 적용하기`

화면 상단에 `1/4~4/4` 진행을 유지하고, 각 단계에는 다음 행동 하나만 강하게 둔다.

### 팀장 일상

`오늘 미결 3건` → `내가 결정할 카드` → `근거/충돌 확인` → `결정` → `원장 반영` → `질문자에게 전달`

분류된 원문 전체보다 “오늘 내가 해야 할 결정”이 먼저 보여야 한다.

### 첫 세팅

`동의 2/3` → `Slack 매핑 1/3` → `연결 가능한 채널` → `원칙/회의 자료` → `첫 수집 확인`

각 단계는 완료 조건, 막힌 사람/항목, 다음 버튼을 한 화면에서 보여준다.

### 조직 관리자

`이상 상태 요약` → `동의/연결 누락 부서` → `담당 부서장에게 이동` → `집계 확인`

조직 관리자는 데이터 열람보다 예외와 연결 상태를 빠르게 찾는 역할에 집중한다.

## 8. 권장 실행 순서

### 먼저 2~4시간

1. 데모 충돌 결정과 Q&A 인용을 수정한다.
2. 쇼케이스 조직의 QA/E2E 데이터를 정리하고 테스트 조직을 분리한다.
3. 제출 빌드의 기능 플래그와 `/demo` 링크를 검증한다.

### 다음 반나절

4. 게스트 4단계 진행 표시와 다음 CTA를 넣는다.
5. 모바일 `더보기` 내비게이션을 만든다.
6. 대시보드·질문·원장에 기본 10건 제한과 필터를 넣는다.

### 이후

7. 관리자 모바일 카드화, 기록 보존 단계화, 문서 중복 제거를 진행한다.
8. 접근성 이름, 모바일 스크롤 힌트, 개인정보 목차를 다듬는다.

## 9. 검증 기록

- `npx playwright test tests/e2e/ui-refresh.spec.ts --project=chromium` → 5/5 통과
- `npx playwright test tests/e2e/guest.spec.ts --project=chromium` → 4/4 통과
- 추가 읽기 전용 캡처 → 로그인 부서 8화면×2 viewport, 조직 관리자 4화면×2 viewport 통과
- 브라우저 콘솔 오류 0건. 개발 모드의 `scroll-behavior` 안내 경고만 확인
- 게스트 열람 전후 AI 호출·DB 행 증가 0건
- Graft/Archify는 실행하지 않음: 코드 구조나 실행 흐름을 변경하지 않은 읽기 전용 UX 감사였기 때문

자동 E2E가 통과한 것과 사용자 신뢰가 확보된 것은 별개다. 이번 감사에서 가장 중요한 발견은 **문자열 인용 검증을 통과한 의미상 오인용**과 **테스트 데이터 오염**이다.
