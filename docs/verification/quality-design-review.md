# 사수 품질·설계 검토

## 판단과 적용 범위

현재 MVP에서 우선 투자할 부분은 새로운 입력 기능보다 **권한 경계와 장애 후 복구**다. 정상 흐름의 단위 테스트는 통과하지만, 최초 정책은 부서 멤버에게 읽기와 쓰기를 함께 열어 두었고 일부 파생 데이터는 원본의 좁은 가시성을 유지하지 못했다. Slack 채널 질문도 질문자의 팀장 권한을 그대로 사용했다. 이는 모델 품질 문제가 아니라 애플리케이션과 DB의 경계 문제다.

이번 변경은 기존 PRD의 불변식을 구현하는 버그 수정이다. 새 기능이나 컷 라인을 확정하지 않는다. 다음 절의 설계 제안은 **미확정 검토안**이며, 채택 시 PRD §3·§8과 ADR을 먼저 갱신해야 한다. 조사 기준은 2026-09-12이고, 계정별 설정·운영 배포 상태는 공식 문서의 일반 설명과 구분한다.

마이그레이션은 `0012_answer_security.sql`과 `0013_authenticated_write_boundaries.sql`이다. 운영 DB에 적용한 것으로 간주하면 안 된다. 새 애플리케이션은 `complete_answer`에 의존하므로 **DB 적용 → 애플리케이션 배포 → 운영 회귀 검증** 순서가 필요하다. 기존 검색 RPC 시그니처를 보존해 DB부터 적용할 수 있게 했다.

## 권한 설계의 남은 검토

Supabase는 RLS를 브라우저부터 DB까지 적용하는 접근 통제 수단으로 설명한다. `USING`은 기존 행의 접근을, `WITH CHECK`는 쓰인 행의 조건을 제한하며 둘은 대체 관계가 아니다. SECURITY DEFINER 함수는 소유자 권한으로 실행되므로 호출자 검증·실행 권한 제한을 함께 설계해야 한다.[^1][^2]

이에 따른 설계 판단은 **읽기 권한에서 수정 권한을 유도하지 않는 것**이다. 이번에는 역할 승격, 답변 위조, 원장 수정, 소스 설정을 우선 보완했다. 아직 `items`, `classifications`, `decision_requests`, `citations` 등의 최초 `FOR ALL` 정책에는 화면에서 제공하지 않는 직접 쓰기 경로가 남아 있다. 입력 어댑터와 워커의 쓰기, 사용자의 명시적 업무 행동을 명령별로 분리하는 후속 검토가 필요하다. 카드 담당자 변경·원본 본문 조작·인용 삽입에 대한 부정 테스트를 다음 권한 검증의 필수 항목으로 권고한다.

카드에 연결된 원장 항목의 가시성은 이번에 보완했지만 **직접 기록한 결정이 비공개 item을 인용하는 경우**는 별도 가시성 설계가 필요하다. 현재 직접 기록은 `request_id=null`이므로 기본 `dept`로 취급한다. 권고안은 결정 생성 시 인용을 포함한 단일 SQL 명령에서 visibility를 산출·고정하는 것이다. 기존 카드 경로와 직접 기록 경로를 같은 트랜잭션 규칙으로 합치면, 결정은 저장됐지만 인용·카드 상태는 반영되지 않은 부분 실패도 함께 다룰 수 있다.

완료 기준은 API 상태 코드만이 아니다. 같은 고정 fixture를 anon·member·lead·다른 부서 JWT로 읽고, 역할 위조·다른 사용자 ID·비공개 원본·수정·삭제를 직접 시도한 SQL 결과가 있어야 한다. 이번 격리 검증은 역할과 `auth.uid()`를 재현하지만 Supabase Auth·PostgREST 전체 동작을 대체하지 않는다.

## Slack 이벤트 수신과 재시도

Slack은 이벤트를 3초 안에 승인하도록 요구하고 실패 시 재전송한다. 이벤트에는 전역적으로 고유한 `event_id`가 포함된다. 따라서 ACK와 중복 방지는 처리 완료와 구분해서 설계해야 한다.[^3]

현재 `app/api/slack/events/route.ts`는 먼저 `ingest_events`에 event_id를 기록하고, 그 뒤 소스·멤버 조회, item/answer 저장, enqueue를 실행한다. 중간 DB 오류가 나도 event_id는 남는다. 재전송은 unique 충돌만 보고 200을 반환하므로, item이나 job이 없는 입력을 영구적으로 누락시킬 수 있다. 반대로 event_id를 무조건 지우는 보정은 동시 재전송과 부분 성공에서 중복을 만들 수 있어 충분한 해결책이 아니다.

권고안은 검증·동의 확인·마스킹 후 **수신 완료 기록 + 업무 row + job**을 하나의 DB 트랜잭션으로 기록하는 것이다. 원문 이벤트를 durable inbox에 저장하는 일반 패턴은 이 프로젝트의 미동의·마스킹 전 원문 저장 금지와 충돌하므로 그대로 도입하면 안 된다. inbox를 채택한다면 허용된 식별자와 이미 마스킹한 payload만 저장하고, 수집 제외 이벤트는 본문 없는 처리 결과만 남겨야 한다.

완료 검증은 저장 단계별 실패 주입, 같은 event_id 동시 제출, 실패 뒤 재전송, 미동의 화자 저장 0건을 포함해야 한다. p95 수신 응답 시간도 별도로 측정해야 한다. 기존 정상 세로 슬라이스의 성공은 이 장애 경로를 입증하지 않는다.

## 워커의 중단·복구·기한

PostgreSQL의 `FOR UPDATE SKIP LOCKED`는 여러 소비자가 같은 큐 행을 두고 기다리지 않도록 하는 데 적합하다. 그러나 이는 claim 시점의 잠금 처리이며, 외부 작업을 실행하다 프로세스가 사라진 경우를 복구하는 임대 계약은 아니다.[^4] Next.js `after()` 역시 해당 라우트의 기본 또는 설정된 최대 실행 시간 안에서 동작한다.[^5]

현재 `claim_jobs()`는 queued만 가져오고, 한번 running으로 바뀐 작업을 회수하는 로직은 없다. 또한 sweep 핸들러는 등록되어 있으나 정기 트리거가 sweep job을 반드시 만들어 실행한다는 배선은 확인되지 않았다. 실패 처리 규칙이 존재하는 것과 그 규칙이 주기적으로 실행되는 것은 다르다. `runOnce()`가 여러 종류의 job을 claim하는데 요청별 핸들러 등록 목록이 다르다는 점도 검토 대상이다. 등록되지 않은 kind는 현재 `unknown_kind`로 실패한다.

권고안은 jobs에 `lease_expires_at`와 실행 소유 토큰을 두고, 만료된 running job만 회수하는 것이다. 완료·재시도 갱신에도 소유 토큰을 요구해야 이전 실행의 늦은 결과가 새 실행을 덮지 않는다. 모든 핸들러 등록은 워커 진입점 하나로 모으고, sweep은 요청 유입량과 무관하게 매분 실행되도록 해야 한다. 이 과정에서도 모델 호출과 Slack 전송의 재실행 가능성을 개별적으로 점검해야 한다.

수신→대기→생성의 전체 기한 2분과 3회 백오프는 함께 계산해야 한다. 문서 재가져오기에는 `created_at` 대신 이번 처리의 시작 시각이 필요할 수 있다. 테스트는 worker 강제 종료, 만료 회수, 늦은 완료, 중복 외부 전송, 2분 뒤 UI 종료를 포함해야 한다. 큐 제품 교체 없이 현재 Postgres 구조에서 보완할 수 있다.

## 근거 기반 답변 품질

인용 quote가 원문에 존재한다는 검사는 출처의 실재성을 확인하지만, 답변의 각 문장이 그 quote에서 도출되는지는 확인하지 않는다. 현재 `verifyAnswerCitations()`는 틀린 인용을 제거한 뒤 하나만 남아도 원래 답변 본문을 유지한다. 따라서 일부 근거가 잘못되어 제거된 경우, 그 근거에 의존한 문장은 그대로 남을 수 있다. 카드의 자유 서술도 같은 관점에서 점검해야 한다.

PRD가 LLM 심판을 컷한 상태이므로 바로 두 번째 모델을 추가하는 것은 권고하지 않는다. 단기 대안은 인용 중 하나라도 실패한 draft 전체를 1회 재생성하고 다시 실패하면 refused/needs_review로 닫는 것이다. 중기 대안은 `claims[{text,citation_ids}]`로 문장과 인용을 연결해, 검증되지 않은 claim만 렌더에서 제외하는 것이다. 둘 다 답변률과 안전성 사이의 선택이므로 PRD와 ADR에 결정 이유를 남겨야 한다.

검색 품질에는 별도 평가셋이 필요하다. 현재 원장 검색은 의미 유사도가 아니라 최근 3건이며, 원칙 청크도 일반 item 상위 8건에서 밀릴 수 있다. PRD의 원칙·선례 검색 목표와 차이가 있다. 먼저 대표 질문 20개에 정답 원칙·결정 ID를 사람이 라벨링하고, 검색 recall과 최종 인용 정확도를 분리해 측정할 것을 권고한다. 모델 교체는 그 뒤 판단할 문제다.

pgvector 공식 문서는 근사 인덱스 검색에서 필터가 결과 수를 줄일 수 있고, 0.8.0 이후 iterative scan으로 추가 후보 탐색을 할 수 있음을 설명한다.[^6] 이 저장소는 이미 HNSW 인덱스를 만들지만 아키텍처 문서에는 순차 스캔으로 서술된 부분이 있다. 실제 확장 버전과 실행 계획을 먼저 확인한 뒤, 소규모 fixture의 정확 검색과 HNSW 검색을 비교해야 한다. 현재 규모에서 인덱스 교체가 필요하다는 결론은 아직 없다.

## 회의 봇과 외부 데이터 보존

Recall 공식 문서는 실시간 `transcript.data` 요청을 처리하기 전에 workspace verification secret으로 서명을 검증하도록 안내한다.[^7] 따라서 PRD의 서명 지원 여부는 구현 대상 API 버전을 지정해 정리할 수 있다. 다만 문서상 지원과 실제 계정에서 봇이 입장해 동의된 화자만 수집하는지는 별개의 검증이다. 현재 리포에서 Recall 봇 수신·입장 경로의 실행 증거를 확인하지 못했으므로, 9/13 판정일까지 실제 회의 1건을 완주하지 못하면 PRD에 정한 전사 업로드 대안을 유지하는 것이 적절하다.

Groq 공식 설명에서 학습 사용 여부와 데이터 보존은 별도 항목이다. 추론과 음성 전사에는 안정성·오남용 감시 목적의 최대 30일 보존이 가능하고, 조직의 Data Controls에서 ZDR 설정을 관리할 수 있다.[^8] 애플리케이션 DB에 음성을 저장하지 않는다는 구현 사실만으로 외부 공급자에도 보존되지 않는다고 표현하면 안 된다. 실제 Groq 조직 설정을 확인하고 제출서·동의문에 맞춰 기재해야 한다.

## 직접 확인해야 할 운영 항목

1. 새 DB 정책은 격리 검증 후 staging 또는 검증용 Supabase에 먼저 적용하고, JWT/RPC 권한 회귀 검증을 실행한다. 운영 반영은 DB 마이그레이션 후 앱 배포 순서다. 기존 운영에 수정이 적용된 것으로 보고하지 않는다.
2. 실제 Slack 채널 수신·DM 결정·스레드 공지를 확인할 테스트 채널과 수신자를 정한다. 이 검증은 실제 메시지가 나가므로 별도 실행 범위가 필요하다.
3. 9/13까지 Recall 계정으로 회의 1건 완주 가능 여부를 판정한다. 실패 시 `.vtt/.txt` 업로드로 제출 범위를 확정한다.
4. Groq 조직 Data Controls의 학습·보존·ZDR 설정과 파일럿 구성원의 수집 동의를 확인한다.
5. 참가 접수 여부와 기존 배포 문서에 기록된 Git 작성자 권한 문제의 해결 여부를 확인한다. Vercel CLI가 없는 환경에서는 `npm i -g vercel` 설치를 권장한다. 이후 환경 확인·배포·로그 조회를 명령으로 재현할 수 있다.
