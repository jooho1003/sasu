# sales-agent-design Planning Document

> **Summary**: 영업팀 고객 요청·견적 변경 검토를 부서 에이전트의 첫 합성 업무로 설계한다.
>
> **Status**: 설계 단계 · **원천**: [PRD AG-01·§8·§10 #28](../../PRD.md), [ADR-074](../../ADR.md)
>
> 이 문서는 PDCA 어댑터다. 범위·결정의 원천은 PRD와 ADR이며, 사례 수치·문구는 [합성 사례](../../planning/영업_에이전트_합성_사례.md)에 둔다.

## Executive Summary

| Perspective | Content |
|---|---|
| Problem | 고객 요청과 견적 변경이 여러 자료에 흩어져 있어 변경점·정책 충돌·미확인 조건을 사람이 다시 모아야 한다. |
| Solution | 합성 영업 사례 하나로 요청 → 근거 있는 검토안 → 팀장 승인 경계를 설계한다. |
| Function/UX Effect | 담당자는 비교표·충돌·질문·회신 초안을 한 작업에서 검토하고, 팀장은 가격·계약·발송을 판단한다. |
| Core Value | 고객에게 확정되지 않은 가격·일정을 약속하지 않으면서 검토 준비 시간을 줄일 가능성을 평가한다. |

## Context Anchor

| Key | Value |
|---|---|
| WHY | 고객 요청·견적·영업 원칙 사이의 차이를 근거와 함께 확인해야 한다. |
| WHO | 영업 담당자와 승인자인 영업팀장 |
| RISK | 초안 견적 또는 고객 희망을 승인된 조건으로 오인하거나, 볼 수 없는 정책을 누설할 수 있다. |
| SUCCESS | 합성 사례에서 네 결과물의 모든 사실·판단이 인용 가능하고, 미확인 조건은 질문으로 남으며, 외부 행동은 일어나지 않는다. |
| SCOPE | 합성 사례 → 작업·승인 동선 설계 → 예외/권한 검증 → 구현 전 실자료 확인 목록 |

## 1. Overview

PRD AG-01의 첫 사례를 영업팀 견적 변경 검토로 좁힌다. 사용자는 실제 자료 대신 합성 데이터를 만들어 자율적으로 설계하도록 했다. 현재 사람이 실제로 처리하는 순서와 영업 정책은 확인되지 않았으므로, 이 단계의 산출물은 설계와 합성 사례이며 제품 구현·실효성 입증이 아니다.

## 2. Scope

- 포함: 입력 자료 네 건, 사용자 지시문, 네 결과물 양식, 근거·권한·팀장 승인 경계, 실패/수정/재시도 동선, 구현 후보 모듈 목록, 설계 검증.
- 제외: 실제 고객 자료·정책 수집, 메일/Slack 고객 발송, 견적 자동 수정, 가격·계약 자동 승인, 기존 S8 점수표 변경, 코드·DB·데모 조직 시드·운영 반영.

## 3. Requirements

| ID | Requirement | Priority | Status |
|---|---|---|---|
| AG-35-01 | 선택한 자료와 지시문으로 영업 검토 작업을 시작하는 동선을 정의 | High | 설계 대상 |
| AG-35-02 | 변경 비교표·원칙 충돌·확인 질문·고객 회신 초안의 근거 형식을 정의 | High | 설계 대상 |
| AG-35-03 | 가격·계약·외부 발송에 팀장 승인, 변경 시 재승인 경계를 정의 | High | 설계 대상 |
| AG-35-04 | 자료 부족·권한 상실·인용 실패·취소·재시도 처리를 정의 | High | 설계 대상 |
| AG-35-05 | 합성 사례와 반례를 통해 설계가 PRD 불변식을 지키는지 확인 | High | 설계 대상 |

비기능: `can_see()` 단일 가시성, 세션/멤버십 기반 부서·요청자, service role의 요청 경로 사용 금지, 마스킹 후 저장, 유효 인용 없는 문장 차단, 게스트 무쓰기·LLM 0회를 구현 계약에 반영한다. 성능 목표는 실제 샘플과 기준선 없이 수치로 약속하지 않는다.

## 4. Success Criteria

- [ ] [합성 사례](../../planning/영업_에이전트_합성_사례.md)에 서로 다른 고객 희망·견적 초안·정책이 있고 기대 결과가 원문에 추적된다.
- [ ] 설계 문서에 사용자 지시, 결과 상태, 팀장 승인, 자료/권한 재검사, 실패/취소/재시도 계약이 있다.
- [ ] 네 결과물의 사실·판단에 근거가 있고, 승인되지 않은 가격·시작일·발송 완료를 단정하지 않는다.
- [ ] 기존 S8과의 경계 및 실제 정책·고객 자료 도입 전 확인 목록을 기록한다.
- [ ] PDCA 설계 대비 분석과 설계 완료 보고에 실행한 검증만 기록한다.

## 5. Risks and Mitigation

| Risk | Impact | Mitigation |
|---|---|---|
| 합성 정책을 실제 회사 원칙으로 오인 | High | 모든 입력·출력에 합성 표시, 실자료 전환 게이트 명시 |
| 고객 희망 가격을 승인 가격으로 표현 | High | 확정/초안/요청 구분, 팀장 승인과 인용 검증 |
| 여러 소스의 가시성 혼합 | High | `can_see()`를 통한 재조회, 가장 좁은 visibility, 미가시 소스 비공개 |
| 기존 S8 기능을 범용 에이전트처럼 재사용 | Medium | S8은 기준표 점수, AG-01은 요청별 검토안으로 별도 동선 |

## 6. Impact Analysis

이 phase는 문서와 합성 자료만 바꾸므로 런타임 소비자 영향은 없다. 후속 구현에서 영향 검토가 필요한 현 자원은 `items`·`sources`·`reviewed_materials`·`agent_roles`·`jobs`·`llm.structured()`·`can_see()`·`search_as()`·대시보드 내비게이션이다. 기존 계약을 변경하는 것으로 간주하지 않으며, 설계 §11의 후보 목록에서 각 소비자와 회귀 검증을 다시 확인한다.

## 7. Verification and Rollout

설계 검증은 합성 입력과 기대 결과의 인용 일치, 5개 실패·권한 반례, PRD/ADR와 설계의 계약 대조로 한다. 코드·DB 테스트와 운영 배포는 이 phase의 완료 증거가 아니다. 실제 팀장·정책·업무 자료를 확인한 뒤 구현 범위를 다시 승인받는다.
