# 사수 PRD 작성용 프롬프트 5종 (사수 버전)

> 원본 프롬프트(비법소스 조합 서비스용)의 구조는 그대로 두고, 대괄호 안의 서비스명·타깃·상황·유저스토리·핵심 흐름만 사수에 맞게 치환했습니다.
> 순서대로 실행하고, 산출물은 모두 `/docs/class`에 저장합니다.
>
> **치환 기준값** (5개 프롬프트 공통)
> - 서비스: **사수** — 회의·슬랙에서 놓친 결정을 담당자에게 밀어주고, 모든 결정을 근거와 함께 기록하는 회사의 결정 인프라 (AI 사수)
> - 주 타깃: 회의는 많고 문서화는 약한 **5~50인 팀의 팀장과 팀원**
> - 핵심 상황: **회의 후 결정을 전달받고 확인할 때**
> - 기존 문서: 기획서(사수 v2.1), MVP 3주 일정표, 원티드 제출 일정표, 제출서 초안 → 프로젝트 디렉토리 `/docs`

---

## 프롬프트 1 (시장조사요약서)

```
기존에 만든 기획서·일정표·제출서 초안은 프로젝트 디렉토리(/docs)에 있어. 먼저 읽고 시작해줘.

나는 [사수 — 회의·슬랙에서 놓친 결정을 담당자에게 밀어주고, 모든 결정을 근거와 함께 기록하는 AI 결정 인프라]를 운영합니다.
주 타깃은 [회의는 많고 문서화는 약한 5~50인 팀의 팀장과 팀원]입니다.

이 고객들이 [회의 후 결정을 전달받고 확인]할 때 겪는 불편함 5가지를 알려줘.
각 불편함마다 아래를 포함해줘.
1. 고객이 느끼는 불편
2. 지금은 어떻게 해결하고 있는지(현재 대안 — 예: 구두 전달, 슬랙 되묻기, 노션 회의록, 클로바노트 등)
3. 실제 고객이 할 법한 한 문장(인용 형식 — 팀장 시점과 팀원 시점을 섞어서)
4. 이 내용 중 직접 확인이 필요한 사실은 무엇인지

추측이거나 확인이 필요한 내용은 문장 끝에 "(확인 필요)"라고 표시해줘.
불편함 5가지 중 최소 1개는 "팀장이 회의 내용을 깜빡하고 전달하지 않아, 나중에 '말해주지 않았냐'는 말을 듣는 상황"을 반드시 포함해줘.

위의 답변을 시장조사요약서.md 로 정리해줘.
위치는 /docs/class
```

## 프롬프트 2 (시장조사 요약서를 표로 정리)

```
방금 작성한 /docs/class/시장조사요약서.md 의 AI 답을 가설 / 확인 사실 / 본인의 판단으로 나누어줘. 그리고 다음 표로 만들어줘.
AI의 답, 분류(가설, 확인 후보, 본인 판단 후보), 다음 행동

"다음 행동"은 실제로 실행 가능한 검증 방법으로 써줘 — 예: 파일럿 팀 인터뷰 질문 1개, 우리 팀 회의 녹음 3건에서 확인, 슬랙 되묻기 횟수 세기 등. 이번 주 안에 할 수 있는 것과 파일럿 기간(9/21~10/16)에 할 것을 구분해줘.

위의 답변을 시장조사_타겟페인.md 에 추가해줘.
위치는 /docs/class
```

## 프롬프트 3 (경쟁사/대체재 비교)

```
기존에 만든 기획서(/docs)의 §04 경쟁 지형 리서치 결과를 먼저 읽고 시작해줘.

[사수 — AI 결정 인프라]의 경쟁 대안을 분석해줘.
직접 경쟁사(회의 AI·조직 지식: Otter, Fathom, Granola, 클로바노트, 티로, 콜라보 / 엔터프라이즈 검색: Glean, 라이너 / 자동화 에이전트: Lindy)와 대체재(구두 전달, 슬랙 되묻기, 노션·구글독스 회의록, 카톡 단톡방, 사람 사수·팀장의 기억)를 모두 포함해줘.
표의 열은 이렇게 만들어줘.
- 경쟁 대안 / 주요 고객 / 가격대 / 강점 / 약점 / 내가 차별화할 지점

"내가 차별화할 지점"은 사수의 결정 레이어(지금 결정 큐 · 결정 원장 · 충돌 감지 · 권한 인지 Q&A) 기준으로 써줘. 회의록·요약 기능으로 차별화하려 하지 마 — 그 층은 커머디티로 취급해.

마지막에 [사수]가 선택받기 위한 포지셔닝 문장 5개도 제안해줘. ("회의록은 남들도 만든다, 사수는 결정을 만든다"는 기존 문장이라 제외하고 새로 5개)
최신 가격·리뷰 수처럼 변동되는 정보는 "(확인 필요)"로 표시해줘.

위의 내용을 경쟁사_비교분석.md 로 정리해줘.
위치는 /docs/class
```

## 프롬프트 4 (화면정의)

```
유저 스토리 10개를 다음 형식으로 써줘.
"[사수 사용자(팀장 또는 팀원)]으로서, 나는 [회의에 참석하지 않아도 결정 내용을 놓치지 않고 근거까지 확인하기] 위해 [결정이 필요한 안건이 슬랙 카드로 먼저 오고, 질문하면 발언자·시각을 인용해 답해주고, 내가 내린 결정을 직접 원장에 기록할 수 있기를] 원한다"

10개 중 팀장 시점 4개, 팀원 시점 4개, 관리자(권한·보안) 시점 2개로 나눠줘.
다음 장면은 반드시 유저 스토리에 포함해줘:
- 폰 원탭으로 회의 녹음을 시작하고 끝나면 자동 업로드되는 장면
- 담당자 슬랙에 '지금 결정 카드'가 도착하고 카드에서 바로 결정하는 장면
- 같은 질문에 팀장과 신입이 권한에 따라 다른 답을 받는 장면
- 새 결정이 과거 결정과 충돌한다고 사수가 지적하는 장면

이를 기반으로 화면정의.md 로 정리해줘. 각 화면마다 어떤 유저 스토리를 충족하는지 번호로 연결해줘.
위치는 /docs/class
```

## 프롬프트 5 (upgraded PRD)

```
방금 만든 [사수]의 시장조사 및 경쟁사 분석 등의 분석 결과인 다음 파일을 참고해서

/docs/class/시장조사요약서.md
/docs/class/경쟁사_비교분석.md
/docs/class/시장조사_타겟페인.md
/docs/class/화면정의.md
그리고 기존 기획서·MVP 3주 일정표(/docs)

나는 PRD를 작성하려고 해.

1. 문제: 타깃 고객의 핵심 불편 사항 (회의 후 결정이 전달되지 않고, 근거가 남지 않고, "말해주지 않았냐" 공방에 심판이 없는 문제)
2. 타깃: 회의는 많고 문서화는 약한 5~50인 팀 — 1차 에이전시·스타트업의 팀장과 팀원, 그리고 권한·보안을 관리하는 관리자
3. 가치: 경쟁사/대체재의 대안으로서 우리만의 해결책 — 회의록(커머디티)이 아니라 결정 레이어: 지금 결정 큐 · 결정 원장 · 충돌 감지 · 권한 인지 Q&A
4. 고객의 유저스토리를 직접 반영해서 화면정의로 수렴
5. 핵심 흐름: 고객 경험 5개를 단계별로 (관심 → 회의 녹음·슬랙 연결 → 지금 결정 카드 확인 → 결정 원장·근거 인용 조회 및 공유 → 내가 직접 결정을 기록하고 사수에게 질문)

다음 항목들을 추가로 구성할 거야.

1. 프로젝트 개요
2. 사용자 시나리오
3. 핵심 기능 목록
4. 기술 스택 (기획서 §08 기준: Next.js + Vercel, Supabase(RLS·pgvector), Whisper 계열 STT + 화자 등록 기반 diarization, Claude Opus 5 정리·답변 / Claude Haiku 4.5 검증·추출, 슬랙 연동)
5. 화면 구성
6. 상세 기능 명세
7. 디자인 가이드
8. 제약 사항 (3주 MVP 범위·컷 리스트, 녹음 고지·동의 등 법적 전제, 보안 설계, 감시 프레임 금지)

이 순서대로 하나씩 질문할 테니까
나와 대화를 통해 하나씩 정해줘.
각 항목을 정할 때마다 MVP 3주 일정표와 충돌하는 부분이 있으면 먼저 알려줘.
```

## 실행 순서 메모

1. 프롬프트 1 → 2 → 3 → 4 → 5 순서대로. 각 프롬프트 시작 전 `/docs`의 기존 문서를 읽게 하는 문장이 들어 있으니 그대로 두기.
2. 프롬프트 5는 대화형이라 한 번에 끝나지 않음 — 8개 항목을 하나씩 답하며 진행 (예상 1~2시간).
3. 산출물 5개(`시장조사요약서.md`, `시장조사_타겟페인.md`, `경쟁사_비교분석.md`, `화면정의.md`, 최종 PRD)는 모두 `/docs/class`에 두고, PRD 완성본은 기획서와 함께 제출서 부록으로 활용.
