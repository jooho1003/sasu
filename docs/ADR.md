# Architecture Decision Records — 사수 (SASU)

- 문서 버전: 1.2
- 작성일: 2026-09-08 (1.2: ADR-031 추가 · 1.1: ADR-028 추가, ADR-011·012·013·020 갱신)
- 지위: **파생 문서**. 여기 적힌 결정은 [PRD](PRD.md)에서 이미 확정된 것이고, 이 문서는 **결정의 이유와 포기한 것**을 한곳에 모은다. 결정을 바꾸려면 PRD를 고치고 여기에 ADR을 추가한다. **코드만 바꾸고 문서를 두지 않는다.**
- 출처: plan-forge Phase 2~5 (렌즈 5개 → Phase 4 삭감 → 외부 리뷰 2곳). 옛 `plan.md` §6 "기술 결정과 이유" 표를 이 문서가 흡수했다.
- 기록 순서는 결정 순서가 아니라 영향 범위 순이다.

## 철학

1. **12일 안에 데모 5장면이 돌지 않으면 아무것도 아니다.** 지금 비용이 들고 이득은 9/20 이후에 나오는 것은 만들지 않는다.
2. **권한은 SQL이 판정한다.** 애플리케이션·UI·슬랙은 그 결과를 보여줄 뿐이다.
3. **검토하지 않아서 없는 것과 검토한 끝에 뺀 것은 문서에선 똑같이 생겼다.** 그래서 뺀 것은 뺐다고 적는다 (부록).
4. **완료는 자기 채점이 아니라 실행 기록으로 판정한다.** 에이전트의 "완료했습니다"는 하한선이다.
5. **동의가 수집보다 먼저다.** RLS는 접근 통제이지 수집의 법적 근거가 아니다.

### ADR-001: 문서 우선순위를 고정하고 `docs/PRD.md`를 최상위로 둔다
**결정**: `docs/PRD.md`의 범위·완료 조건·컷 라인 → `docs/ARCHITECTURE.md`의 구조·불변식 → `docs/ADR.md`의 이유 → `setup-guide`·`submission-checklist`의 절차. 하위 문서가 상위 문서를 암묵적으로 바꾸지 않는다.
**이유**: 확정 계획(옛 `plan.md`)과 상세 명세(`prd.md`)가 두 파일이면 범위 변경을 어느 쪽에 적을지 매번 갈리고, 이미 기각된 안이 되살아난다. market-front 프로젝트(ADR-001 갱신)에서 같은 이유로 plan을 PRD에 흡수했고 잘 작동했다.
**트레이드오프**: PRD 한 문서가 무거워졌다(900줄 안팎). "계획 승인 이력"이라는 별도 축은 Git 로그와 PRD §12가 대신한다. plan.md의 내용은 Git 히스토리(`63b4134`)에 남는다.

### ADR-002: 컨셉은 v3 "부서별 결정 사수"
**결정**: v1(AI 팀원 평가)·v2.1(회의 중심 결정 인프라)을 폐기하고 v3로 간다. 결정 레이어(카드 → 원장 → 권한 인지 Q&A) + **부서 단위 격리**.
**이유**: 회의록·검색은 Otter·Fathom·티로·콜라보·Glean이 이미 하는 커머디티다. 조사한 경쟁사 어디에도 "결정 큐·결정 원장·충돌 감지"는 없고, 부서 격리는 "회사 전체를 아는 AI"(Lindy·Glean)와의 구조적 차이다.
**트레이드오프**: v1은 관리 대상이 AI라 서사가 역전됐고, v2.1은 채널 하나(회의)로는 "결정 시스템" 주장이 약했다. v3는 채널이 셋이라 12일 안에 범위가 빡빡하다 — ADR-025의 게이트로 감당한다.

### ADR-003: 입력 채널은 슬랙 + 온라인 회의 봇 + 노션 세 개
**결정**: 슬랙 상시 수신(+7일 백필), 회의 봇 전사, 노션 원칙 문서.
**이유**: 사용자 결정. 데모 장면 3("채널이 달라도 같은 결정 카드")은 채널 2개 이상이 있어야 성립한다. 슬랙만이면 장면 3이 불성립, 슬랙+노션이면 회의의 "보류 안건"이 없다.
**트레이드오프**: 외부 리뷰 두 곳 모두 "12일에 채널 3개는 비현실적"이라 판정했다. 범위 대신 판정 시점을 앞당기는 것(ADR-025)으로 대응한다.

### ADR-004: 노션은 1회 가져오기 + 수동 [다시 가져오기]
**결정**: 지정 페이지·하위 블록을 items로 가져온다. 폴링·웹훅·변경 감지는 만들지 않는다.
**이유**: 부서 원칙 문서는 데모 기간 안에 바뀌지 않는다. 폴링·변경 감지가 노션 연동 비용의 대부분이다.
**트레이드오프**: 원칙 문서가 바뀌면 lead가 직접 눌러야 한다. 기획서의 "노션 상시 관찰"은 로드맵으로 내려갔다.

### ADR-005: 회의는 Recall.ai 류 봇, D6(9/13) 판정 후 실패 시 전사 업로드
**결정**: 전사 업로드 파서(.vtt/.txt)를 **먼저** 만들고 봇을 붙인다. D6까지 봇 전사가 items로 들어오지 않으면 업로드로 확정한다.
**이유**: 봇은 Lindy·Otter와 같은 방식이라 "실현 가능성" 어필에 유리하고, 자체 STT 운영이 없다. 판정일을 박아 12일 리스크의 상한을 둔다.
**트레이드오프**: 자체 Meet 봇(+1주)·Whisper 자체 STT(운영 부담)·폰 녹음(v2.1 — 화자 식별 비용)을 포기했다. Codex 리뷰는 "처음부터 업로드만"을 권했으나, 사용자가 봇을 명시적으로 택했다. 업로드 우선 구현 + 판정일로 갈음.

### ADR-006: 첫 부서(파일럿 1호)는 우리 팀 자신
**결정**: 실데이터 파이프라인은 우리 팀 슬랙 채널에 건다. 가상 회사(온새미로)는 게스트 모드 합성 데이터로만 쓴다.
**이유**: 사용자 결정. 실데이터·동의가 가장 쉽고, 개발 중 분류를 실데이터로 테스트할 수 있다.
**트레이드오프**: 두 번째 파일럿 팀 섭외(9/12)가 실패하면 데모데이 서사가 "1팀 4주 실데이터 + 게스트 2부서"로 약해진다. 그때는 약해진 조건을 발표에서 숨기지 않는다.

### ADR-007: 프론트·API는 Next.js App Router + Vercel, 별도 백엔드 없음
**결정**: 대시보드·원장·Q&A·게스트 모드·슬랙 이벤트 수신을 전부 Route Handler로.
**이유**: 심사 기간(9/21~10/5) 안정 접속을 1인이 관리해야 한다. 서버가 하나면 관리 대상도 하나다.
**트레이드오프**: 함수 타임아웃·Cron 간격이 플랜에 묶인다(ADR-010). 슬랙 3초 규칙은 ADR-009로 푼다.

### ADR-008: DB·인증·벡터는 Supabase Postgres + pgvector + RLS + Auth 하나
**결정**: 별도 벡터 DB를 두지 않는다. 권한 판정은 SQL 함수 `can_see()` 하나에 두고 RLS 정책과 `search_as()`가 같은 함수를 호출한다.
**이유**: RLS가 곧 "권한 인지 답변"의 물리적 구현이다. 벡터 DB가 따로 있으면 권한 필터를 두 곳에서 관리하게 되고, 누락 한 줄이 유출이다.
**트레이드오프**: pgvector는 인덱스 없이 5만 건 이하에서만 ms 단위다(ARCHITECTURE §9). 행별 `can_see()` 호출은 대량 조회에서 느려질 수 있다 — 지금 규모에선 무시.

### ADR-009: 비동기는 Postgres `jobs` 테이블 + `/api/jobs/run` 워커, Edge Function 배제
**결정**: 요청 핸들러는 검증 → DB 쓰기 → `enqueue` → `after(runOnce)` → 응답. 워커는 `FOR UPDATE SKIP LOCKED`로 job을 집고 재시도·멱등·2분 스윕·`llm_calls` 기록을 한곳에서 한다.
**이유**: 아키텍처 렌즈 지적 — 서버리스에서 "200 보내고 계속 처리"는 저절로 되지 않는다. Supabase Edge Function은 런타임 2개를 1인이 관리하게 되고, 외부 큐 서비스는 의존성을 추가한다.
**트레이드오프**: 워커가 단일 레인이라 부서 10개부터 분당 처리량 한계. 지금 규모(하루 ~200 job)에선 여유.

### ADR-010: 매분 트리거는 Supabase `pg_cron`+`pg_net` (D3 확정)
> **확정 (2026-09-10 / D3)**: Vercel 팀 `wadelee1005-3954s-projects`의 플랜이 **Hobby**로 확인됐다(`billing.plan = "hobby"`). Vercel 공식 문서 *Usage & Pricing for Cron Jobs*의 플랜별 표에서 Hobby의 Minimum interval은 **"Once per day"**이고, 더 잦은 cron 표현은 *"배포 단계에서 실패"*한다고 명시돼 있다. 따라서 Vercel Cron은 후보에서 탈락하고 **Supabase `pg_cron` + `pg_net`**으로 확정한다. 구현은 `supabase/migrations/0004_worker_cron.sql`(스케줄·함수)과 `scripts/setup-worker-cron.ts`(시크릿 주입) 두 곳이다.
> 같은 문서의 함수 지속시간 표에서 Hobby의 `maxDuration`은 기본 300초·최대 300초다. `after()`의 별도 상한은 문서에 표기가 없어 함수 실행 시간에 묶이는 것으로 본다 — 300초를 상한으로 가정하고 설계한다.

**결정**: Supabase `pg_cron`이 매분 `public.run_jobs_tick()`을 돌리고, 이 함수가 `net.http_post`로 `/api/jobs/run`을 호출한다. 워커 코드는 트리거와 무관하게 동일하다. 트리거 호출은 `x-jobs-secret` 헤더로 인증한다.
**이유**: 외부 리뷰 지적 — Hobby 플랜은 Cron이 하루 1회일 수 있어 설계 기반이 미검증이었다. `pg_cron`은 무료 티어·외부 의존성 없음.
**트레이드오프**: cron-job.org 외부 핑(의존성 추가)·QStash(비용)를 포기. 시크릿이 `public.worker_config`에 평문으로 앉는다 — RLS를 켜고 정책을 만들지 않아 anon·authenticated는 전면 거부이고 service role만 읽는다. service role 키를 가진 쪽은 어차피 DB 전체를 읽으므로 노출면이 늘지 않는다. 판정 결과는 `setup-guide.md` §2에 기록한다.

### ADR-011: LLM 역할 분리 — 큰 모델 = 카드·답변·회의 정리 / 작은 모델 = 분류 / 규칙 = 정량 신호
> **갱신 (1.1)**: 모델이 Opus 5 / Haiku 4.5에서 Groq `openai/gpt-oss-120b` / `openai/gpt-oss-20b`로 바뀌었다 (ADR-028). 역할 분리 구조 자체는 그대로다.
**결정**: 물음표·2인칭 요청·마감 표현·"보류" 태그·12시간 무응답 질문은 규칙이 잡고, 규칙이 잡은 것만 작은 모델(gpt-oss-20b)에 보낸다. 카드·답변·회의 정리만 큰 모델(gpt-oss-120b).
**이유**: 비용·일관성. 정량 신호는 규칙이 더 정확하다. 전부 큰 모델이면 비용이 몇 배가 되고, 전부 작은 모델이면 카드 품질이 떨어진다.
**트레이드오프**: 규칙의 "결정 필요" 재현율(가설 #8, 작업 임계 0.7)에 카드 자동 생성이 묶인다. 미달 시 수동 승격 경로가 데모를 지킨다.

### ADR-012: 형식 제어는 structured output뿐, 필드 순서는 citations → 근거 → 결론
**결정**: `CardDraft`·`AnswerDraft`의 스키마에서 `citations[]`가 첫 필드. `background`/`reasoning`이 다음, `recommendation`/`answer`가 마지막.
**이유**: 프롬프트만으로 JSON을 요구하면 파싱 실패가 난다. 스키마로 강제하는 것이 유일하게 안정적인 형식 제어다.
> **갱신 (1.1)**: Groq 전환(ADR-028)으로 근거가 두 곳 바뀌었다. ① 원래 이유였던 "Opus 5는 budget_tokens·prefill이 안 된다"는 무효 — 대신 strict `json_schema`가 **모든 필드 required + `additionalProperties: false`**를 요구해 optional을 쓸 수 없고, null이 정상인 필드는 nullable union이 된다. ② **필드 순서는 더 이상 강제 수단이 아니다** — json_schema의 properties 순서는 생성 순서를 보장하지 않는다. 순서는 스키마·프롬프트 양쪽에 적되, 실제 방어는 인용 문자열 검증(ADR-013)이 전담한다.
**트레이드오프**: `stop_reason: refusal`이 없어 거절을 별도 신호로 못 받는다 — 스키마의 `refused` 필드와 인용 0개로 판정한다(`llm.ts`).

### ADR-013: 인용 검증은 문자열 포함 검증만, LLM 심판(2차) 없음
**결정**: `quote`가 원문에 포함되는지만 검사. 실패 인용 제거, 0개면 답변 `refused` / 카드 `needs_review`.
**이유**: Phase 4 삭감 — LLM 심판(2차)은 데모에서 차이가 보이지 않고 지연·비용만 추가한다.
> **갱신 (1.1)**: Groq 전환으로 필드 순서 강제가 약해졌으므로(ADR-012 갱신), 이 문자열 검증이 인용 정합성의 **유일한** 방어선이 되었다. 중요도가 올라갔을 뿐 결정은 그대로다.
**트레이드오프**: 원문에 있는 문장을 문맥과 다르게 인용하는 오류는 잡지 못한다. 파일럿 기간에 사례가 쌓이면 재검토.

### ADR-014: 가시성은 소스별 2단계(`dept`/`leads_only`), lead 수동 지정, 파생물은 가장 좁은 것 상속
**결정**: 프라이빗 슬랙 채널 기본 `leads_only`, 퍼블릭·노션 기본 `dept`. 카드·회의 정리·충돌 설명은 원본 중 최솟값을 상속하고 이후 좁아지는 변경 금지.
**이유**: 데모 장면 4("같은 질문, 다른 답")에 충분하다. 슬랙·노션 원본 권한 자동 상속은 커넥터마다 모델이 달라 12일 안에 불가.
**트레이드오프**: lead가 잘못 지정하면 유출. ACL 테이블·개인 범위는 부서 간 교차가 생길 때로 미룬다.

### ADR-015: 답변이 게시되는 곳의 권한이 질문자 권한보다 우선한다
**결정**: 퍼블릭 채널에서 `@사수`로 물으면 lead가 물었어도 member 권한으로 검색. lead 권한 답변은 웹 S4·슬랙 DM에서만. 결정 공지 스레드는 결과 한 줄 + 원장 링크만.
**이유**: 보안 렌즈 — lead가 채널에서 물으면 `leads_only` 내용이 채널 전원에게 샌다. 카드에는 `leads_only` 근거가 섞일 수 있어 스레드에 사유를 쓰면 같은 경로로 샌다.
**트레이드오프**: lead가 채널에서 "왜 이것밖에 안 나오지"를 겪는다. "N건 제외"를 표시하지 않으므로 UX로 설명할 수단이 없다 — 고정 문구로만 안내.

### ADR-016: 신원 매핑은 슬랙 이메일 ↔ auth 이메일 일치
**결정**: `users:read.email` 스코프로 세팅 시 자동 매핑. 매핑 없는 슬랙 사용자의 질문·버튼은 거절.
**이유**: 별도 연결 UI·슬랙 OAuth 로그인(설치 흐름 필요) 없이 된다.
**트레이드오프**: 스코프 승인 조건(가설 #15)에 묶인다. 안 되면 세팅에서 수동 매핑 표.

### ADR-017: 슬랙 앱은 단일 워크스페이스 수동 설치, 토큰은 env
**결정**: OAuth "Add to Slack"을 만들지 않는다. S5는 `conversations.list`로 채널 선택만.
**이유**: 파일럿 1팀. OAuth 설치는 멀티 워크스페이스에서만 필요하다.
**트레이드오프**: 파일럿 2팀째는 별도 배포 인스턴스. 워크스페이스 2개째부터 토큰 테이블이 필요하다(ARCHITECTURE §9).

### ADR-018: 임베딩 모델은 D2에 확정, 컬럼은 확정 후 마이그레이션
**결정**: 스키마 v1에 `embedding` 컬럼을 넣지 않는다. Voyage vs OpenAI를 우리 팀 메시지 20쌍으로 비교한 뒤 `vector(N)` + `embed_model` 마이그레이션.
**이유**: 외부 리뷰 지적 — `vector(1024)`를 박아두고 "미정"이라 하면 미정이 거짓이다.
**트레이드오프**: D2 하루가 모델 비교에 든다. 모델 교체 시 전량 재임베딩은 알고 감수(`embed_model`로 혼재만 막는다).

### ADR-019: 게스트 모드는 합성 데이터를 실제 파이프라인으로 돌린 스냅샷, 부서 2개
**결정**: 온새미로 주식회사 영업팀·개발팀의 3주치 합성 슬랙·회의·원칙 문서 → 실제 파이프라인 → DB 시드. Q&A는 사전 실행 6건(1건은 두 부서에 같은 질문) + 시드 시 저장한 범용 AI 답 `generic_answer`. 자유 질문은 막는다.
**이유**: 우리 팀 실데이터 노출 금지 + "모조 UI가 아님" + 심사 기간 API 비용·장애 차단. 부서 2개는 핵심 차별점 "부서 격리"를 데모에서 보여줄 유일한 방법(외부 리뷰 지적) — 비용은 데이터뿐.
**트레이드오프**: 합성 데이터 텍스트 작성이 D3~D5에 병행 부담. 실데이터 익명화(누출 위험)·하드코딩 목업(진정성)·부서 1개(격리 미시연)를 포기.

### ADR-020: API 키는 공동 키 1개, 비용 상한 $100
> **갱신 (1.1)**: 키가 `ANTHROPIC_API_KEY`에서 `GROQ_API_KEY`로 바뀌었다 (ADR-028). Groq 콘솔에 spend limit이 없으면 선불 크레딧 충전액이 상한 역할을 한다 `(확인 필요 — PRD §10 #19)`.
**결정**: 우리 팀 파일럿 + 게스트 모드가 키 하나를 쓴다. `llm_calls`로 측정하고 세팅 화면에 "이번 달 사용액"을 보인다. `/ask`는 사용자당 하루 50회.
**이유**: 사용자별 키는 과금 모델이 생길 때의 일이다. 게스트 모드는 사전 실행 스냅샷이라 $0.
**트레이드오프**: 키 하나가 새면 전부 샌다. Vercel env 외에는 두지 않는다.

### ADR-021: 동의가 수집보다 먼저, 미동의 멤버의 발언은 저장하지 않는다
**결정**: 세팅 체크리스트 0단계 = 멤버 동의 수집. 채널 멤버 전원 동의 후에만 채널 연결. 어댑터가 `author_ext_id`로 미동의 발언을 skip. 이름만 가리고 본문을 저장하는 방식은 폐기.
**이유**: Codex 리뷰 — "RLS는 접근 통제이지 수집의 법적 근거가 아니다." 근거는 동의다.
**트레이드오프**: 한 명이 동의하지 않으면 채널을 연결할 수 없다. 늦게 합류한 사람의 발언은 동의 전까지 비어 있다. 봇 참석 고지·퇴사자 이름 보존의 법적 요건은 대회 후 자문(가설 #5·#17).

### ADR-022: 삭제 정책은 "본문·임베딩 삭제 + 인용 quote 보존" 하나로 통일
**결정**: 채널 제거·슬랙 삭제 이벤트 시 `items.content`·`embedding` 하드 삭제 + `deleted_at`. 행과 `citations.quote`는 원장 근거로 남긴다. 동의문에 명시.
**이유**: Codex 리뷰 — 6-6(소프트)과 6-12(하드)가 불일치했다. 원장에 인용된 발언은 결정의 일부다.
**트레이드오프**: "완전 삭제" 요구에는 조직 단위 전량 삭제(파일럿 종료)로만 응한다.

### ADR-023: 결정은 append-only, 정정은 `supersedes_id`
**결정**: `decisions`는 생성만. 정정은 새 행 + `supersedes_id` + 사유. `decided_by`는 `on delete set null`, `decided_by_name` 스냅샷.
**이유**: 원장은 조직의 업무 기록이다. 탈퇴·삭제로 원장이 함께 지워지거나 삭제가 막히면 안 된다. 정정 UI는 나중이지만 스키마는 지금이 공짜다.
**트레이드오프**: 정정 이력이 목록에 쌓인다 — 최신 행만 기본 표시.

### ADR-024: `can_see()` 단일 판정, 요청 경로에서 service role 금지
**결정**: RLS 정책(USING + WITH CHECK)과 `search_as()`가 같은 SQL 함수를 호출한다. 사용자 요청 경로는 세션 클라이언트 또는 `search_as(user_id)`. service role은 어댑터·워커·시드 전용. `excluded_count` 2차 검색은 제거.
**이유**: 판정 로직이 두 곳이면 반드시 어긋난다. service role로 검색한 뒤 애플리케이션에서 필터링하면 누락 한 줄이 유출이다. `excluded_count`를 빼자 요청 경로에서 service role이 아예 사라져 보안이 단순해졌다.
**트레이드오프**: 감사 로그의 "권한 밖 제외 건수"를 잃었다. 화면이 없으니 지금은 무의미.

### ADR-025: D3 세로 슬라이스 게이트 + 고정 컷 라인 순서
**결정**: 9/10 자정까지 "실제 슬랙 메시지 → 분류 → 카드 → 웹 결정 → 원장"이 배포 URL에서 5분 안에 완주되지 않으면 즉시 강등(회의 업로드 전용·노션 텍스트 붙여넣기·키워드 검색). 그 뒤 컷 ①~⑦은 PRD §8-2 순서와 판정일로만 발동. 절대 안 버리는 것 다섯: 결정 카드 · 원장 · 권한별 답변 차이 · 근거 인용 · 게스트 모드.
**이유**: 외부 리뷰 공통 지적 — "컷 라인은 사후 손절이지 사전 리스크 분산이 아니다." 범위는 사용자 결정이라 유지하되 판정 시점을 앞당겼다. 축소를 그때그때 정하면 매번 다시 논의한다.
**트레이드오프**: 컷 ⑤(DM 버튼·모달)는 유저 플로우 렌즈의 이탈 방지 원칙을 되돌린다 — 발동 시 장면 3을 웹 카드로 촬영하고 매직링크 왕복 이탈을 감수한다.

### ADR-026: 완료는 실행 기록으로 판정한다
**결정**: PRD §11 검증표의 각 행을 실제로 돌린 기록(스크린샷·쿼리 결과·E2E 로그)이 있어야 완료다. Codex의 자기 보고는 신호가 아니다. D8 오후에 RLS·워커·서명 검증 코드를 사람이 직접 읽는다.
**이유**: AI 구현의 "완료했습니다"는 검증되지 않은 주장이다. 특히 RLS는 통과하는 것처럼 보이면서 WITH CHECK가 빠져 있기 쉽다.
**트레이드오프**: D8 오후 반나절이 검증에 든다. 그래서 버퍼로 잡았다.

### ADR-027: 구현은 Harness(`phases/` step + `scripts/execute.py`)로 Codex에 넘기고, TDD·위험 명령 훅을 건다
**결정**: market-front에서 검증된 실행기·훅·슬래시 커맨드를 복사해 sasu 구조에 맞췄다. `lib/` 모듈은 테스트 파일이 먼저 있어야 편집 가능. AGENTS.md와 CLAUDE.md는 같은 내용.
**이유**: 1인·기획 Claude·구현 Codex 체제에서 step 파일이 곧 지시서다. 가드레일(AGENTS.md + `docs/*.md`)이 매 step에 주입되어 세션이 바뀌어도 규칙이 유지된다. 훅은 "테스트 없이 구현"과 "되돌릴 수 없는 명령"을 기계적으로 막는다.
**트레이드오프**: step 파일 작성 비용. `docs/` 최상위 5개 문서가 매 프롬프트에 들어가 8만 자를 넘는다 — stdin으로 넘겨 Windows 명령줄 상한을 피한다.

### ADR-028: LLM 공급자를 Anthropic에서 Groq으로 전면 교체한다 (D1, 9/8)
**결정**: 카드·답변·회의 정리는 **`openai/gpt-oss-120b`**, 분류는 **`openai/gpt-oss-20b`**를 Groq에서 부른다. `ANTHROPIC_API_KEY`는 `GROQ_API_KEY`로 대체되고, `lib/llm.ts`는 Anthropic SDK가 아니라 Groq SDK(OpenAI 호환 Chat Completions)를 쓴다. 규칙 휴리스틱 1차 → LLM 2차라는 ADR-011의 역할 분리 구조와, `llm.ts` 단일 호출점이라는 불변식은 그대로다.
**이유**: 사용자가 확보한 키가 `GROQ_API_KEY` 하나다. 그 제약 안에서 모델을 고르면 선택지가 사실상 하나로 좁혀진다 — 인용 강제(ADR-012·013)가 strict `json_schema`에 걸려 있는데, Groq에서 strict를 지원하는 production 모델은 `openai/gpt-oss-120b`와 `openai/gpt-oss-20b` 둘뿐이다. `llama-3.3-70b-versatile`은 strict를 지원하지 않아 `citations[]` 스키마 강제가 성립하지 않고, `qwen/qwen3.8-27b`는 strict를 지원하나 preview(평가 전용)라 심사 기간 9/21~10/5 내내 살아 있어야 한다는 DoD와 충돌한다.
**트레이드오프**:
- **필드 순서 강제를 잃었다.** ADR-012의 "citations를 먼저 쓰게 한다"는 순차 생성에 기댄 장치였는데, json_schema의 properties 순서는 생성 순서를 보장하지 않는다. 인용 정합성의 방어선이 문자열 검증(ADR-013) 하나로 줄었다 — 그래서 ADR-013의 중요도를 올려 적었다.
- **`stop_reason: refusal`을 잃었다.** 거절을 프로토콜 수준에서 못 받고 본문으로 받는다. `AnswerDraft.refused`와 인용 0개로 판정한다.
- **optional 필드를 못 쓴다.** strict는 모든 필드 `required` + `additionalProperties: false`를 요구한다. `deadline_hint`·`assignee_hint`·`confidence`처럼 null이 정상인 필드는 nullable union으로 정의해야 하고, 이 제약이 `lib/contracts.ts`의 Zod 스키마 설계를 직접 규정한다.
- **한국어 생성 품질이 미검증이다.** Opus 5 기준으로 쓰인 카드·답변 품질 기대치가 그대로 성립하는지 모른다 — PRD §10 #21로 올려 D3 카드 생성 때 육안 판정한다.
- **단가를 모른다.** §8-5의 $100 상한을 재계산해야 한다 (PRD §10 #19).
- **임베딩은 별개 문제다.** Groq의 `nomic-embed-text-v1_5` 제공 여부가 공식 모델 목록에서 확인되지 않는다. 확인되면 키 하나로 끝나고, 아니면 Voyage/OpenAI 키가 따로 필요하다 — 어느 쪽이든 ADR-018(D2 확정 후 마이그레이션)은 그대로다.
- 되돌리는 비용은 낮다. `llm.ts`가 유일한 호출 지점이라 SDK 교체와 모델 상수 두 줄이면 원복된다. 그래서 프로바이더 추상화 계층은 만들지 않는다 — 지금 비용이 들고 이득은 없을지도 모르는 것은 만들지 않는다(철학 1).
**기각한 대안**: ① `llama-3.3-70b-versatile`(strict 미지원 → 인용 강제 불성립) ② `qwen/qwen3.8-27b`(preview → 심사 기간 가동 보장 없음) ③ 분류만 Groq + 생성은 Anthropic(키가 없다) ④ 개발 중 Groq → 제출 전 Anthropic 교체를 전제로 한 프로바이더 추상화(두 경로를 다 검증해야 해서 12일 안에 비용이 이득을 넘는다).

### ADR-029: 임베딩은 OpenAI `text-embedding-3-small` 1536차원으로 확정한다 (D2, 9/10)
**결정**: `OPENAI_API_KEY`로 OpenAI Embeddings API의 `text-embedding-3-small`을 호출하고, `items.embedding vector(1536)`와 `embed_model`을 저장한다. `search_as()`는 `can_see()`를 호출하며 현재 모델과 일치하는 행만 반환한다. 모델명은 `EMBEDDING_MODEL`로 고정 가능하되 차원이 다른 모델은 마이그레이션 없이 선택하지 않는다.
**이유**: MVP에서 한국어 짧은 발언·원칙 문서·Q&A 질문을 같은 벡터 공간으로 검색해야 하고, 별도 임베딩 공급자 키를 추가하지 않으면서 OpenAI의 안정적인 임베딩 엔드포인트를 사용할 수 있다. 데이터가 쌓인 뒤 모델을 바꾸더라도 `embed_model`로 혼합 검색을 막는다.
**트레이드오프**: 현재 환경에 `OPENAI_API_KEY`가 없으면 embed job은 `embedding_not_configured`로 재시도 후 실패하며 해당 항목은 검색에서 빠진다. 배포 전 Production/Preview 환경에 키를 넣고 첫 파일럿 데이터의 임베딩 상태를 확인해야 한다. Voyage 비교 실험은 MVP 마감 뒤로 미룬다.

### ADR-030: 임베딩은 Voyage AI `voyage-4-lite` 1024차원으로 재확정한다 (D2 갱신, 9/10)
**결정**: `EMBEDDING_PROVIDER=voyage`를 기본으로 하고 `VOYAGE_API_KEY`로 Voyage Embeddings API의 `voyage-4-lite`를 호출한다. 검색 문서는 `input_type=document`, 질문은 `input_type=query`로 구분한다. `items.embedding`은 `vector(1024)`로 재생성하고, `search_as()`는 `embed_model = 'voyage-4-lite'`인 행만 반환한다. `EMBEDDING_PROVIDER=openai`를 선택하면 기존 OpenAI `text-embedding-3-small` 호환 경로를 유지한다.

**이유**: Voyage의 최신 경량 범용 모델을 사용하면 한국어 부서 기록 검색에 맞는 다국어 임베딩과 query/document 검색 지시를 사용할 수 있고, MVP의 비용·지연을 낮출 수 있다. 기본 차원이 OpenAI 경로와 달라 스키마를 억지로 혼합하지 않고 D2 마이그레이션으로 명시적으로 전환한다.

**트레이드오프**: 기존 1536차원 임베딩은 재사용할 수 없어 실데이터를 전량 재임베딩해야 한다. 마이그레이션은 기존 벡터를 비우고 `embed` job을 다시 만든다. Voyage 키가 없으면 job은 `embedding_not_configured`로 실패하므로 Vercel Production/Preview와 로컬 환경에 키를 넣어야 한다. OpenAI 호환 경로는 남겨 두지만 두 provider의 벡터를 한 검색 공간에 섞지 않는다.

### ADR-031: 슬랙 최소 스코프를 8개에서 10개로 늘린다 — `channels:read`·`groups:read` 추가 (D3, 9/10)
**결정**: 봇 토큰 스코프에 `channels:read`·`groups:read`를 더해 최소 10개로 한다. PRD §4의 "최소 스코프 8개"는 이 두 개를 포함한 10개로 갱신한다.

**이유**: `lib/slack/post.ts`의 `listConversations()`(`conversations.list`)와 `conversationMembers()`(`conversations.members`)가 이 스코프를 요구한다. 8개만으로는 두 호출이 `missing_scope`로 죽고, 그러면 세팅 화면의 **채널 연결 목록**과 **채널 멤버 전원 동의 확인**(ARCHITECTURE §불변식 8 · ADR-016)이 성립하지 않는다. 즉 이 두 스코프는 기능 추가가 아니라 이미 확정된 동의 게이트를 집행하기 위한 최소 조건이다. 실측으로 확인했다 — `conversations.list`가 `needed: channels:read,groups:read`를 반환했다.

**트레이드오프**: 읽기 범위가 "채널 목록과 채널 기본 정보"만큼 넓어진다. 메시지 본문 접근은 `channels:history`·`groups:history`가 이미 담당하므로 실질적 확대는 채널 메타데이터와 멤버 ID 목록에 그친다. 파일·이메일 본문 스코프는 여전히 요청하지 않는다. `channels:join`은 **추가하지 않는다** — 봇의 채널 진입은 사람이 초대하는 경로만 남겨, 수집 범위가 코드로 넓어지지 않게 한다.

### ADR-032: 음성은 업무 입력 전사로 제공하고, 음성 생체 식별은 MVP에서 제외한다 (D5, 9/11)
**결정**: S4에 브라우저 녹음 버튼을 제공하고, 서버의 `lib/llm.ts`에서 Groq Whisper로 한국어 전사한 뒤 사용자가 텍스트를 확인·수정해 기존 ASK 파이프라인으로 보낸다. 원본 음성은 저장하지 않는다. 회의 화자 식별은 동의한 멤버의 전사 라벨 매핑을 사용한다.
**이유**: Lindy도 음성 메모 전사·실행을 제공하지만, 사수의 차별점은 입력 수단이 아니라 부서 원칙·결정 원장·질문자 권한이다. 음성 지문 식별은 생체정보 동의, 화자 임베딩 모델, 오인식 시 저장 차단과 이의제기까지 별도 안전 설계가 필요하다. 현재 MVP의 동의 모델과 Recall/전사 라벨 경로로는 이를 정직하게 보장할 수 없다.
**트레이드오프**: 음성으로 사람을 자동 식별하지 못한다. 대신 브라우저 webm 등 짧은 음성 요청을 전사하고, 텍스트 확인 단계를 둬 오인식이 근거 없는 질문으로 실행되는 일을 줄인다. 생체 식별은 별도 명시적 동의와 공급자 평가 후 로드맵으로 둔다.

### ADR-033: Lindy 공개 기능군을 제품 확장의 기준으로 삼고, 비교 우월성은 실험으로 검증한다 (9/12)

- 배경: 사용자가 Lindy 기능을 흡수한 뒤 고도화하는 방향을 명시했다. 최신 공식 문서에는 개인/팀 컨텍스트, Skills, Routines, 회의, 파일, 실행 승인, MCP 연동이 있다. ADR-002의 초기 경쟁 조사에서 이를 없는 기능으로 추론하거나 권한 지원 자체를 SASU만의 차이라고 해석하면 안 된다.
- 결정: PRD §3에 전체 공개 기능군 흡수 목표를 반영한다. §8의 기존 제출 범위는 추가 일정 결정 전까지 유지한다. 조사 시점별 기능 목록, 실제 구현 상태, 시나리오 통과 증거를 별도로 관리한다.
- 검증: 동일 업무·권한·성공 기준으로 비교하기 전에는 Lindy보다 좋다고 홍보하지 않는다. 합성 데이터 정확도는 독립 검수 여부를 표시하며 단위 테스트 통과율과 구분한다.
- 근거 및 확장 순서: [기능 격차 분석](verification/lindy-capability-gap.md), [확대 평가](verification/expanded-evaluation.md).

### ADR-034: 제출 기준 문서를 정정하고 규칙에 의한 분류 누락을 제거한다 (9/12)

- 사용자 확인: 제출 전에 모두 반영할 문서는 원티드 신청·접수 문서다. 저장소의 `submission/원티드 지원서.md`와 제출 체크리스트를 기준으로 확인한다. Lindy 비교 계정은 없고, QA 도구 설정 경고를 기록한 뒤 테스트 계속 진행을 승인했다.
- 결정: 규칙을 모델 호출 제외 조건으로 쓰지 않는다. 동의·마스킹된 유효 저장 항목 모두를 기존 `llm.structured("classify")`로 의미 분류하며 규칙은 보조 신호·마감 추출에 남긴다. 본문 속 모델 지시를 따르지 않고 미결 결정·실행 요청·완료 사실·비업무 대화의 정의를 프롬프트에 명시한다.
- 안전 경계: 존재/삭제 검사, 4,000자 제한, unclassified 실패 처리, confidence 0.6 기준을 유지한다. 규칙 비후보이면서 confidence=null이면 카드로 자동 승격하지 않는다. 빈 본문은 모델·큐 쓰기 없이 종료한다.
- 트레이드오프: 기존 K개 후보 호출 대신 N개 유효 항목 호출로 비용·부하가 늘어난다. 전후 호출·토큰·지연·오탐·재현율을 기록한다. 기존 64문장은 회귀 평가이며 독립 블라인드 평가라고 부르지 않는다. Lindy 대비 우월성은 미검증이다.


### ADR-035: 공통 워커 배선과 답변 인용 전체 검증을 적용한다 (9/12)

- `kickWorker()`와 인증된 정기 트리거가 같은 진입점에서 전체 핸들러를 등록하고, 별도 sweep job 존재와 무관하게 pending sweep 후 claim한다. 경로별 핸들러 누락으로 정상 kind가 실패하는 일을 방지한다.
- 답변 인용이 하나라도 잘못되거나 0개면 전체 초안을 1회 재생성한다. 두 번째도 실패하면 canonical refused 문구만 저장·게시한다. 모델의 refused 자유 서술도 그대로 게시하지 않는다. 부분적으로 유효한 인용만 남기고 전체 초안을 유지하는 방식을 폐기한다.
- 사용자에게 보이는 본문과 인용은 기존 complete_answer 원자 저장을 유지한다. 문자열 검증은 의미적 뒷받침 판정이 아니며 추가 생성 비용과 거절률은 별도로 평가한다.
- Slack의 event_id를 업무 저장보다 먼저 독립 커밋하던 방식을 제거한다. 0014의 service-role 전용 ingest_slack_atomic에서 동의·연결 상태를 잠금 후 재검증하고 이벤트·item/answer·job을 함께 커밋한다. 실패 시 전체 롤백하며 미동의 본문은 저장하지 않는다. 일반 메시지 재전달로 원본/삭제 상태를 덮지 않는다. 운영 반영은 0012~0014 DB 마이그레이션 후 앱 배포 순서다.
- 실제 게이트웨이가 반환하는 llm_refusal 오류는 Q&A의 refused 종료로 매핑하되 네트워크/DB 오류는 숨기지 않는다. handler 성공 후 job 완료 기록만 실패한 경우에는 handler를 실패했다고 간주해 재큐잉하지 않는다. 이 경우 남는 running 작업의 복구는 lease 설계의 후속 범위다.
- 0015에서 authenticated/anon의 items·citations UPDATE/DELETE, classifications INSERT/UPDATE/DELETE를 회수한다. 기존 앱의 문서/회의 업로드 INSERT와 SELECT RLS, service-role 유지보수는 보존한다. 원문을 읽을 수 있다고 원문이나 모델 분류를 수정할 수 있는 것은 아니다. 신규 입력/인용 생성과 카드 명령별 권한 분리는 후속 검토로 남긴다.

### ADR-036: D6 판정 — 회의 봇은 컷, 입력은 전사 업로드로 확정한다 (9/13)

- 결정: ADR-005의 판정 조건(D6까지 봇 전사가 items로 들어오지 않음)이 충족됐다. Recall.ai 키가 발급되지 않았고 봇 실행 기록이 없으므로 PRD §8-2 컷 ②를 발동한다. 회의 입력은 이미 구현된 `.vtt/.txt` 업로드(lead 전용, 10MB, 미동의 화자 skip)가 유일한 경로다.
- 이유: 남은 4일(D6~D10)을 봇 연동·웹훅 서명·녹음 삭제 설정에 쓰면 절대 안 버리는 다섯(카드·원장·권한 차등·인용·게스트)과 D9 동의 흐름, 권한 쓰기 경계 보강이 밀린다. 업로드 경로로도 데모 장면 3(회의 보류 안건)을 재현할 수 있다.
- 동반 결정: 컷 ③(72h 병합)은 발동하지 않고 구현을 시도한다. 판정은 9/14 자정, 기준은 §11 DECIDE 행이다. 병합은 PRD §6-3 ⑥ 규칙(72h·0.85·visibility를 좁히지 않음)을 그대로 따르고 LLM 확인은 넣지 않는다.
- 트레이드오프: "Lindy·Otter처럼 회의에 봇이 들어온다"는 실현 가능성 어필을 잃는다. 제출물에는 로드맵으로만 적는다. 전사 파일을 사람이 내려받아 올리는 한 단계가 파일럿 사용성을 낮춘다.

### ADR-037: 병합은 임베딩 후보 + gpt-oss-20b 동일 안건 확인으로 한다 (9/13)

- 근거: `docs/verification/D6-merge-similarity-extended.md` — Voyage `voyage-4-lite` 24쌍 실측. 같은 안건 10쌍 0.582~0.784(중앙 0.720), 같은 대상·다른 결정 10쌍 0.537~0.842(중앙 0.701), 무관 4쌍 ≤0.498. 0.85는 같은 안건 0/10 병합, 0.70은 6/10 병합에 오병합 5, 0.55는 10/10에 오병합 9.
- 결정: 임베딩은 후보 선정(72h·≥0.55·visibility 좁힘 금지)에만 쓰고, 최종 판정은 `llm.structured("merge_confirm")` gpt-oss-20b strict schema `{same_decision: boolean, reason: string}` 1회. 후보가 여럿이면 유사도 순 최대 3개까지 확인하고 처음 참인 카드에 병합. 호출 실패·거절·스키마 오류는 병합하지 않음(새 카드).
- 게이트: 같은 24쌍 fixture에서 오병합(hard-different·different) 0건, 같은 안건 병합 7/10 이상. 미달이면 9/14 자정 PRD §8-2 컷 ③ 발동.
- 트레이드오프: PRD §8-0에서 미뤘던 LLM 확인을 앞당겨 결정 후보 1건당 최대 3회 분류 모델 호출이 늘어난다(`llm_calls`에 기록). 오병합은 잘못된 근거가 카드에 섞이는 것이라 누락(카드 2장)보다 비용이 크다고 판단했다. 유사도 분포는 합성 fixture 1회 측정이라 파일럿 실데이터에서 재측정한다.

### ADR-038: 부서 에이전트 역할을 문서 어시스턴트 위의 "기준표 평가"로 추가한다 (D7, 9/14)
- 배경: 2026-09-14 사용자 요청. 부서마다 에이전트에게 역할을 줄 수 있어야 한다. 예로 든 것은 HR의 "개발자 지원서·포트폴리오를 인재상·프로젝트 활용 방식 기준으로 검토해 점수표로 정리"다. 기존에는 시스템 프롬프트가 작업별로 코드에 고정돼 있고 `departments.template`도 `general` 1종이라 해당 기능이 없었다.
- 결정: lead가 부서 단위로 **역할(`agent_roles`)**을 만든다. 역할은 이름, 지시문, 평가 기준 1~10개(라벨·설명·가중치 1~5), visibility를 가진다. lead는 S7에 올린 문서를 골라 역할을 적용한다. 문서 1건당 `agent_role_results` 1행이 생기고 job `run_agent_role`이 gpt-oss-120b를 `llm.structured("run_agent_role")`로 1회 부른다. 기준마다 점수(0~5 정수 또는 null)·이유·인용을 받는다. 인용 quote가 그 문서 chunk에 포함되지 않은 기준은 점수를 버리고 "근거 없음"으로 표시한다. 총점은 모델이 아니라 코드가 계산한다. 분모는 **역할의 전체 기준 가중치 합**이고, 근거 없는 기준은 0점으로 반영한다(9/14 로컬 평가 정정: 근거 있는 기준만 평균하면 기준 1개만 5점인 문서가 3개 모두 5점인 문서와 같아졌다). 화면은 "근거 없음 (0점 반영)"으로 표시한다. 근거 없는 기준의 `rationale`은 모델이 null로 낼 수 있다. 유효 기준이 0개면 `failed(citation_invalid)`다.
- 범위를 이렇게 좁힌 이유: ① 기존 문서 업로드·마스킹·chunk·인용 검증·jobs를 그대로 재사용해 9/17 프리징 안에 끝낼 수 있다. ② 슬랙·회의 관찰이나 카드 생성까지 역할을 반영하는 범용 에이전트는 기존 파이프라인 회귀 위험이 커서 로드맵으로 둔다. ③ "역할"은 자유 채팅이 아니라 **기준표 + 인용**이다. 사수의 불변식(인용 없는 문장은 렌더하지 않는다)을 지키려면 출력 형태가 고정돼야 한다.
- 채용 사용의 전제 (PRD §8-1의 "인사평가 보조" 제외와의 관계): 제외 대상은 **구성원 감시·인사평가**이며 그대로 유지한다. 외부 지원자의 서류 검토 보조는 아래 조건에서만 허용한다.
  - AI는 점수와 근거만 낸다. 합격·탈락 판정 필드는 없고 자동 발송·자동 탈락도 없다. 화면에 "참고용 · 최종 판단은 담당자" 고정 문구를 둔다. 완전 자동화된 결정이 되지 않게 해 개인정보보호법 제37조의2(자동화된 결정) 대상 여부 논쟁을 피한다 `(확인 필요: 법률 자문)`.
  - 시스템 프롬프트에 직무와 무관한 특성(나이·성별·출신지역·혼인·가족·종교·장애·외모·사진·출신학교 서열 등)을 점수에 반영하지 말라는 고정 가드를 넣는다. lead의 지시문이 이를 덮어쓸 수 없다. 채용절차법 제4조의3(직무 수행과 무관한 개인정보 요구 금지) 취지다.
  - 역할의 visibility 기본값은 `leads_only`다. 결과의 visibility는 역할과 문서 중 더 좁은 것을 따른다(ARCHITECTURE §3.7).
  - 업로드 화면에 "지원자에게 개인정보 수집·이용 동의를 받은 문서만 올리세요" 고지를 둔다. 원본 파일은 기존대로 저장하지 않는다. 삭제는 기존 소스 제거 경로를 쓴다.
- 기각한 대안: ① 부서별 자유 시스템 프롬프트(인용 강제·거절 판정이 성립하지 않음) ② 모델이 총점·합불을 직접 출력(검증할 수 없는 수치가 결정처럼 읽힘) ③ 역할을 카드·답변 파이프라인 전체에 주입(3일 안에 회귀 검증 불가) ④ 로드맵만 제시(사용자가 9/14 구현을 선택).
- 일정: PRD §9 진행 기록의 "9/14~9/17은 버그픽스만"을 이 기능 1건에 한해 사용자 결정(9/14)으로 예외 처리한다. D10(9/17) 프리징은 유지한다. 9/16 자정까지 로컬 검증(§11 "부서 역할" 행)을 통과하지 못하면 컷 라인 ⓪순위로 기능을 숨기고 제출서에는 로드맵으로 적는다.

### ADR-039: 로드맵 ④ "인사평가 보조"를 "채용 예고편"으로 교체한다 (9/14)
- 배경: 2026-09-14 사용자가 다른 아이디어 "직업예고편"(입사 전에 실제 직무를 게임처럼 체험하는 웹)을 사수와 비교해 달라고 했다. 아이디어만 놓고 보면 원티드 본업(채용)과의 연결과 발표 전달력은 직업예고편이, 기술 깊이와 해자는 사수가 앞섰다. 사용자는 이를 "회사가 실제 업무와 문서를 넣으면 회사별 게임이 만들어지고 사전과제로 쓰는" 형태로 구체화했고, 사수와 결합하기로 했다. 한편 기획서 v3 §09 로드맵 ④ "인사평가 보조"는 기획서 스스로 "가장 위험한 프레이밍"이라고 적어둔 항목이다.
- 결정:
  1. 로드맵 ④를 **채용 예고편**으로 교체한다. 사수의 결정 원장(가시성 `dept`)과 원칙 문서를 가상화해 지원자가 입사 전에 2D 오피스 게임으로 체험하고, 합격하면 같은 부서 사수가 온보딩을 맡는다. 컨셉·불변식·단계는 [proposal/채용예고편_컨셉.md](proposal/채용예고편_컨셉.md)에 있다.
  2. **구성원 인사평가 보조는 로드맵에서도 뺀다.** 지금까지는 "발표에서 로드맵 한 줄"로 남겨 뒀다. 외부 지원자 서류 검토 보조(ADR-038, S8)는 그대로 둔다.
  3. **9/20 제출 범위는 바꾸지 않는다.** 구현도, 게스트 모드 목업도, 제출서 기재도 없다. 발표 로드맵 한 줄과 본선 Q&A에서만 말한다. D10(9/17) 프리징은 유지한다.
  4. 게임 UI는 ZEP류 2D 탑뷰 메타버스 문법(아바타 이동, 오브젝트 상호작용, NPC 말풍선)을 따르되 **자체 구현**한다. ZEP 플랫폼과 에셋은 쓰지 않는다.
  5. 공개 예고편(익명·채점 없음, R1)을 사전과제 예고편(동의·채점, R2)보다 먼저 한다. R2는 법률 자문을 받은 뒤에 연다.
- 이유: ① 이번 대회에서 사수의 가장 약한 고리였던 "원티드 본업과의 거리"를 새 기능 없이 서사로 메운다. ② 구성원 인사평가보다 위험이 낮다. 평가 대상이 동의한 외부 지원자이고 AI는 합불을 내지 않는다. ③ 사수에 이미 있는 원장·원칙 문서·ROLES·인용 검증을 재료로 쓰므로, 직업예고편 단독안의 약점(회사별 입력 부담, 공통 콘텐츠와의 중복)이 줄어든다. ④ ZEP류 문법은 설명 없이 조작할 수 있고, 사수의 개념(원칙 문서·회의·스레드·카드·원장)을 방 하나하나로 옮기기 좋다.
- 조건(가드): 입력은 `dept` 원장과 원칙 문서뿐이고 원시 발언은 제외 · 발행 전 원문 겹침 검사, 고유명사 검사, lead 승인 · 합불·추천 필드와 일괄 불합격 없음 · 모든 점수에 지원자 본인의 행동·답변 인용 · NPC는 사실집 밖 사실을 말하지 않음 · 조작은 채점하지 않고 목록형 모드 제공 · 예고편 결과를 입사 후 평가에 쓰지 않음. 법령 쟁점(AI 기본법 제2조 제4호 사목, 개인정보보호법 제37조의2, 채용절차법 제4조의3·제11조)은 컨셉 문서 §9에 정리했다 `(확인 필요: 법률 자문)`.
- 트레이드오프: 원티드와 이어지는 서사를 얻는 대신, 본선에서 "채용 AI"에 대한 규제·차별·대리 풀이 질문을 받게 된다. 답변 골자는 컨셉 §13에 준비했다. 발표에서 두 제품처럼 들리면 "부서 단위 + 결정" 서사가 흐려지므로 로드맵 한 줄과 Q&A로만 말하고 데모하지 않는다. 사전과제 모드는 고영향 AI 의무가 걸려 있어 1인 규모로 운영하기 어려울 수 있다(컨셉 가설 T6).
- 기각한 대안: ① 직업예고편으로 단독 피벗(제출까지 6일이고, 이미 배포된 사수를 버리게 된다) ② 인사평가 보조 유지(구성원 대상이라 감시 프레임) ③ 제출 전에 게스트 모드에 예고편 화면 추가(모조 UI 금지, 프리징 위반) ④ ZEP 플랫폼 위에 구현(지원자 데이터가 제3자를 거치고 RLS·인용 검증을 집행할 수 없다) ⑤ 예고편 점수를 입사 후 평가·성과와 개인 단위로 연결(감시 프레임이자 목적 외 이용. 집계 타당도 연구만 R4로 둔다) ⑥ 게임 점수를 "적합도 예측"으로 표기(정답 데이터가 없다).

### ADR-040: 채용 예고편 R1 체험 슬라이스 개발 착수 (9/15)

- 배경: 사용자가 채용예고편 개발 착수를 요청했다. ADR-039의 구현 유보를 PRD §3-1·§8-1 범위에서 변경한다.
- 결정: 합성 퀘스트 3개, 맵 1장, 선택지 NPC, 사실집 인용, 단서 수첩, 결정 작성, 기록실 비교를 우선 완주한다. `/trailers`는 서버 환경 변수 `SASU_TRAILER_PREVIEW_ENABLED=true`일 때만 열고 기본 404·noindex로 둔다. 기존 제출·게스트 동선에 추가하지 않는다.

- 구현: React/CSS 자체 탑뷰 맵과 같은 콘텐츠의 목록 모드를 사용한다. 최초 맵은 방 사이의 자유 이동이며 Phaser/Tiled 의존성은 도입하지 않는다. NPC 응답과 기록실 이유는 사실집의 문자열 인용 검증을 통과해야 한다.
- 이유/한계: 첫 실행 경로와 접근성을 외부 서비스 없이 검증한다. 합성 사례는 가상화 품질·기밀 차단·실제 채용 효과의 증거가 아니다. R1 전체 및 R2 채점은 완료로 표시하지 않는다. D10 프리징과 R2 법률 자문 전제는 유지한다.

### ADR-042: 운영 중인 쓰기 경계 구멍 2건을 신규 기능보다 먼저 고친다 (9/15)
- 배경: 설계 조사 중 발견하고 외부 리뷰(Codex, 9/15)가 마이그레이션 근거로 확인했다. Supabase 기본 `authenticated` 테이블 권한이 전제다. ① `departments_member_access`가 `FOR ALL`이고 USING·WITH CHECK 모두 부서 `id`만 `can_see()`에 넘기며 `departments` 쓰기 회수가 없다(0002:62). 멤버가 자기 부서의 `org_id`를 데모 조직으로 바꾸면 anon 데모 정책(0002:295) 때문에 실제 부서 데이터가 익명 조회 대상이 된다. ② `items_source_access`가 `FOR ALL`이고 0015는 UPDATE·DELETE만 회수했다. member는 `dept` 소스, lead는 `leads_only` 소스에 마스킹하지 않은 본문을 PostgREST로 직접 넣을 수 있다(불변식 9 위반).
- 결정: phase `8-security-hotfix`를 모든 신규 phase보다 먼저 한다. `departments`는 SELECT 전용 정책 + authenticated·anon INSERT·UPDATE·DELETE 회수. `items`는 authenticated INSERT 회수. 문서·전사 업로드는 CLAUDE.md가 허용하는 "수집 어댑터 insert"로서, 라우트가 세션으로 lead를 검증하고 `lib/mask.ts`로 마스킹한 뒤 service role로 insert한다. SQL에 마스킹 정규식을 복제하지 않는다. 보안 하니스(`scripts/verify-security-sql.mjs`)에 Supabase 기본 GRANT를 먼저 적용하는 단계를 넣고, 전 테이블의 authenticated 직접 쓰기 경계를 표 테스트로 고정한다.
- 이유: 둘 다 지금 배포된 서비스 링크에서 열려 있는 경로다. 조직 단위 권한(ADR-044)이 생기면 ①의 영향이 커진다. 기존 하니스(PGlite)는 Supabase 기본 GRANT를 재현하지 않아 이 종류의 구멍을 못 잡는다.
- 운영 반영: 되돌리기 어려운 DB 변경이므로 **사용자 승인 후** 적용한다. 적용 전 기존 E2E(게스트·세로 슬라이스·권한·역할·문서 업로드) 전부 통과.
- 기각한 대안: ① items INSERT를 lead + 소스 종류로만 제한(lead의 마스킹 우회가 남는다) ② SQL 트리거로 마스킹 패턴 거부(정규식이 TS와 SQL 두 곳에 생겨 어긋난다) ③ 신규 기능과 같은 마이그레이션에 섞기(컷할 때 보안 수정까지 빠진다).

### ADR-043: 메인 웹사이트는 같은 앱의 정적 페이지로 만든다 (9/15)
- 배경: 서비스 링크로 들어온 심사위원·투표자가 처음 보는 `/`가 자리표시 한 줄("사수" + 데모 링크)이다. metadata·OG·아이콘·robots·sitemap이 없고, 전역 CSS의 `main`·`h1`·`a` 요소 규칙이 레이어 밖에 있어 Tailwind 유틸리티를 이긴다.
- 결정: `app/(site)` 그룹의 정적 서버 컴포넌트로 `/`(히어로·문제·작동 방식·차이·권한별 답·신뢰·조건부 예고편·CTA·푸터)와 `/privacy`(개인정보 처리 안내, 법률 검토 전 초안 표시)를 만든다. 파일럿 문의·데모 영상·투표 링크는 서버 환경 변수(`SASU_PILOT_CONTACT_URL`·`SASU_DEMO_VIDEO_URL`·`SASU_VOTE_URL`, `https:`/`mailto:`만)로 받고 비어 있으면 버튼을 렌더하지 않는다. 해석은 `lib/site.ts` 하나(TDD). 새 화면 전에 전역 요소 규칙을 `@layer base`로 옮기고 토큰을 `@theme inline`에 등록하며, 회귀 캡처로 기존 화면을 비교한다. 제품 화면 이미지는 게스트 모드 실제 캡처만 쓴다.
- 이유: ADR-007(런타임 하나). 정적이라 투표 트래픽과 DB 장애에 무관하다. 자체 문의 폼은 개인정보 보관·파기·스팸 방어를 새로 만든다.
- 카피 금지선: "감시·대체·평가"(부정문 포함), "적합도 예측", AI가 거른다는 긍정 서술, 경쟁사 실명·우월성 주장(ADR-033), 출처 없는 수치.
- 기각한 대안: 별도 마케팅 사이트(관리 대상 2개), 자체 문의 폼, 애니메이션·아이콘·UI 라이브러리 추가(프리징 직전 번들·공격면 증가), HTML로 다시 그린 가짜 제품 화면.

### ADR-044: 고객사 조직 관리자 — 권한만으로는 내용을 볼 수 없고, 권한을 올리는 작업은 부서장만 한다 (9/15)
- 배경: 사용자 요청("관리자 페이지"), 대상은 고객사 조직 관리자. 지금은 조직 단위 역할이 없고 멤버 추가·부서장 지정이 service role 시드 스크립트로만 가능하다.
- 결정:
  1. `org_admins` 테이블과 판정 함수 `is_org_admin()` 하나. 관리 데이터는 SECURITY DEFINER RPC가 메타데이터만 반환한다(부서·멤버·동의·소스 메타·답변 메타데이터·AI 호출 수·관리 기록). 질문 원문·질문자·대화 본문·카드·원장 내용은 반환하지 않는다. `can_see()`는 바꾸지 않는다. 조직 id는 SQL이 `auth.uid()`에서 정한다.
  2. 권한 분리: 조직 관리자는 부서 생성, **멤버 0명인 부서의 첫 부서장 초대(자기 이메일 금지)**, 권한 축소(부서장 해제·멤버 제외), 조직 공개 예고편 허용, 예고편 철회만 한다. 기존 부서의 멤버 초대와 부서장 승격은 이미 내용을 볼 수 있는 부서장이 S5에서 한다.
  3. 신규 함수는 전부 `revoke all … from public, anon, authenticated, service_role` 후 최소 grant. 여러 게이트가 공유하는 내부 함수는 `private` 스키마. 데모 래퍼는 조직 인자 없음. `(dept_id, org_id)` 복합 FK.
  4. 초대: 토큰 해시만 저장, 7일, 1회용, `auth.jwt()` 이메일 일치, 수락 시 표시 이름 입력, 수락·철회 시 해시 무효화.
  5. 동의: 수집 범위가 바뀌지 않으므로 수집 동의 버전은 올리지 않고, 관리자 열람 범위를 동의 화면·동의 DM·파일럿 동의문에 **고지**로 추가한다 `(확인 필요: 법률 자문)`.
  6. 권한 경계 판정("위반 N건")은 제공하지 않는다. `answers`에 전달 경로·질문 당시 역할이 없어 계산할 수 없는 값을 안전 판정처럼 보여주게 된다.
  7. 첫 조직 관리자는 운영 스크립트로만 지정한다. `/demo/admin`은 같은 화면을 읽기 전용으로, 이메일·초대·관리 기록 없이 보여준다.
- 이유: 외부 리뷰 R-2 — 관리자가 자기(또는 보조) 이메일을 부서장으로 초대할 수 있으면 "관리자는 내용을 보지 않는다"가 거짓이 된다. 권한을 올리는 작업을 이미 권한을 가진 부서장에게만 주면 상승 경로가 "빈 새 부서의 첫 부서장"으로 줄어든다.
- 남는 한계: 관리자가 보조 이메일로 빈 새 부서의 첫 부서장이 될 수 있다. 기존 부서 내용에는 닿지 않고, 이후 합류하는 멤버에게 부서장으로 표시되며 동의는 그 뒤에 받는다. 동의문·발표에서 숨기지 않는다.
- 기각한 대안: ① 관리자에게 부서 콘텐츠 열람권(감시 도구로 읽힌다) ② 관리자가 모든 초대·승격(자기 승격) ③ 동의 v2를 웹에만 강제(슬랙 수집과 모순, R-7) ④ URL에 `[org]`(IDOR 검증 지점만 늘어난다) ⑤ 사용량 화면(`cost_usd`가 null — 호출 수 한 줄로 대체).

### ADR-045: 채용 예고편 실데이터 발행과 합성 지원자 채점을 9/20 제출에 포함한다 (9/15)
- 배경: 사용자가 9/15에 두 번 "발행 + 합성 지원자 채점까지, 제출 포함"을 선택했다. ADR-040의 "9/20 게스트·제출물 제외"와 PRD §8-1의 해당 행을 이 결정으로 대체한다. phase 7(ADR-040·041)의 합성 체험 범위와 step 파일은 바꾸지 않는다.
- 결정:
  1. **발행**: lead가 원장 결정 1~3건(가시성 `dept`, 최신 정정본) 선택 → job이 결정당 `llm.structured("trailer_generate")` 1회로 `TrailerScenario[]` 생성 → phase 7의 `validateScenario` → 워커가 결정적 검사(20자 이상 원문 겹침·고유명사·마스킹 패턴) → lead 원문 대조·수정 → **항목별 공개 승인** → 발행. 입력은 결정의 `outcome`·`rationale`·카드 제목·`dept` 원칙 chunk뿐이다(원시 발언·카드 배경·인용 quote 제외).
  2. **발행 조건 세 가지**: ① 검사 통과(`gate_passed_hash`) ② 전 항목 승인(`approval_hash`) ③ 조직 관리자가 켠 `orgs.trailer_publish_enabled`. `publish_trailer`는 SQL에서 현재 시나리오 해시가 두 해시와 같을 때만 slug를 발급한다. 검사 기록 RPC는 service_role 전용이고 통과했을 때만 해시를 쓴다.
  3. **공개 조회**: `public_trailer(slug)` anon RPC가 `{scenarios, apply_url}`만 반환한다. noindex, LLM·쓰기·분석 0. 철회하면 즉시 캐시를 지우고, 재발행하면 새 slug를 쓴다.
  4. **합성 지원자 채점**: 합성 attempt 3건에 job `score_trailer_attempt`(`AGENT_ROLE_SYSTEM_GUARD` 재사용)를 돌린다. 점수 근거는 이유 서술 문자열·이벤트 seq·선택 사실 id만 인정하고, 확인하지 않은 대화 id는 면접 질문 근거로만 쓴다. 총점은 `weightedScore()`. 합불·추천 필드 없음. **실제 지원자(`kind='candidate'`)는 `orgs.trailer_assessment_enabled`(운영 스크립트만 변경, 기본 off)가 꺼져 있으면 RPC와 트리거가 거부한다.** 실제 지원자 초대·동의·보관 파기는 만들지 않는다.
  5. 게스트: `/demo/d/[dept]/trailers`(읽기 전용: 원장 → 검사 → 발행 → 점수표)와 공개 체험 링크. 데모 시나리오·점수는 실제 파이프라인 실행 결과를 스냅샷으로 시드한다.
- 이유: 합성 체험만으로는 "사수가 아는 부서의 결정으로 예고편을 만든다"는 결합 서사가 시연되지 않는다. 자동 검사는 바꿔 쓰기·분할·전략 수치 노출을 막지 못하므로(외부 리뷰 R-4) 사람의 항목별 승인과 조직 단위 허용을 조건으로 둔다.
- 법적 한계: 채용 평가는 AI 기본법 고영향 영역(제2조 제4호 사목)이다. 실제 지원자 채점은 법률 자문 전 비활성으로 두고, 제출물·발표에서 "합성 지원자"임을 명시한다. "적합도 예측"·AI가 거른다는 표현은 쓰지 않는다.
- 기각한 대안: ① 합성 체험만 제출(외부 리뷰 권고, 사용자 선택과 다르다) ② 검사 통과만으로 발행(자동 검사의 한계) ③ 실제 지원자 채점을 켜고 제출(법률 자문 전) ④ 원시 발언을 생성 입력에 포함(목적 외 이용) ⑤ 한 LLM 호출로 결정 3건 생성(300초 상한·부분 실패).

### ADR-046: 기능 프리징을 9/19 12:00로 옮기고, 운영 DB 반영은 phase 검증 뒤에만 한다 (9/15)
- 배경: ADR-042~045의 범위는 D10(9/17) 프리징 안에 들어가지 않는다. 외부 리뷰(R-3)는 "4일에 화면 13개·마이그레이션 4개·job 3종은 비현실적이니 지금 컷하라"고 판정했다. 반대 근거는 이 저장소의 실행 기록이다: phase 3(D6~D10, step 15개)과 phase 4(부서 역할, step 7개)가 각각 하루에 끝났다.
- 결정: 기능 프리징을 9/19 12:00로 옮긴다. phase 순서는 8 보안 핫픽스 → 9 메인(병행 가능) → 10 조직 관리 → 11 예고편 발행 → 12 합성 채점이고, 마이그레이션 번호는 이 순서로 직렬이다. **각 phase의 마이그레이션은 그 phase의 보안 하니스·E2E가 통과한 뒤에만 운영 DB에 적용한다.** 컷은 코드 삭제가 아니라 플래그 끄기 + 해당 phase 마이그레이션 미적용이다. 컷 순서와 판정 시각은 PRD §8-2.
- 이유: 라우트 플래그만 끄면 이미 적용된 테이블·RPC의 공격면이 남는다(R-3). 판정을 날짜에 박아야 밀린 기능이 제출 품질을 잠식하지 않는다.
- 절대 안 버리는 것: 보안 핫픽스 · 기존 5개(카드·원장·권한 차등·인용·게스트) · 메인 최소판 · 서비스 링크 안정성.
- 보정(9/15): DB가 필요한 E2E를 언제 돌리는지는 ADR-047이 정한다. 운영 DB가 하나뿐이라 위 굵은 문장을 문자 그대로 실행할 수 없다.

### ADR-047: 운영 DB가 하나뿐이므로, DB가 필요한 E2E는 마이그레이션 적용 뒤 기능 플래그를 끈 상태에서 돌린다 (9/15)
- 배경: ADR-046과 불변식 22는 "그 phase의 보안 하니스·E2E가 통과한 뒤에만 운영 DB에 적용"한다고 정했다. 하지만 Supabase 프로젝트는 운영 하나뿐이고 로컬 개발·E2E도 그 DB를 쓴다. 관리 RPC나 예고편 테이블을 쓰는 E2E는 마이그레이션이 적용된 DB에서만 돌 수 있어서, 문구대로면 적용 조건과 적용이 서로를 기다린다. 대안도 마땅치 않다. 로컬 Supabase(Docker)는 여유 메모리 약 1.1GB에서 OOM 위험이 있다(이 PC에서 하네스가 두 번 강제 종료됐다). 스테이징 프로젝트는 계정 작업·무료 한도·Auth URL 설정이 필요하다.
- 결정 (9/15 사용자 선택, 실행 플랜 `sasu-scope-expansion-2026-09-15` D-2 B안):
  1. 운영 적용 조건: 그 phase의 보안 하니스(PGlite — RPC 흐름·함수 실행 권한·쓰기 경계 포함), DB가 필요 없는 E2E, 단위 테스트·빌드, Claude 리뷰가 모두 통과해야 한다.
  2. 적용 순서: 마이그레이션을 운영에 적용한다 → 기능 플래그를 끈 채 배포한다 → 로컬 서버(플래그 on)와 운영 DB로 전용 QA 조직(`is_demo=false`, 파일럿·데모 조직과 분리)에서 E2E를 돌린다 → 통과하면 플래그를 켜고 배포한다.
  3. E2E가 실패하면 플래그를 끈 채 고친다. 컷 판정 시각까지 통과하지 못해 컷하면 `supabase/rollback/<번호>_*_down.sql`로 그 phase의 테이블·RPC를 제거한다. DROP은 훅이 막으므로 사람이 SQL 편집기에서 실행한다. "컷된 기능의 테이블·RPC를 운영 DB에 남기지 않는다"는 ADR-046의 목적은 그대로 지킨다.
  4. 운영 쓰기 E2E와 실제 LLM 데모 스냅샷은 phase마다 사용자 승인을 받은 운영 반영 단계에서만 한다.
- 이유: 보안 보증은 E2E가 아니라 보안 하니스에서 나온다. RPC 권한·조직 일치·쓰기 경계는 PGlite가 검사한다. 플래그를 꺼도 RPC는 PostgREST로 호출할 수 있으므로 하니스 통과를 운영 적용의 필수 조건으로 둔다. phase 4 운영 반영(0023·0024)도 같은 순서로 통과했다.
- 남는 위험: 플래그 off 기간이나 롤백 전까지 새 RPC가 운영 DB에 있다. QA 조직 데이터가 운영 DB에 남는다(RLS로 다른 조직과 분리됨).
- 기각한 대안: ① 로컬 Supabase(메모리) ② 스테이징 프로젝트(계정 작업·한도) ③ 문구 유지(실행할 수 없다).
